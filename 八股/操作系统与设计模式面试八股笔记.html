操作系统与 Linux 总览

这两章导读的目的不是增加背诵量，而是先把后面会反复出现的对象放进同一张地图。操作系统可以先理解成一层“资源管理与保护软件”：它把有限的 CPU、内存、磁盘、设备和网络能力，组织成多个程序可以安全、并发、相对方便地使用的抽象。

先建立五个核心抽象

现实资源 操作系统提供的抽象 后文会在哪里展开
CPU 时间 进程、线程、调度 第 2～5 章
物理内存 虚拟地址空间、页、页表 第 6～7 章
磁盘与设备 文件、目录、文件描述符 第 8 章
外设事件 中断、系统调用、IO 第 1、9 章

这张表是本部分的主线：程序想运行，就要获得 CPU；程序想保存数据，就要经过内存和文件系统；程序想和别的程序或机器协作，就要经过 IPC 或网络；所有资源访问都要受到权限和并发规则的约束。

一次普通操作经过了什么

可以用“在终端执行命令并读取一个文件”作为贯穿全篇的例子：

键盘输入
  ↓
终端/TTY 接收字符
  ↓
Shell 解析命令、创建或查找进程
  ↓
用户程序调用 libc，libc 进一步发起系统调用
  ↓
CPU 从用户态进入内核态，内核检查权限并调度资源
  ↓
文件系统定位目录、inode 和数据块，必要时等待磁盘
  ↓
中断通知 IO 完成，内核把结果交给进程
  ↓
程序得到字节，Shell 再把结果显示到终端

这条路径可以帮助理解几个容易混淆的词：系统调用是程序主动请求内核服务的入口；中断是硬件或内核事件让 CPU 暂停当前执行、转去处理另一件事的机制；进程是资源隔离和调度的基本容器；文件描述符是进程访问文件、管道和 socket 的统一句柄。

Linux 到底由哪些层组成

  • 硬件：CPU、内存、磁盘、网卡和其他设备。
  • Linux 内核：负责调度、内存管理、文件系统、驱动、网络协议栈和安全隔离。
  • 系统调用接口与 libc：应用与内核之间的稳定接口；read、write、fork 等通常通过 libc 进入内核。
  • Shell 与系统工具：bash、zsh、ps、find 等是用户态程序，不等于内核本身。
  • 发行版：Ubuntu、Debian、CentOS 等是内核、工具链、包管理器、初始化系统和默认配置的组合。

因此，“Linux 系统”不只是一份内核，也不只是一串命令。后文讲 Linux 命令和排障时，默认读者已经知道这些命令只是通过系统调用观察或改变内核维护的状态。

Linux 基础：命令行、文件、用户与进程环境

本章只补齐阅读后文所需的最低限度 Linux 背景，不把它写成完整的 Linux 运维手册。目标是让没有 Linux 使用经验的人，看到 fd、/proc、权限、管道和进程命令时，知道它们在系统中的位置。

Terminal、TTY 和 Shell 的区别

  • Terminal 是终端程序或终端设备，负责让人输入和看到输出。
  • TTY 是内核提供的终端设备接口；远程登录时通常会得到一个伪终端（PTY）。
  • Shell 是解释命令的用户态程序，例如 bash。它负责解析参数、展开变量、连接管道，并启动其他程序。

输入 ls -l 时，Shell 并没有“内置完成所有工作”：它解析出程序名和参数，找到 ls，创建或启动进程，并为标准输入输出准备好文件描述符；ls 再通过系统调用读取目录并输出结果。

路径、目录和常见目录

  • /var/log/app.log 是绝对路径，从根目录 / 开始。
  • ./app 表示当前目录下的 app，../app 表示父目录下的 app。
  • pwd 查看当前目录，cd 修改 Shell 的当前工作目录；当前目录是进程环境的一部分，不是全局变量。
目录 最低限度的理解
/etc 系统和服务的配置
/var 经常变化的数据，如日志、缓存、队列
/home 普通用户的家目录
/tmp 临时文件，权限和清理策略需特别留意
/proc 内核和进程状态的伪文件系统，第 11 章会用它排障
/dev 设备文件和部分特殊设备接口

目录本质上也是一种文件系统对象，用来把名字映射到 inode；文件名不等于文件内容，inode、数据块和文件描述符的关系会在第 8 章完整展开。

用户、用户组与权限

Linux 通过用户 ID、组 ID 和权限位限制资源访问。最常见的三组权限对象是：文件所有者（user）、所属组（group）和其他人（other）；每组权限通常由读 r、写 w、执行 x 组成。

-rwxr-x---
 ↑   ↑  ↑
 所有者 组  其他人

对普通文件，r 通常表示读取内容，w 表示修改内容，x 表示作为程序执行；对目录，r 表示列出名字，w 表示增删目录项，x 表示进入目录并访问其中对象。删除文件主要取决于父目录的写和执行权限，这是排障中很容易误判的一点。

root 是权限能力很强的特权用户，sudo 是在授权规则允许时临时以更高权限执行某条命令。权限越高，误操作影响范围越大，所以排障时应先确认目标路径和命令作用范围。

标准输入、输出、错误和文件描述符

进程启动时通常会拥有三个标准流：

  • stdin（fd 0）：标准输入；
  • stdout（fd 1）：正常输出；
  • stderr（fd 2）：错误或诊断输出。

文件描述符（fd）只是进程内的一个整数索引，背后可能指向普通文件、管道、socket、终端或设备。于是很多看似不同的 IO，都能通过统一的 read/write 接口处理。

command > result.log       # stdout 写入文件
command 2> error.log       # stderr 写入文件
command > all.log 2>&1     # 先把 stdout 指向文件，再让 stderr 跟随 stdout
producer | consumer        # stdout 接到下一个进程的 stdin

管道和重定向不是 Shell 的“魔法数据通道”，而是 Shell 创建 fd、调用 pipe/dup2 等系统调用后，把多个进程连接起来。第 3、8、10、11 章会分别从 IPC、文件系统和排障角度再次使用它们。

1. 内核态与用户态、系统调用、中断详解

题目

什么是内核态和用户态？为什么要区分？系统调用的完整流程是怎样的？中断是什么，软中断和硬中断有什么区别？

这道题在考什么

这是操作系统面试的"第一块地基"。面试官问它，不是要你背 Ring 0/Ring 3 这些名词，而是想确认一件事：你写的每一行代码（read 文件、new 内存、发网络包）最终都要落到内核头上，你知不知道这条"从应用到硬件"的完整通路。后面几乎所有 OS 话题——进程切换、缺页中断、零拷贝、epoll——都建立在"用户态/内核态切换有成本"这个事实上，这道题答不好，后面的"为什么慢、怎么优化"都无从谈起。

思考路径也很自然：先问"为什么要分两个态"（答案是保护——不设墙，任何程序都能搞垮整台机器）；有了墙就有新问题——"应用怎么合法地穿墙"（答案是系统调用这个唯一入口）；再进一步——"除了应用主动穿墙，还有什么事件会把 CPU 拽进内核"（答案是中断和异常）。三个子问题就是"设墙 → 开门 → 门铃"的一条线，答题时按这条线讲，逻辑自己就通了。

面试核心结论

CPU 通过特权级把运行环境分成两档：用户态跑应用代码，只能访问受限的指令和自己的地址空间；内核态跑操作系统代码，可以执行特权指令、访问所有硬件资源。划分的目的是保护——应用程序有 bug 或恶意行为时，破坏范围被圈在自己进程内，碰不到内核和其他进程。应用需要硬件服务（读文件、收发网络包、申请内存）时，唯一的正规入口是系统调用：通过专用指令陷入内核，内核校验参数、代表进程完成操作再返回。中断是硬件/软件打断 CPU 当前工作的机制：硬中断由外设异步触发（网卡收包、时钟），软中断由内核调度执行耗时的后半段处理；Linux 用"上半部快速响应 + 下半部延后处理"的结构避免长时间关中断。

为什么要区分内核态和用户态

假设没有这道墙：任何程序都能直接改页表、操作磁盘控制器、修改其他进程的内存——一个野指针就能让整台机器崩溃，恶意程序可以为所欲为。所以 CPU 硬件层面提供特权级（x86 的 Ring 0 ~ Ring 3，实际只用 Ring 0 和 Ring 3）：

维度 用户态（Ring 3） 内核态（Ring 0）
运行的代码 应用程序 内核、驱动
可执行指令 普通指令 全部指令（含特权指令：改页表、开关中断、访问 IO 端口）
可访问内存 本进程用户空间 全部物理内存
崩溃影响 本进程被杀 整机宕机（内核 panic）

进程的虚拟地址空间也按此划分：用户空间（低地址）+ 内核空间（高地址，所有进程共享同一份内核映射）。用户态代码访问内核地址直接触发段错误。

一句话总括：这道墙用一次"陷入内核"的切换成本，换来了故障隔离和安全边界。

什么时候会从用户态切到内核态

三种入口，面试必背：

  1. 系统调用：应用主动请求内核服务，例如 read、write、fork。这是唯一的"主动"入口。
  2. 中断：外设异步打断，例如网卡收到数据、时钟滴答。与当前进程无关，纯属"被打断"。
  3. 异常：当前指令执行出错，例如缺页异常（详见第 6 章）、除零、非法指令。由当前进程"闯祸"触发，处理后可能恢复执行（缺页）也可能杀进程（段错误）。

三者统一的处理骨架：保存现场（寄存器、程序计数器）→ 切到内核栈 → 执行内核处理函数 → 恢复现场返回。

系统调用的完整流程

以 read(fd, buf, len) 为例：

① 应用调用 glibc 封装的 read()
② glibc 把系统调用号（read = 0）放入约定寄存器（rax），参数放入 rdi/rsi/rdx
③ 执行 syscall 指令 → CPU 切换到内核态，跳转到内核的系统调用入口
④ 内核保存用户态现场，按调用号查系统调用表，找到 sys_read
⑤ sys_read 校验参数（fd 是否有效、buf 是否是本进程合法地址），执行真正的读取
⑥ 结果写入返回值寄存器，执行 sysret/iret 返回用户态，恢复现场
⑦ glibc 拿到返回值：>= 0 是成功结果，负值转换成 -1 并设置 errno

要点：

  • 应用平时调用的 read/malloc 是 C 库函数，库函数内部才可能发起系统调用；malloc 多数时候在用户态的内存池里就地分配，只在池不够时才用 brk/mmap 系统调用向内核要内存（详见《C++ 篇》第 6 章）。区分"库函数"和"系统调用"是高频追问。
  • 系统调用有固定开销：两次特权级切换、现场保存恢复、安全校验，比普通函数调用贵一到两个数量级。高性能编程减少系统调用次数的常见手段：缓冲 IO 攒批（详见第 9 章）、writev 聚集写、io_uring 批量提交（详见《网络篇》第 28 章）。

用户态/内核态切换和进程上下文切换的区别

经常被混为一谈，必须分清：

  • 模式切换（用户态 ↔ 内核态）：同一个进程内的特权级变化，只需保存/恢复部分寄存器，开销小（百纳秒量级）。系统调用就是模式切换。
  • 进程上下文切换：CPU 从一个进程换到另一个进程，要切换地址空间（页表）、内核栈、全部寄存器，还会让 TLB 和 CPU 缓存大面积失效，开销大（微秒量级）。上下文切换必然伴随模式切换，反之不成立。

进程/线程/协程的切换成本对比详见《C++ 篇》第 27 章。

中断：硬中断与软中断

中断让 CPU 能够响应"随时可能发生"的事件，避免轮询浪费。

硬中断：由硬件设备通过中断控制器发给 CPU，异步、随时发生。例如网卡收到数据包、磁盘完成读写、时钟定时器到期。特点：

  • 打断当前任务立即处理，处理期间通常屏蔽同类中断。
  • 处理函数必须极快——中断处理期间当前 CPU 干不了别的，耗时长会丢事件。

软中断：由内核代码主动触发（raise_softirq），在合适的时机（硬中断返回前、或内核线程 ksoftirqd 中）执行，可被硬中断打断。承担"耗时但不紧急"的工作：网络协议栈处理、定时器回调、RCU 清理。

上半部 / 下半部（Linux 中断设计的核心思想）：

网卡收包的完整路径：
硬中断（上半部）：网卡触发 IRQ → 驱动只做最少的事：确认中断、把数据放进接收队列、
                  标记软中断待处理 → 立刻返回（微秒级）
软中断（下半部）：NET_RX 软中断被调度 → 协议栈逐层解析（IP → TCP）→
                  数据放入 socket 接收缓冲区 → 唤醒等待的进程

这样设计的原因：硬中断处理时间必须极短，把能拖的活全部拖到软中断里做，兼顾响应速度和吞吐。排障时 top 里的 hi/si 两列就是硬/软中断的 CPU 占比，网络流量大的机器 si 高是正常现象（详见第 11 章）。

常见面试追问

追问 1：为什么系统调用比函数调用慢？

函数调用只是一次跳转加栈帧操作。系统调用多了：特权级切换两次、用户态/内核态现场的保存与恢复、内核入口的安全校验（参数地址合法性检查），部分场景还有数据在用户缓冲区和内核缓冲区之间的拷贝。量级上函数调用是纳秒级，系统调用是百纳秒到微秒级。

追问 2：printf、malloc、read 哪些是系统调用？

都不是，三个都是 C 库函数。read 是对系统调用 sys_read 的薄封装，基本一对一；printf 内部有用户态缓冲，攒够了才调用一次 write；malloc 在用户态内存池里分配，池耗尽才通过 brk/mmap 找内核。库函数的价值之一就是用缓冲和池化减少昂贵的系统调用次数。

追问 3：中断处理函数里为什么不能睡眠？

睡眠意味着调度器要挂起"当前进程"换别人上 CPU，但中断处理运行在中断上下文，借用的是被打断进程的内核栈，它自己没有进程身份、没有可供调度器挂起的实体，睡了就再也没人能唤醒它，直接锁死 CPU。所以中断上下文只能用自旋锁、分配内存要用不睡眠的 GFP_ATOMIC 标志，可能阻塞的工作必须推给下半部或内核线程。

追问 4：软中断把 CPU 打满了怎么办？

典型场景是大流量下 ksoftirqd 占满单核——网卡中断默认只打到一个 CPU 上。手段：开启网卡多队列 + RSS 把流量按连接哈希分散到多个 CPU；irqbalance 或手动绑核分散中断亲和性；RPS/RFS 软件层面把包分给其他 CPU 处理。面试点到"中断集中在单核、想办法摊开"即可。

追问 5：一次 read 磁盘文件，发生了几次状态切换、几次拷贝？

传统缓冲 IO：read 陷入内核（切换 1）→ DMA 把磁盘数据搬进内核页缓存（不占 CPU）→ CPU 把页缓存拷贝到用户缓冲区 → 返回用户态（切换 2）。共 2 次模式切换、1 次 CPU 拷贝、1 次 DMA 拷贝。这是零拷贝优化的起点，完整推演详见第 9 章。

追问 6：vDSO 听说过吗？

内核把少数只读且高频的系统调用（如 gettimeofday、clock_gettime）的实现映射到用户空间，调用时根本不陷入内核，直接读共享页里的数据，把"系统调用"降级成普通函数调用。这是"系统调用开销大，能省则省"思想的极致案例，说出来是亮点。

易错点

  • 把"用户态/内核态切换"和"进程上下文切换"混为一谈，两者开销差一个量级以上。
  • 认为 malloc、printf 是系统调用。它们是库函数，内部按需发起系统调用。
  • 认为中断只有硬件才能触发，漏掉软中断和异常这两类入口。
  • 说不出上半部/下半部的设计动机（硬中断必须快，耗时活延后）。
  • 认为内核态代码"更快"。同样的指令在两种模式下速度一样，内核态的意义是权限，频繁切换反而更慢。
  • 中断处理里调用可能睡眠的函数（工程事故高发，面试也常反问）。

面试回答模板

如果面试官问"讲讲用户态内核态和系统调用"，可以这样回答：

CPU 用特权级把执行环境分成用户态和内核态：用户态跑应用，只能执行普通指令、访问本进程的用户空间；内核态跑操作系统，能执行改页表、操作设备这类特权指令。划分的目的是隔离和保护，应用崩溃被限制在自己进程里。从用户态进内核态有三个入口：主动的系统调用、外设的中断、执行出错的异常。系统调用的流程是：库函数把调用号和参数放进约定寄存器，执行 syscall 指令陷入内核，内核查系统调用表、校验参数、执行服务，再把结果放回寄存器返回用户态；它比函数调用贵一到两个数量级，所以有缓冲 IO、批量提交这些减少调用次数的优化，另外要注意 read 这类是系统调用的薄封装，而 printf、malloc 是带缓冲和内存池的库函数，池不够时才真正陷入内核。中断分硬中断和软中断：硬中断由设备异步触发、必须快进快出；Linux 把耗时的处理放到软中断做，也就是上半部快速响应、下半部延后处理，网卡收包就是典型——硬中断只把包挂进队列，协议栈解析全在 NET_RX 软中断里完成，top 里的 hi 和 si 两列对应它们的 CPU 占比。

2. 进程的状态与调度算法详解

题目

进程有哪些状态，状态之间怎么转换？PCB 是什么？常见的进程调度算法有哪些，各自的优缺点是什么？

这道题在考什么

有了第 1 章的"内核负责管理一切"，紧接着的问题就是：机器只有几个 CPU 核，却要同时跑成百上千个进程，内核靠什么变戏法？这道题考的就是这个戏法的两半——用"状态"描述每个进程此刻缺什么（缺 CPU 是就绪、缺事件是阻塞），用"调度算法"决定下一个把 CPU 给谁。面试官借它判断你是否理解"并发是调度出来的假象"，这也是后面聊多线程、上下文切换成本、CPU 飙高排查的共同前提。

思考时抓住一个问题："一个进程为什么会停下来？"要么时间片到了（回就绪队列排队），要么在等 IO/锁（进阻塞队列，给它 CPU 也没用）——五状态模型就是把这两种"停"和"跑"画成图。而调度算法没有标准答案，只有场景取舍：批处理要吞吐、交互式要响应，每个算法都是对某种场景的偏袒，答题时讲清"它偏袒谁、牺牲了谁"，比背优缺点清单高一个档次。

面试核心结论

进程的经典模型是五状态：新建、就绪、运行、阻塞、终止。核心三角是就绪/运行/阻塞——就绪缺的是 CPU，阻塞缺的是事件（IO 完成、锁释放），运行态时间片用完回就绪、等资源则入阻塞。内核用 PCB（Linux 里是 task_struct）记录进程的全部管理信息，上下文切换保存和恢复的就是它。调度算法按场景分：批处理看吞吐（FCFS 简单但短任务被拖死，SJF 平均等待最短但长任务饥饿）；交互式看响应（时间片轮转公平及时，优先级调度灵活但会饿死低优先级，多级反馈队列综合两者，兼顾响应和吞吐，接近实际系统）。Linux 的 CFS 用红黑树按虚拟运行时间挑"跑得最少"的进程，追求加权公平。

进程五状态模型

            创建完成             被调度（分到 CPU）
  新建 ────────────→ 就绪 ─────────────────→ 运行 ────→ 终止
                      ↑  ←───────────────────  │        （exit）
                      │      时间片用完/被抢占    │
                      │                        │ 等待事件（IO、锁、sleep）
                      │      事件完成           ↓
                      └─────────────────────  阻塞

三个核心状态的判据（面试官爱抠的点）：

  • 就绪（Ready）：万事俱备，只欠 CPU。放在就绪队列里等调度。
  • 运行（Running）：正在 CPU 上执行。单核任一时刻最多一个进程处于运行态。
  • 阻塞（Blocked/Waiting）：在等某个事件，给它 CPU 也没法跑。等的是 IO 完成、锁、信号量、sleep 到期。

两条容易考的转换规则：

  1. 阻塞态不能直接变运行态——事件完成后先回就绪队列，再等调度。
  2. 运行态到就绪态的路径有两条：时间片耗尽、被更高优先级进程抢占。

扩展状态（Linux 实际使用）：

  • 可中断睡眠（S）与不可中断睡眠（D）：D 状态连 kill -9 都无法打断，通常在等磁盘 IO，大量 D 状态进程是 IO 出问题的信号（排障详见第 11 章）。
  • 僵尸（Z）：进程已退出，PCB 还留着等父进程收尸（详见第 4 章）。
  • 停止（T）：被 SIGSTOP 暂停，如 Ctrl+Z。

PCB：进程的身份档案

PCB（进程控制块）是内核为每个进程维护的数据结构，Linux 中就是 task_struct，包含：

  • 标识信息：PID、PPID、用户 ID。
  • 状态信息：当前状态、优先级、调度参数、统计的 CPU 时间。
  • 现场信息：寄存器快照、程序计数器——上下文切换时保存/恢复的主体。
  • 资源信息：页表指针（内存）、打开文件表（fd，详见第 8 章）、信号处理表、工作目录。

上下文切换的本质就是：把当前进程的现场存进它的 PCB，从下一个进程的 PCB 里恢复现场（成本分析详见《C++ 篇》第 27 章）。

调度算法逐个讲

评价指标先立好：周转时间（提交到完成）、等待时间、响应时间（交互场景）、吞吐量、公平性。不同场景权重不同，没有全能算法。

1. 先来先服务 FCFS

按到达顺序排队执行，非抢占。

  • 优点：实现最简单、绝对公平、无饥饿。
  • 缺点：护航效应——一个长任务排在前面，后面一串短任务全部陪等，平均等待时间可以差到没法看。
  • 适合批处理，不适合任何交互场景。

2. 短作业优先 SJF

每次挑预计运行时间最短的执行。

  • 优点：可以证明平均等待时间最优。
  • 缺点一：运行时间靠预估，估不准全盘皆输。
  • 缺点二：长作业饥饿——短任务源源不断时，长任务永远排不上。
  • 抢占版叫最短剩余时间优先（SRTF）：新任务剩余时间比当前更短就抢占。

3. 时间片轮转 RR

就绪队列按 FIFO 排，每个进程最多跑一个时间片（几毫秒到几十毫秒），到点强制换下一个。

  • 优点：响应及时、公平，交互系统的基础。
  • 关键参数是时间片长度：太长退化成 FCFS，响应变差；太短则上下文切换占比过高，吞吐被切换开销吃掉。典型取 10ms~100ms 量级。

4. 优先级调度

按优先级挑进程，可抢占。优先级可静态指定，也可动态调整。

  • 优点：重要任务优先，实时系统必需。
  • 缺点：低优先级饥饿。解法是老化（aging）：等待越久优先级越涨，总有出头之日。
  • 经典事故案例：优先级反转——低优先级进程持有高优先级进程需要的锁，中优先级进程还在中间插队，火星探路者号真实翻过车；解法是优先级继承（持锁的低优先级进程临时提升到等锁者的优先级）。

5. 多级反馈队列 MLFQ（最接近实用的经典算法）

多个优先级队列，时间片逐级变长；新进程进最高级队列；用完整个时间片说明是 CPU 密集型，降一级；在时间片内主动让出（发起 IO）说明是交互型，留在高优先级。

Q0（优先级高，时间片 10ms）→ 用满降级
Q1（时间片 20ms）           → 用满降级
Q2（时间片 40ms，FCFS 兜底）
调度规则：永远先跑高级队列；低级队列只在高级队列空时才有机会
防饿：周期性把所有进程提回最高队列（boost）

精妙之处：不需要预知运行时间，用行为自动分类——交互型进程自然留在高优先级拿到快响应，CPU 密集型沉到底层批量跑，兼顾响应与吞吐。

6. Linux 实际用的：CFS 完全公平调度器（普通进程）

给每个进程记一个虚拟运行时间 vruntime（实际运行时间 ÷ 权重，nice 值决定权重），调度时永远挑 vruntime 最小的跑——"谁跑得最少让谁跑"。就绪进程按 vruntime 组织在红黑树里，取最左节点 O(log n)。没有固定时间片，按活跃进程数动态均分调度周期。实时进程另走 SCHED_FIFO/SCHED_RR 策略，优先级永远压过普通进程。

常见面试追问

追问 1：阻塞和就绪的本质区别是什么？

缺的东西不同。就绪缺 CPU，给它 CPU 立刻能跑；阻塞缺事件，给 CPU 也没用，必须先等 IO 完成、锁释放这类外部条件。所以唤醒（阻塞→就绪）和调度（就绪→运行）是两个独立动作。

追问 2：时间片设多长合适？

权衡响应和开销：设 T 为时间片、C 为一次上下文切换成本，切换开销占比约 C/(T+C)。T 太小（如 1ms 对 1μs 切换）开销尚可但缓存反复失效；太大则交互响应变差、退化向 FCFS。工程上取 10ms 量级，并像 CFS 一样根据负载动态调整。

追问 3：什么是优先级反转？怎么解决？

高优先级任务 H 等低优先级任务 L 持有的锁，而中优先级任务 M 抢占了 L 的 CPU——H 被 M 间接压制，优先级形同虚设。解法：优先级继承（L 临时升到 H 的优先级，尽快跑完释放锁）或优先级天花板（持锁即升到预定高优先级）。可举火星探路者号的真实案例加分。

追问 4：IO 密集型和 CPU 密集型进程，调度上应该偏向谁？

优先照顾 IO 密集型：它每次只用一小段 CPU 就发起 IO 进入阻塞，尽早调度它能让 IO 设备早点忙起来，CPU 和设备并行度最高；CPU 密集型给长时间片减少切换。多级反馈队列的"主动让出留在高优先级、用满时间片降级"正是这个思想的自动化。

追问 5：CFS 为什么用红黑树，vruntime 是什么？

CFS 需要频繁执行"取最小 vruntime 的进程"和"插入/删除就绪进程"，红黑树三种操作都是 O(log n)，且最左节点缓存后取最小是 O(1)（红黑树本身详见《C++ 篇》第 29 章）。vruntime 是按权重折算的运行时间：nice 值低（优先级高）的进程权重大，同样跑 10ms 记的 vruntime 更少，于是能分到更多实际 CPU——公平指"加权公平"。

追问 6：进程调度和线程调度是一回事吗？

Linux 内核只认调度实体：task_struct 既表示进程也表示线程（线程是共享地址空间的 task），内核调度的粒度就是 task，所以说"Linux 线程是轻量级进程"。用户态线程/协程的调度由运行时自己做，内核无感知（详见《C++ 篇》第 27 章）。

易错点

  • 画状态图时让阻塞直接转运行。必须先回就绪，经调度器挑选。
  • 认为单核机器上多个进程可以同时处于运行态。运行态最多一个，其余在就绪队列。
  • 把 D 状态（不可中断睡眠）当成普通阻塞，排障时对着 kill -9 无效一脸茫然。
  • 只背算法名字，说不出 FCFS 的护航效应、SJF 的饥饿、RR 时间片的两难——缺点比定义更常被追问。
  • 不知道老化和优先级继承这两个"饥饿/反转"的标准解法。
  • 把 CFS 说成时间片轮转。CFS 没有固定时间片，靠 vruntime 排序挑人。

面试回答模板

如果面试官问"进程状态和调度算法"，可以这样回答：

进程经典五状态：新建、就绪、运行、阻塞、终止。核心是中间三个：就绪只缺 CPU，运行正占着 CPU，阻塞在等 IO 或锁这类事件——时间片用完从运行回就绪，等事件从运行进阻塞，事件完成回就绪而非直接运行。内核用 PCB 也就是 task_struct 记录进程的标识、状态、寄存器现场和资源，上下文切换保存恢复的就是它。调度算法按场景讲：FCFS 最简单但有护航效应，长任务把短任务全拖住；SJF 平均等待时间最优，但要预估时长且长作业会饥饿；时间片轮转保证响应和公平，难点是时间片长度——太长退化成 FCFS、太短切换开销占比过高；优先级调度服务实时需求，代价是低优先级饥饿和优先级反转，分别用老化和优先级继承解决；多级反馈队列是集大成者，新任务进高优先级短时间片队列，用满降级、主动让出留级，自动把交互型留在上层、CPU 密集型沉到底层，响应吞吐兼顾。Linux 普通进程实际用 CFS：每个任务记按权重折算的虚拟运行时间，红黑树维护就绪队列，永远挑 vruntime 最小的跑，实现加权公平，实时任务另走 FIFO/RR 策略。

3. 进程间通信方式（IPC）详解

题目

进程间通信有哪些方式？各自的原理、优缺点和适用场景是什么？哪种方式最快？

这道题在考什么

这道题的前提藏在第 6 章：虚拟内存让每个进程活在自己的地址空间里，彼此完全看不见——隔离带来了安全，也带来了新麻烦：两个进程想传个数据怎么办？所有 IPC 方式本质上都是"在内核里开一条通道"的不同姿势。面试官问它，一是看你知不知道这层因果（先有隔离、才有 IPC），二是看你能不能按"数据量、速度、是否跨机器"给场景选型，而不是死背六种方式。

比较各种方式时抓一条主线：数据从 A 进程到 B 进程，拷贝了几次、陷入内核几次？管道和消息队列都要"用户 → 内核 → 用户"两次拷贝；共享内存把同一块物理内存映射给双方，零拷贝所以最快，但内核不再帮你排队，同步得自己用信号量管。想通"快慢的根源是拷贝次数"，"哪种最快、为什么"这类追问就是送分题。

面试核心结论

进程地址空间相互隔离（隔离本身详见第 6 章虚拟内存），交换数据必须借助内核提供的通道，主要有六种：管道（匿名管道限亲缘进程、半双工，命名管道无此限制）、消息队列（有格式的消息链表、可按类型取）、共享内存（同一块物理内存映射进多个进程，速度最快，需配合同步机制）、信号量（用于同步互斥的计数器，配合共享内存使用）、信号（异步事件通知，携带信息量最小）、socket（唯一能跨主机的方式，本机也常用 Unix 域套接字）。速度排序大致是：共享内存 > 管道/消息队列/Unix 域 socket > 网络 socket，核心差别在数据拷贝次数和是否陷入内核。

为什么进程通信需要内核帮忙

每个进程有独立的虚拟地址空间，A 进程里的地址 0x1000 和 B 进程里的 0x1000 映射到完全不同的物理页，直接传指针毫无意义。所以要么让内核当二传手（管道、消息队列：数据从 A 拷进内核，再从内核拷给 B），要么让内核把同一块物理内存同时映射给两个进程（共享内存：之后的读写不再经过内核）。理解这两条路线，六种方式的性能差异就全通了。

管道

匿名管道：pipe() 创建，内核里的一块环形缓冲区，返回读写两个 fd。

int fds[2];
pipe(fds);              // fds[0] 读端，fds[1] 写端
if (fork() == 0) {      // 子进程继承 fd，父子各关掉不用的一端
    close(fds[1]);
    read(fds[0], buf, sizeof(buf));
} else {
    close(fds[0]);
    write(fds[1], "hello", 5);
}
  • 特点：半双工（单向，双向要开两条）；只能用于有亲缘关系的进程（fd 靠 fork 继承传递，fork 详见第 4 章）；字节流无格式；缓冲区满则写阻塞、空则读阻塞。
  • shell 里的 ls | grep cpp 就是匿名管道：shell 先 pipe 再 fork 两个子进程，把 ls 的 stdout 和 grep 的 stdin 接到管道两端（详见第 10 章）。

命名管道（FIFO）：mkfifo 在文件系统里创建一个管道文件，任意进程凭路径打开即可通信，突破亲缘限制。其余特性与匿名管道一致。

消息队列

内核维护的消息链表，msgget/msgsnd/msgrcv 操作。

  • 相比管道的三个改进：有消息边界（按条收发，免拆包）；可按类型选择性接收（不必严格先进先出）；生命周期随内核——进程退出后消息还在，双方不必同时在线。
  • 短板：每条消息有大小上限、队列有总量上限；每次收发都是"用户态 → 内核 → 用户态"两次拷贝，大数据量吃亏。

共享内存

最快的 IPC：把同一块物理内存映射进多个进程的地址空间，之后读写就是普通内存访问，零内核介入、零数据拷贝。

// POSIX 风格
int fd = shm_open("/myshm", O_CREAT | O_RDWR, 0666);
ftruncate(fd, 4096);
void* p = mmap(nullptr, 4096, PROT_READ | PROT_WRITE, MAP_SHARED, fd, 0);
// 之后 p 上的读写另一进程立即可见
  • 快的代价是内核不再提供任何同步保证：两个进程同时读写就是数据竞争，必须自带同步——通常配信号量或放在共享内存里的进程间互斥锁（pthread mutex 设 PTHREAD_PROCESS_SHARED 属性）。
  • "共享内存 + 信号量"是经典组合拳，面试把这句说出来就到位了。
  • 典型应用：高吞吐的本机生产者消费者（日志采集 agent）、数据库共享缓冲池、多进程服务器的会话共享。

信号量

本质是内核维护的计数器，P 操作（减一，不够则阻塞）和 V 操作（加一，唤醒等待者），用于同步与互斥，携带的信息只有"计数"。

  • 二值信号量当互斥锁用，计数信号量控制并发数（如限制同时访问某资源的进程数为 N）。
  • 定位要说准：它管"协调时序"，数据传递交给共享内存等手段——两者是搭档关系。
  • 线程级的对应物（std::counting_semaphore、mutex 与条件变量）详见《C++ 篇》第 25 章。

信号

异步事件通知机制：内核或进程向目标进程发一个编号（如 SIGINT=2、SIGKILL=9、SIGSEGV=11），目标进程中断当前流程去执行信号处理函数。

  • 携带信息量最小（基本只有信号编号），定位是"事件通知"而非"数据传输"。
  • 进程的三种处置方式：执行默认动作（多数是终止）、忽略、注册自定义处理函数（signal/sigaction）。
  • SIGKILL(9) 和 SIGSTOP 不能被捕获、忽略或阻塞——内核保留的最终控制权，高频考点。
  • 常考信号：SIGSEGV（段错误）、SIGPIPE、SIGCHLD（子进程退出，收尸相关，详见第 4 章）、SIGTERM vs SIGKILL（前者可被捕获做清理，kill 默认发它；后者强制）。
  • 信号处理函数里只能调用异步信号安全函数（write 可以，printf/malloc 不行），因为它可能打断在任意执行点，重入非安全函数会死锁或损坏状态。

socket

唯一支持跨主机的 IPC；本机通信用 Unix 域套接字（address family 为 AF_UNIX）：走完整的 socket API，但数据在内核内直接转发，不经过网络协议栈，比 TCP 回环快，还能在进程间传递文件描述符（SCM_RIGHTS，这是其他 IPC 都做不到的独门绝技）。Docker 的 /var/run/docker.sock、MySQL 本机连接的 .sock 文件都是它。网络 socket 的完整体系详见《网络篇》。

常见面试追问

追问 1：为什么共享内存最快？

其他方式每次通信都要陷入内核并经历"发送方用户态 → 内核缓冲 → 接收方用户态"至少两次拷贝；共享内存只在建立映射时进一次内核，之后读写就是普通访存，零拷贝零系统调用。代价是同步责任转嫁给了使用者。

追问 2：管道的本质是什么？为什么匿名管道只能用于亲缘进程？

内核里的一块固定大小环形缓冲区，以一对 fd 的形式暴露。匿名管道没有名字，其他进程无从引用，fd 只能通过 fork 继承传播，所以限定亲缘进程；命名管道把入口挂到文件系统路径上，凭路径就能打开，突破了这个限制。

追问 3：kill -9 和 kill -15 有什么区别？为什么有的进程 kill -9 也杀不掉？

kill 默认发 SIGTERM(15)，进程可以捕获它做清理后优雅退出，也可以忽略；SIGKILL(9) 不可捕获不可忽略，内核直接终结进程。杀不掉的两种情况：进程处于不可中断睡眠 D 状态（通常卡在磁盘 IO，信号要等它回到可运行才处理，详见第 2、11 章）；僵尸进程（已经死了，杀无可杀，要处理的是它父进程，详见第 4 章）。

追问 4：信号处理函数里为什么不能随便调 printf/malloc？

信号可能在任意指令间打断主流程。如果主流程正在 malloc（持有堆锁），处理函数再进 malloc 就自死锁；printf 的缓冲区同理会被重入破坏。只能使用异步信号安全函数清单里的函数（write、_exit 等），工程惯例是处理函数里只设一个 volatile sig_atomic_t 标志，主循环里检查处理。

追问 5：两个进程要交换大量数据，你选哪种方案？怎么设计？

首选共享内存加同步原语：shm 开一块环形缓冲区，信号量（或进程间 mutex+条件变量）协调生产消费；数据量大时零拷贝优势碾压其他方案。若双方需要解耦、允许离线，退到消息队列；跨主机直接 socket。答题结构"选型 + 同步设计 + 理由"三句话即可。

追问 6：线程间通信和进程间通信有什么本质区别？

线程共享同一地址空间，天然共享全局变量和堆，通信是"直接读写 + 同步保护"的问题（mutex/条件变量/原子，详见《C++ 篇》第 25、26 章）；进程地址空间隔离，先要解决"数据怎么过去"，才轮到同步。所以线程通信谈的是同步原语，进程通信谈的是通道。

易错点

  • 背了六种方式，说不出"内核二传手 vs 共享映射"这条性能主线，被问"为什么共享内存快"就卡住。
  • 认为管道是全双工。半双工，双向通信要两条管道。
  • 说共享内存"自带同步"。它恰恰什么同步都不提供，必须配信号量或进程间锁。
  • 把信号当数据传输手段。它只递编号，定位是异步通知。
  • 不知道 SIGKILL/SIGSTOP 不可捕获，或答不出 kill -9 杀不掉 D 状态进程。
  • 忽略 Unix 域套接字，以为 socket 只用于网络——本机 RPC、传递 fd 都靠它。
  • 在信号处理函数里调用非异步信号安全函数。

面试回答模板

如果面试官问"进程间通信有哪些方式"，可以这样回答：

进程地址空间相互隔离，通信要靠内核，路线有两条：内核当二传手，或者把同一块物理内存映射给多个进程。具体六种：管道是内核里的环形缓冲区，半双工字节流，匿名管道靠 fork 继承 fd 所以限亲缘进程，shell 的竖线就是它，命名管道挂在文件系统路径上、任意进程可用；消息队列是内核里有边界的消息链表，能按类型取、双方不必同时在线，但单条消息有大小限制且每次两回拷贝；共享内存把同一块物理内存映射进多个进程，之后读写零拷贝零系统调用，是最快的方式，代价是内核不管同步，要配信号量或进程间锁，"共享内存加信号量"是经典组合；信号量本身是同步工具，P/V 操作的计数器；信号是异步事件通知，只带一个编号，SIGKILL 和 SIGSTOP 不可捕获不可忽略，处理函数里只能用异步信号安全函数；socket 是唯一跨主机的方式，本机则用 Unix 域套接字，不走协议栈还能传递文件描述符。选型逻辑：大数据量高频交换用共享内存，结构化低频消息用消息队列，异步通知用信号，跨主机或需要成熟生态用 socket。

4. fork、写时复制与僵尸/孤儿进程详解

题目

fork 的原理是什么，为什么说它"调用一次返回两次"？什么是写时复制？僵尸进程和孤儿进程是什么，僵尸进程怎么产生、怎么清理？

这道题在考什么

前三章讲的都是"进程已经在那儿了"，这道题回到起点：Linux 里进程是怎么生出来的？fork 是 Unix 最有个性的设计——不是"创建一个新程序"，而是"把自己复制一份"，很多人第一次见"调用一次返回两次"都会懵，面试官就爱用这个懵点检验你是否真理解了"fork 之后是两个各自独立执行的进程"。而写时复制和僵尸进程，则分别是这个设计在性能和资源回收上引出的两个必然话题。

理解顺序建议是：先想清楚 fork 语义（复制出的子进程从同一个返回点继续跑，靠返回值分辨父子）；然后自然会疑惑"复制整个地址空间不是巨慢？"——写时复制就是对这个疑问的回答（先共享、谁写谁复制）；最后想"进程死了尸体谁收？"——父进程要 wait，不 wait 就留下僵尸，父进程先死就托孤给 init。生、活、死一条线，三个子问题各占一段。

面试核心结论

fork 复制当前进程创建子进程：子进程获得父进程地址空间、文件描述符表、信号处理等的副本，两个进程从 fork 的返回点分别继续执行——父进程里返回子进程 PID，子进程里返回 0，靠返回值区分身份。现代实现靠写时复制（COW）避免真拷贝：fork 时只复制页表并把页都标成只读，谁写谁触发缺页异常，内核此刻才复制那一页——fork 因此几乎瞬间完成。子进程先于父进程退出且父进程没调用 wait 回收时，子进程的 PCB 残留成僵尸进程，占着 PID；父进程先退出则子进程成孤儿，由 init（或 subreaper）收养并负责后续收尸，孤儿无害、僵尸堆积有害。清理僵尸的根本办法是让父进程履行 wait 职责，或杀掉父进程让 init 接手。

fork 的行为

#include <unistd.h>

pid_t pid = fork();
if (pid < 0) {
    // 失败：进程数达上限或内存不足
} else if (pid == 0) {
    // 子进程：fork 返回 0
    // 想知道自己的 PID 用 getpid()，父进程 PID 用 getppid()
} else {
    // 父进程：fork 返回子进程的 PID
}

"调用一次，返回两次"的准确解释：fork 在内核里把父进程完整复制一份，两个进程的程序计数器都停在 fork 的返回点，各自被调度后都从这里往下跑，于是同一行代码在两个进程里各返回一次。父进程需要拿到孩子的 PID 来管理（wait、kill），子进程调 getpid 就能知道自己是谁，所以设计成"父得子 PID、子得 0"。

子进程复制到什么：地址空间（COW 方式）、文件描述符表（共享同一打开文件表项，文件偏移量是共享的，详见第 8 章）、信号处理设置、环境变量；不复制的：PID、父进程的锁状态、未决信号。

写时复制 COW

朴素 fork 要把父进程几个 GB 的内存全量拷贝，慢且多数拷贝是白费——子进程往往紧接着 exec 换新程序，拷来的内存全部作废。COW 的做法：

fork 时：
  只复制页表，父子的页表项指向同一批物理页
  把这些页全部标记为只读

之后任意一方写某页：
  触发缺页异常（写只读页）→ 内核发现是 COW 页
  → 复制该页，修改写方页表指向新页，恢复可写 → 重新执行写指令
  （另一方仍用旧页，从此各写各的）

效果：fork 的成本从"拷贝整个地址空间"降到"拷贝页表"，毫秒级变微秒级；物理拷贝推迟到真正写入的那一刻、且只拷被写的页。"fork + exec"这条最常见路径因此几乎零浪费。

COW 是"懒惰是美德"思想的代表，同类还有：std::string 曾经的 COW 实现、Redis RDB 的 bgsave 靠 fork+COW 拿到内存快照（父进程继续写、子进程看到的是 fork 瞬间的版本）。

配套细节：vfork 是历史产物，父子共享地址空间且父进程挂起等子进程 exec，COW 普及后没有存在必要；exec 家族用新程序镜像替换当前进程的地址空间，PID 不变——"fork 生孩子，exec 换脑子"，shell 执行命令就是 fork + exec + wait 三连（详见第 10 章）。

僵尸进程

定义：子进程已经退出，父进程还没有调用 wait/waitpid 回收它——退出状态、PID 等信息保存在残留的 PCB 里等父进程来取，这个"只剩 PCB 的尸体"就是僵尸进程（ps 里状态 Z，名字带 <defunct>）。

为什么要有这个设计：子进程的退出码总得有地方存着等父进程查询（父进程可能晚些才关心），PCB 就是这个信箱。所以每个子进程退出后都会短暂经历僵尸态，父进程及时 wait 就立即消失；一直不 wait 才会堆积成问题。

危害：僵尸不占内存不占 CPU（进程实体已释放），占的是 PID 和进程表项——PID 是有限资源，僵尸堆积多了系统再也 fork 不出新进程。

清理办法（按根治程度排序）：

  1. 父进程正确收尸：阻塞 wait()；或注册 SIGCHLD 处理函数，在其中循环 waitpid(-1, &st, WNOHANG) 收割所有已退出子进程（循环 + WNOHANG 是标准写法，一次信号可能对应多个退出）。
  2. 明确不关心退出状态：signal(SIGCHLD, SIG_IGN)，内核直接自动回收，不产生僵尸。
  3. 两次 fork 技巧：父 fork 出子，子再 fork 出孙后立即退出，孙变孤儿由 init 收养代管收尸——用于父进程无法改造的场景。
  4. 事后补救：僵尸本身杀不掉（它已经死了），kill 它的父进程，僵尸变孤儿被 init 收养，init 立即回收。

孤儿进程

定义：父进程先退出，子进程还在运行。内核把它过继给 1 号进程 init/systemd（或最近的 subreaper），养父会在它退出时负责 wait。

  • 孤儿进程无害：有人管、能被正常回收，机制本身就是兜底设计。
  • 应用：守护进程（daemon）的经典创建流程主动利用孤儿机制——fork 后父进程退出，子进程被 init 收养、脱离终端会话在后台长期运行。

僵尸 vs 孤儿对比

维度 僵尸进程 孤儿进程
谁先死 子先死，父不收尸 父先死，子还活着
状态 已终止，只剩 PCB 正常运行
归属 仍挂在原父进程名下 被 init/systemd 收养
危害 堆积耗尽 PID 无害
处理 父进程 wait / 杀父进程 无需处理

常见面试追问

追问 1：fork 之后父子进程谁先执行？

不确定，由调度器决定，程序不能依赖执行顺序（需要顺序就用管道、信号或 wait 显式同步）。Linux 曾倾向子进程先跑：子进程大概率马上 exec，先跑能减少 COW 复制。

追问 2：fork 后子进程会复制父进程的线程吗？

只复制调用 fork 的那个线程，其他线程在子进程里消失。风险随之而来：若其他线程持有锁（如 malloc 内部锁）时发生 fork，子进程里锁永远没人释放，一碰就死锁。所以多线程程序里 fork 后只应调用异步信号安全函数并尽快 exec，或用 pthread_atfork 做锁清理——多线程与 fork 的组合是工程雷区。

追问 3：printf 打印一半时 fork，缓冲区会怎样？

用户态缓冲区随地址空间被复制，父子各持一份未刷新的内容，之后各自刷新就会打印两遍。这也是"fork 前先 fflush"的原因，同时解释了重定向到文件（全缓冲）时输出重复而终端（行缓冲）不重复的经典现象。

追问 4：Redis 的 bgsave 为什么用 fork？内存会翻倍吗？

fork+COW 让子进程免费获得 fork 瞬间的内存快照：子进程慢慢把数据写盘，父进程继续服务，父进程每写一个页才复制那一页。内存增量等于快照期间被修改的页，写压力大时最坏趋近翻倍，所以要预留内存并避开写高峰。这一问把 COW 从概念落到名场面，容易拿分。

追问 5：怎么发现和定位系统里的僵尸进程？

ps aux | grep Z 或 ps -ef | grep defunct 找到僵尸及其 PPID；top 的任务行也直接显示 zombie 计数。定位到父进程后先查它为什么不 wait（常见于粗糙的 fork 后不管型代码），修代码或重启/杀掉父进程让 init 接管（排障套路详见第 11 章）。

追问 6：守护进程为什么要 fork 两次？

第一次 fork + 父退出：子被 init 收养、脱离原会话；setsid 后子进程成为新会话首进程，但会话首进程仍可能重新获得控制终端，于是第二次 fork 再退出一层，最终的孙进程不再是会话首进程，彻底与终端绝缘。两次 fork 分别解决"脱离父进程"和"永不沾终端"。

易错点

  • 说 fork "复制并立即拷贝全部内存"。现代实现是 COW，fork 本身只复制页表。
  • 认不清返回值方向：父进程拿到的才是子 PID，子进程拿到 0。
  • 认为僵尸进程占用大量内存 CPU。它只占 PID 和进程表项，但这足以拖垮系统。
  • 试图 kill -9 僵尸进程本身。对象错了，要处理的是它的父进程。
  • 把孤儿进程当问题处理。孤儿由 init 收养，机制健康。
  • 忽略"每个子进程都会短暂经历僵尸态"这一事实，把正常瞬态当异常。
  • SIGCHLD 处理函数里只 wait 一次。信号不排队，必须循环 waitpid + WNOHANG 收干净。
  • 多线程程序随意 fork 后继续执行复杂逻辑，踩中锁死陷阱。

面试回答模板

如果面试官问"讲讲 fork 和僵尸进程"，可以这样回答：

fork 复制当前进程产生子进程，两个进程都从 fork 返回点继续执行，父进程返回子进程 PID、子进程返回 0，这就是调用一次返回两次。子进程得到地址空间、fd 表、信号设置的副本，其中 fd 和父进程共享文件偏移。地址空间的复制靠写时复制：fork 只拷页表并把页标记只读，任何一方写入时触发缺页异常，内核才真正复制那一页，所以 fork 微秒级完成，fork 加 exec 的主流路径几乎零浪费；Redis bgsave 就靠 fork 加 COW 拿内存快照，内存增量取决于快照期间的写量。子进程退出后，退出状态要保存在 PCB 里等父进程 wait 领取，这个只剩 PCB 的阶段就是僵尸态——父进程及时 wait 它转瞬即逝，父进程不收尸才会堆积，僵尸不占内存但占 PID，堆多了系统 fork 不出新进程；清理办法是让父进程用 SIGCHLD 加循环 waitpid 收割，或者 SIG_IGN 让内核自动回收，实在不行杀掉父进程，僵尸变孤儿由 init 接管回收。孤儿是父进程先退出、子进程被 init 收养，无害，守护进程还主动利用它：两次 fork 加 setsid 脱离终端在后台长跑。

5. 死锁详解（四个必要条件与银行家算法）

题目

什么是死锁？产生死锁的四个必要条件是什么？处理死锁有哪些策略？银行家算法是怎么工作的？

这道题在考什么

死锁在 C++ 篇聊多线程加锁时已经露过面，这里从操作系统视角把它理论化。面试官问这道题通常有两层意图：浅层是背功——四个必要条件是教科书经典，答不出显得基础太虚；深层是工程感——线上真发生"两个事务/两个线程互相卡死"，你能不能从四个条件反推出"破坏其中之一"的解法。银行家算法则是"避免"策略的代表作，考的是你对"安全状态"这个概念的理解。

思考框架先定义再拆解：死锁 = 一圈进程互相等待、谁都动不了。四个必要条件就是把"这一圈是怎么形成的"拆成四个环节（资源独占、拿着不放、抢不走、等成一圈），缺一个环都成不了。处理策略按"介入时机"排：事前预防（设计上掐掉一个条件）→ 运行时避免（分配前算安全性）→ 事后检测解除 → 干脆不管（鸵鸟）。记住通用系统实际选鸵鸟、数据库选检测，这个反差是常见追问点。

面试核心结论

死锁指一组进程互相持有对方需要的资源并等待，谁都无法推进。四个必要条件缺一不可：互斥（资源同一时刻只能一个进程用）、持有并等待（拿着已有资源不放再去要新的）、不可剥夺（资源只能主动释放，抢不走）、循环等待（形成资源等待环）。处理策略四档：预防（设计上直接破坏某个必要条件，如按序申请资源破坏循环等待）、避免（运行时算安全性再分配，代表是银行家算法）、检测与解除（允许发生，用资源分配图定期查环，查到就杀进程或抢资源）、鸵鸟策略（成本考量下干脆不管，通用操作系统的实际选择）。银行家算法的核心：每次分配前假装分下去，检查系统是否仍存在一个能让所有进程依次跑完的安全序列，存在才真分配。

什么是死锁

经典场景两个线程两把锁：

线程 A：持有锁 1，申请锁 2
线程 B：持有锁 2，申请锁 1
→ A 等 B 放锁 2，B 等 A 放锁 1，永远等下去

工程代码示例与排查（gdb、固定加锁顺序、std::scoped_lock）在《C++ 篇》第 25 章已展开，本章补齐操作系统层的理论体系：条件、模型与算法。死锁的参与者可以是进程也可以是线程，资源可以是锁、也可以是打印机、内存、数据库行锁。

四个必要条件

面试必背，且要能一条条解释"为什么必要"：

  1. 互斥：资源排他使用，一次只能归一个进程。资源若可共享（如只读文件），根本无需等待。
  2. 持有并等待（请求与保持）：进程握着已到手的资源，同时申请新资源被阻塞。若申请前先放手，就不会出现"占着 A 等 B"。
  3. 不可剥夺：已分配的资源不能被强行夺走，只能等持有者用完主动释放。若可随时剥夺，等待链随时可被打断。
  4. 循环等待：存在进程等待环 P1→P2→…→Pn→P1，每个都在等下一个手里的资源。

四条同时成立死锁才可能发生；破坏任意一条，死锁必然无法形成——这就是"预防"策略的理论依据。注意方向：四条件是死锁的必要条件，同时满足只说明"可能死锁"，不代表一定发生。

处理策略一：死锁预防（设计期破坏必要条件）

逐条对应：

  • 破坏互斥：让资源可共享。适用面窄（多数资源天生排他），基本只在理论上成立。
  • 破坏持有并等待：一次性申请全部资源，拿不全就全不拿。缺点是资源利用率低（早申请晚使用）、可能饥饿。C++ 里 std::lock(m1, m2) / std::scoped_lock 同时锁多把锁就是这个思想的落地。
  • 破坏不可剥夺：申请新资源失败时，主动释放已持有资源稍后重试；或允许高优先级抢占。缺点是被剥夺方的工作可能作废、实现复杂。
  • 破坏循环等待：给所有资源全局编号，规定只能按编号递增顺序申请。环要求"有人先大后小"，按序申请让环无法闭合。这是工程中最实用的一条——"固定加锁顺序"防死锁的理论出处就在这里。

处理策略二：死锁避免（运行期动态判断）——银行家算法

思路：条件允许发生，但每次分配资源前先算一算"分出去之后系统还安不安全"，不安全就让申请者等。

安全状态的定义：存在一个执行序列 P1, P2, …, Pn，使得每个进程都能用"当前可用资源 + 前面进程释放的资源"满足其最大需求并顺利跑完。存在这样的安全序列即安全；不存在则不安全（注意：不安全state只是有死锁风险，未必已死锁）。

银行家算法（名字来自银行放贷：确保任何时刻都能让至少一个客户提完全款）：

数据结构（n 个进程、m 类资源）：

Available[m]      当前各类资源的可用数
Max[n][m]         每个进程对各类资源的最大需求（需事先声明）
Allocation[n][m]  已分配给每个进程的资源
Need[n][m]        还需要的资源 = Max - Allocation

进程 Pi 发来请求 Request 时：

① Request ≤ Need[i]   ？否则报错（要的比声明的还多）
② Request ≤ Available ？否则 Pi 等待（现货不够）
③ 试探性分配：Available -= Request; Allocation[i] += Request; Need[i] -= Request
④ 安全性检查：
     Work = Available; Finish[all] = false
     反复寻找一个 Finish 为 false 且 Need ≤ Work 的进程 Pk：
         找到 → 假设它跑完：Work += Allocation[k]; Finish[k] = true; 继续找
         找不到 → 停止
     所有 Finish 都为 true ⇒ 安全，真正执行分配
     否则 ⇒ 不安全，回滚第③步，让 Pi 等待

手算例题的套路（面试可能给表让你判断）：拿 Work 从小需求进程开始"滚雪球"，谁的 Need 装得下就让谁跑完回收资源，能滚完全部进程就安全，同时写出安全序列。

局限（为什么实际系统不用）：要求进程预先声明最大需求（现实做不到）、进程数和资源数固定、每次分配都要跑 O(m·n²) 检查——假设过强，教学价值大于工程价值。

处理策略三：死锁检测与解除

允许死锁发生，定期检测，发现后解除。

检测：资源分配图——进程指向所申请资源、资源指向持有它的进程。每类资源只有一个实例时，图中有环 ⟺ 死锁；多实例时有环只是必要条件，要用类似银行家安全检查的化简算法判定。

解除：

  • 杀进程：全部杀掉（代价大）或按代价逐个杀（优先杀优先级低、已运行时间短、持有资源多的），直到环打破。
  • 抢资源：强行剥夺某进程资源给别人，被抢者回滚到安全点（需要检查点支持，数据库领域常用）。

数据库是这套策略的忠实用户：InnoDB 用等待图检测死锁，检出后回滚代价最小的事务。

处理策略四：鸵鸟策略

假装死锁不存在。听起来敷衍，实际是通用操作系统（Linux/Windows）对进程级资源的现实选择：死锁概率低、预防和避免的常态开销高，权衡之下把问题留给应用层和运维（出事重启）。工程师因此更要在应用层自律——按序加锁、用 RAII 锁、限制锁粒度（详见《C++ 篇》第 25 章）。

四种策略对比

策略 时机 思路 代价 使用者
预防 设计期 破坏四条件之一 资源利用率下降 应用层编码规范（按序加锁）
避免 分配时 只进入安全状态 需先验信息 + 每次检查 教学（银行家算法）
检测与解除 事后 查环、杀进程/回滚 检测开销 + 回滚损失 数据库（InnoDB）
鸵鸟 从不 概率低就不管 出事人工处理 通用 OS

常见面试追问

追问 1：四个条件里工程上最常破坏哪一条？

循环等待，手段是全局固定加锁顺序（资源编号法）；其次是持有并等待，用一次性申请（std::scoped_lock 多锁版）。互斥基本没法破坏，不可剥夺实现代价高。答题时把条件和 C++ 实践对应起来是加分点。

追问 2：不安全状态等于死锁吗？

两码事。不安全状态只是找不到确保全员完成的安全序列，存在死锁的可能；实际是否死锁还取决于进程后续真实的申请行为（可能有进程根本用不满声明的最大值）。安全 ⇒ 必无死锁；不安全 ⇒ 可能死锁。银行家算法保守地拒绝进入一切不安全状态。

追问 3：资源分配图有环一定死锁吗？

每类资源只有单实例时，有环等价于死锁；资源有多个实例时，有环只是必要条件——环上的进程可能从环外实例获得资源而解套，需进一步用化简算法判定。

追问 4：银行家算法为什么不实用？

三个过强假设：进程要预先声明最大资源需求（一般声明不了）；进程和资源数量固定（系统动态变化）；每次分配都跑一遍 O(m·n²) 安全检查（高频分配扛不住）。它的价值在于给"避免"策略提供了精确的理论模型。

追问 5：活锁和死锁的区别？饥饿呢？

死锁是全员阻塞、状态完全不变；活锁是大家都在动作（不断重试、互相让路）却没有实质进展，像走廊两人反复同向避让；饥饿是个别进程长期得不到资源（如低优先级被无限延后），其他进程运转正常。解法各异：死锁靠破坏四条件，活锁引入随机退避打破对称，饥饿用老化机制（详见第 2 章）。

追问 6：怎么写代码从源头避免死锁？

规范清单：全局统一的加锁顺序；能用一把锁解决就用一把；多锁必须一起拿时用 std::scoped_lock；锁的持有时间最小化、持锁不调用外部未知代码；用 lock 层级检查工具（TSan、锁排序断言）兜底。这些正是"预防"理论在工程的投影（详见《C++ 篇》第 25 章）。

易错点

  • 四条件背成"充分条件"。它们是必要条件，同时满足才可能死锁。
  • 把"不安全状态"直接等同于"已死锁"。
  • 认为资源分配图有环必死锁，忽略多实例情形。
  • 银行家算法只会背名字，给张表算不出安全序列——要动手练一遍滚雪球流程。
  • 说不出四种策略的层次，或不知道通用 OS 实际采用鸵鸟策略、数据库采用检测回滚。
  • 把活锁、饥饿与死锁混为一谈。

面试回答模板

如果面试官问"讲讲死锁"，可以这样回答：

死锁是一组进程互相持有对方需要的资源且相互等待，全员无法推进。四个必要条件：互斥、持有并等待、不可剥夺、循环等待，缺一不可，因此处理思路的第一档就是预防——设计上破坏某个条件，工程里最常用的是给资源全局编号按序申请来破坏循环等待，也就是固定加锁顺序，其次是用 scoped_lock 一次性申请全部锁来破坏持有并等待。第二档是避免，运行时只允许进入安全状态，代表是银行家算法：维护 Available、Max、Allocation、Need 四张表，收到请求先试探性分配，再做安全性检查——看能否找到一个安全序列让所有进程依次满足最大需求并跑完，找得到才真分配，找不到就回滚等待；它要求预知最大需求、每次分配都要检查，所以是教学模型。第三档是检测与解除：允许死锁发生，用资源分配图查环——单实例资源有环即死锁，检出后杀代价最小的进程或回滚，InnoDB 对事务死锁就是这么干的。第四档鸵鸟策略，通用操作系统因为死锁概率低、预防代价高，干脆不处理，把责任留给应用层，所以写代码时按序加锁、RAII 管锁这些纪律才格外重要。另外要分清概念：不安全状态只是可能死锁，活锁是动而无进展，饥饿是个别进程长期拿不到资源。

6. 虚拟内存、分页与分段详解

题目

为什么需要虚拟内存？虚拟地址到物理地址是怎么翻译的？多级页表解决什么问题？TLB 是什么？分页和分段有什么区别？缺页中断的完整流程是怎样的？

这道题在考什么

这是操作系统面试的核心中的核心，因为它同时回答了三个日常疑问：为什么 8G 内存能"同时运行"占用远超 8G 的程序？为什么野指针只崩自己的进程不崩系统？为什么两个进程打印同一个地址值却互不干扰？面试官用这道题区分"背过八股"和"真懂内存"——后者能把地址翻译、多级页表、TLB、缺页中断串成一个连贯的故事，而不是四个孤立名词。

串故事的方法是沿着"一次内存访问"走一遍：CPU 拿到的是虚拟地址 → 要查页表翻译成物理地址 → 页表本身太大怎么办（多级页表，按需建目录）→ 每次访存都多查几次内存太慢怎么办（TLB 缓存翻译结果）→ 查到的页不在物理内存怎么办（缺页中断，从磁盘调入）。每个机制都是为了解上一个机制引出的新问题，这条"问题链"就是最自然的答题顺序。分页 vs 分段则是历史对比题，记住现实是"分页为主、分段退化"即可。

面试核心结论

虚拟内存给每个进程一个独立、连续、完整的地址空间假象，操作系统加硬件（MMU）负责把虚拟地址翻译到物理地址。三大价值：进程隔离（谁也碰不到谁的物理页）、内存超卖（物理内存 + 交换区，程序可用空间超过物理内存）、地址独立（程序按固定地址编写，加载哪里都能跑）。翻译以页（通常 4KB）为单位查页表；单级页表本身太占内存，多级页表按需分配目录层级省空间；每次访存都查页表要多次内存访问，TLB 缓存最近的翻译结果把常见情况压回一次访存。访问的页无有效映射时触发缺页中断，内核按需从磁盘调入、必要时先用置换算法腾位置（详见第 7 章）。分段按逻辑模块（代码/数据/栈）划分、长度可变、有外部碎片；分页固定大小、消除外部碎片只剩内部碎片；x86 的现实是分段基本退化，分页为主。

为什么需要虚拟内存

倒推法回答，假设进程直接用物理地址：

  1. 无隔离：任何进程算出一个地址就能读写任意物理内存，改掉别的进程甚至内核的数据（安全边界的另一半在第 1 章的特权级）。
  2. 无法搬移与共享：程序编译时写死物理地址，两个程序用了同一地址就无法同时运行；物理内存也没法灵活腾挪。
  3. 大小受限：程序大小超过物理内存就跑不起来，多个大程序更无从谈起。

虚拟内存一次解决三个问题：

  • 每个进程独享一套虚拟地址空间（32 位 4GB、64 位实际用 48 位共 256TB），页表把它映射到分散的物理页，进程之间物理页天然隔离。
  • 程序面对的地址固定且连续，物理内存可以任意搬移、换出到磁盘，甚至多个进程把同一物理页映射进各自空间实现共享（共享库、共享内存 IPC 详见第 3 章、fork 的 COW 详见第 4 章——这两个机制都寄生在页表之上）。
  • 物理内存 + swap 构成"看起来更大的内存"，配合按需调页，程序只把正在用的部分留在物理内存。

地址翻译：页表怎么工作

内存按固定大小切页：虚拟空间切成页（page，典型 4KB），物理内存切成同样大小的页框（page frame）。虚拟地址拆成两段：

32 位地址、4KB 页：
┌──────── 高 20 位 ────────┬─── 低 12 位 ───┐
│        虚拟页号 VPN       │    页内偏移     │
└──────────────────────────┴────────────────┘
翻译：物理地址 = 页表[VPN].物理页框号 × 4KB + 页内偏移

页表项除了物理页框号还带控制位：有效位（在不在物理内存）、读/写/执行权限位、脏位（被写过，换出时才需写回磁盘）、访问位（置换算法用，详见第 7 章）。MMU 硬件负责查表翻译，权限不符直接触发异常——段错误的硬件来源就在这里。

多级页表：解决页表自身太大

单级页表的账：32 位空间 ÷ 4KB 页 = 2^20 项，每项 4 字节，每个进程 4MB 页表；64 位空间更是天文数字。但进程实际只用了地址空间的一小部分，绝大多数表项是空的。

多级页表按"目录树"组织：

32 位二级页表：
虚拟地址 = [10 位 页目录索引 | 10 位 页表索引 | 12 位 偏移]
页目录（1K 项）→ 指向二级页表（每个 1K 项）→ 指向物理页

省内存的关键：没用到的地址区间，页目录项置空，对应的二级页表根本不分配
64 位用四级（PGD→PUD→PMD→PTE），思路相同

代价：一次翻译要逐级查表——二级查 2 次内存、四级查 4 次，访存开销放大数倍。这个代价由 TLB 来消化。

TLB：翻译的缓存

TLB（Translation Lookaside Buffer）是 MMU 里的一小块高速缓存，存最近用过的"虚拟页号 → 物理页框号"映射：

  • 命中（程序局部性保证了绝大多数命中）：一步拿到物理页框，翻译几乎免费。
  • 未命中：走多级页表慢速路径，结果回填 TLB。

两个工程关联：

  • 进程上下文切换会刷新 TLB（不同进程页表不同），这是切换昂贵的重要原因之一（详见《C++ 篇》第 27 章）；ASID/PCID 技术给 TLB 条目打进程标签来缓解。
  • 大页（HugePage，2MB/1GB）：一条 TLB 条目覆盖更大范围，减少未命中，数据库和高性能场景常用；代价是内部碎片变大、内存管理变粗。

缺页中断的完整流程

访问的虚拟页在页表中无有效映射（有效位为 0）时，MMU 触发缺页异常，内核接管：

① 检查地址合法性：不在进程任何 VMA 区域内 → 段错误 SIGSEGV，进程被杀
② 合法但页不在内存：
   - 首次访问的匿名页（如新分配的堆）→ 分配物理页清零映射（按需分配）
   - 文件映射页（代码、mmap 文件）→ 从磁盘文件读入
   - 被换出到 swap 的页 → 从交换区读回
   - COW 页的写访问 → 复制页、改写映射（详见第 4 章）
③ 物理内存不足 → 先执行页面置换算法挑牺牲页（详见第 7 章），
   脏页写回磁盘后腾出页框
④ 更新页表项、置有效位 → 返回用户态重新执行触发缺页的那条指令

细分两类（性能分析常用，详见第 11 章 排障）：

  • 软缺页（minor fault）：页其实在物理内存（页缓存里、或只需建立映射/COW），不用碰磁盘，微秒级。
  • 硬缺页（major fault）：必须从磁盘读，毫秒级，大量硬缺页说明内存不足开始抖动。

分段与分页

分段按程序逻辑结构划分：代码段、数据段、栈段各是一段，长度不一。段表记录每段的基址和界限，翻译 = 段基址 + 段内偏移，越界检查用界限。

维度 分段 分页
划分依据 逻辑模块，对程序员可见 固定大小，纯物理管理，程序员无感
大小 可变 固定（4KB 等）
碎片 外部碎片（段间空隙难以利用），需内存紧凑 无外部碎片，只有内部碎片（最后一页用不满，平均浪费半页）
共享/保护粒度 按逻辑段，天然合理 按页，粒度机械
  • 段页式：先分段、段内再分页，兼顾逻辑清晰与碎片控制，代价是翻译更多一级。
  • 现实答案：x86-64 的分段已经退化（基址全 0，只留权限位的少量用途），主流系统以分页为核心；平时说的"代码段、数据段"是 ELF/进程布局的逻辑概念（详见《C++ 篇》第 5 章内存分区），底层由分页实现。

常见面试追问

追问 1：虚拟内存和物理内存的大小有什么关系？

没有绑定关系。32 位进程虚拟空间固定 4GB，与机器插多少内存无关；虚拟空间可以远大于物理内存（按需调页 + swap 支撑），多个进程的虚拟空间总和更是远超物理内存——虚拟内存本质是"地址的账本"，物理内存是"真实的库存"。

追问 2：一次内存访问在最坏情况下要访问几次内存？

四级页表且 TLB 全未命中：4 次页表访问 + 1 次数据访问 = 5 次。TLB 命中则 1 次数据访问搞定。这道算术题考的是"多级页表省空间、TLB 救时间"的配对关系。

追问 3：为什么页大小通常是 4KB？大页什么时候用？

权衡：页越小内部碎片越少但页表项越多、TLB 覆盖范围越小；页越大反之。4KB 是历史沉淀的平衡点。TLB 未命中成为瓶颈的大内存应用（数据库缓冲池、DPDK、JVM 大堆）用 2MB/1GB 大页扩大 TLB 覆盖，代价是分配粒度粗、可能浪费内存。

追问 4：段错误（SIGSEGV）在硬件层面是怎么发生的？

访问的虚拟地址要么不在任何有效映射区域（缺页处理中发现地址非法），要么权限不符（写只读页、用户态碰内核地址、执行不可执行页）——MMU 按页表项的有效位和权限位裁决，触发异常后内核向进程发 SIGSEGV。所以野指针的惩罚由硬件页表机制执行（指针安全详见《C++ 篇》第 3 章）。

追问 5：swap 是什么？swap 使用率高说明什么？

磁盘上划出的"内存溢出区"：物理内存吃紧时，把不活跃的匿名页换出到 swap 腾地方。swap 被持续大量使用，说明物理内存不足、系统开始用磁盘速度顶替内存速度，伴随大量硬缺页，性能断崖下跌（抖动，详见第 7 章）；排障时 free/vmstat 看 swap in/out 是标准动作（详见第 11 章）。

追问 6：mmap 和虚拟内存是什么关系？

mmap 直接操作虚拟内存机制：在进程地址空间登记一段 VMA 映射到文件或匿名内存，登记时不分配物理页，首次访问靠缺页中断按需加载。文件映射省掉 read 的一次拷贝（零拷贝的一种，详见第 9 章）；malloc 的大块分配底层也走匿名 mmap（详见《C++ 篇》第 6 章）。

易错点

  • 把虚拟内存说成"就是 swap 交换区"。swap 只是虚拟内存体系中"超卖"的一个组件，隔离与地址独立同样是核心价值。
  • 认为页表翻译是软件做的。查表翻译由 MMU 硬件完成，内核负责维护页表和处理缺页。
  • 讲不清多级页表为什么省内存（空洞区域不分配下级表），只会背"分级"。
  • 忽略 TLB，答不出"多级页表变慢靠什么补救"。
  • 分段分页的碎片类型说反：分段外部碎片、分页内部碎片。
  • 缺页流程漏掉"返回后重新执行触发缺页的指令"这一步。
  • 不区分软缺页和硬缺页，性能分析时抓不住重点。

面试回答模板

如果面试官问"讲讲虚拟内存和分页机制"，可以这样回答：

虚拟内存给每个进程独立、连续的地址空间假象，价值有三：进程间物理页天然隔离；程序地址与物理位置解耦，还能通过共享映射实现共享库和 COW；配合按需调页和 swap，可用空间超过物理内存。翻译以页为单位，典型 4KB：虚拟地址拆成页号加页内偏移，MMU 查页表把页号换成物理页框号，页表项还带有效位、读写执行权限位、脏位和访问位，权限不符就是段错误的硬件来源。单级页表每进程要 4MB 且大部分为空，所以用多级页表：按页目录树组织，没用到的区间不分配下级表，64 位是四级；代价是一次翻译要查多次内存，靠 TLB 缓存最近的页号映射来补救，命中时翻译几乎免费，这也解释了上下文切换贵——要刷 TLB，以及大页优化——一条 TLB 条目覆盖 2MB。访问无效页触发缺页中断：地址非法直接 SIGSEGV；合法则按需分配、从文件或 swap 读入、COW 复制，内存不足先跑置换算法腾页，最后重执行那条指令；缺页分软硬，硬缺页要碰磁盘，大量出现就是内存不足的信号。分段按逻辑模块划分、长度可变、有外部碎片；分页固定大小、只剩内部碎片；现代 x86 分段已退化，分页为主，平时说的代码段数据段是进程布局的逻辑概念。

7. 页面置换算法详解（含手写 LRU）

题目

常见的页面置换算法有哪些？各自的原理和优缺点是什么？什么是 Belady 异常和内存抖动？手写一个 O(1) 的 LRU 缓存。

这道题在考什么

这道题是第 6 章缺页中断的直接续集：物理内存满了，新页要进来，谁出去？置换算法就是"挑牺牲页"的规则。面试官喜欢它有两个原因：一是它是"用过去预测未来"这类启发式思想的经典标本，OPT → FIFO → LRU → Clock 的演进线索清晰，最能看出你是理解还是硬背；二是它自带一道手写题——O(1) LRU 是大厂出场率极高的代码题，从理论直接落到编码。

比较算法时盯住一个标尺：离理论最优（OPT，换将来最久不用的页）有多远、实现代价多大。FIFO 只看"来得早晚"完全无视访问规律，所以有 Belady 异常这种反直觉现象；LRU 用"最近没用过 ≈ 将来也不用"逼近 OPT，但精确实现要哈希表 + 双向链表；Clock 用一个访问位近似 LRU，便宜到硬件愿意配合——工程永远在"效果"和"代价"之间找平衡点，这条线讲清楚，三个算法的优缺点不用背。

面试核心结论

物理内存装不下所有页时，缺页调入新页前要挑一个牺牲页换出，挑选规则就是页面置换算法。OPT 换"将来最久不会用到"的页，缺页率理论最低但要预知未来，只作评测基准；FIFO 换最早进来的，实现最简单，但会踢掉常驻热页，还有 Belady 异常（内存变大缺页反而变多）；LRU 换最久没被访问的，用"过去预测未来"，效果接近 OPT，精确实现要哈希表加双向链表；Clock（二次机会）用环形队列加访问位近似 LRU，硬件代价小，操作系统实际采用的是它的变种。置换算法失效、进程频繁换页导致 CPU 全花在磁盘 IO 上的现象叫抖动。手写 LRU 是本主题的落地题：哈希表定位 + 双向链表维护访问顺序，get/put 都是 O(1)。

问题背景

按需调页体系下（详见第 6 章），物理页框是稀缺资源。缺页中断需要调入新页而没有空闲页框时，必须选一个已在内存的页换出（干净页直接丢，脏页先写回磁盘）。选得好，被换出的页很久用不到；选得差，刚换出又要换回，一来一回都是毫秒级磁盘 IO。评价指标就一个：缺页率。

OPT 最佳置换（理论基准）

规则：淘汰"未来最长时间内不再被访问"的页。

  • 可以证明缺页率最低，但要求预知完整的未来访问序列，无法实现。
  • 用途：离线评测其他算法的天花板——"LRU 效果接近 OPT"这句话的参照物就是它。

FIFO 先进先出

规则：淘汰最早调入内存的页，一个队列即可实现。

  • 优点：实现成本最低。
  • 缺点一：进入时间和使用频率无关——最早进来的很可能是一直在用的热页（比如全局配置页），照踢不误。
  • 缺点二：Belady 异常——给它更多页框，缺页率反而可能上升。经典反例是访问串 1 2 3 4 1 2 5 1 2 3 4 5：3 个页框缺页 9 次，4 个页框缺页 10 次。原因是 FIFO 的淘汰顺序与访问局部性无关，不满足栈算法性质；LRU/OPT 满足栈性质（大内存的驻留集包含小内存的驻留集），不会出现该异常。

LRU 最近最久未使用

规则：淘汰"最长时间没有被访问"的页。依据是时间局部性：最近用过的，接下来大概率还会用——拿过去近似 OPT 的未来。

  • 效果：常规负载下缺页率接近 OPT，是通用性最好的策略。
  • 反例也要会说：顺序扫描一个大于内存的大文件，每页只碰一次，LRU 把热数据全挤出去换进一堆只用一次的页（缓存污染）。数据库和内核对此都有改良：LRU-K、分代 LRU。
  • 实现代价是它的短板：精确 LRU 每次访存都要更新顺序结构。放在 CPU/MMU 层面做不起，所以操作系统用 Clock 近似；放在软件缓存层（Redis、业务缓存）就是经典的哈希 + 双向链表（见下文手写）。

Clock 时钟算法（二次机会）

用最小硬件支持（页表项一个访问位 R，MMU 访问该页时自动置 1）近似 LRU：

所有页框排成环，指针像钟表一样扫描：
  指到某页：R == 1 → 清零，给第二次机会，指针前移
            R == 0 → 淘汰它（自上次扫描以来没人用过）
  • 开销极小，效果与 LRU 接近，操作系统实际采用（Linux 的页回收是基于访问位的双链表分代变种：active/inactive list）。
  • 改进版考虑脏位 D：优先淘汰 (R=0, D=0) 的页——既冷又干净，换出连磁盘写回都省了。

其他两个一句话算法

  • LFU 最不经常使用：按访问次数淘汰最少的。缺点是老热页积累的高计数迟迟不退场（缓存了历史，响应不了变化），需配合计数老化；Redis 的 LFU 就带衰减因子。
  • NRU/随机：嵌入式或简化场景使用，知道名字即可。

内存抖动与工作集

抖动（颠簸，thrashing）：多道程序度过高、每个进程分到的页框太少，谁跑都缺页，刚换出的页马上又被换回，CPU 利用率骤降——全系统都在等磁盘。特征曲线：并发度升高，CPU 利用率先升后断崖下跌。

工作集理论给出解释与对策：进程在一个时间窗口内实际访问的页集合叫工作集；分到的页框覆盖不了工作集就必然频繁缺页。对策：按工作集分配页框、装不下就挂起部分进程（降低多道程序度）、加内存。排障视角：vmstat 看 si/so 持续不为零、sar -B 看 majflt 飙升，就是抖动信号（详见第 11 章）。

手写 O(1) LRU 缓存

面试落地题（LeetCode 146 原题）：get 和 put 都要 O(1)。

结构选型的推导：O(1) 查找 → 哈希表；O(1) 维护访问顺序（任意位置摘除 + 头部插入 + 尾部淘汰）→ 双向链表；两者组合，哈希表的 value 指向链表节点。

class LRUCache {
    struct Node {
        int key, value;
        Node *prev = nullptr, *next = nullptr;
        Node(int k, int v) : key(k), value(v) {}
    };

    int cap_;
    std::unordered_map<int, Node*> map_;   // key -> 链表节点
    Node* head_;                            // 哨兵：head_ 后面是最新
    Node* tail_;                            // 哨兵：tail_ 前面是最旧

    void remove(Node* n) {                  // 从链表摘下
        n->prev->next = n->next;
        n->next->prev = n->prev;
    }
    void pushFront(Node* n) {               // 插到头部（最新位置）
        n->next = head_->next;
        n->prev = head_;
        head_->next->prev = n;
        head_->next = n;
    }

public:
    explicit LRUCache(int capacity) : cap_(capacity) {
        head_ = new Node(0, 0);
        tail_ = new Node(0, 0);
        head_->next = tail_;
        tail_->prev = head_;
    }

    int get(int key) {
        auto it = map_.find(key);
        if (it == map_.end()) return -1;
        Node* n = it->second;
        remove(n);                          // 访问即刷新：摘下重插头部
        pushFront(n);
        return n->value;
    }

    void put(int key, int value) {
        auto it = map_.find(key);
        if (it != map_.end()) {             // 已存在：更新值 + 刷新位置
            it->second->value = value;
            remove(it->second);
            pushFront(it->second);
            return;
        }
        if ((int)map_.size() == cap_) {     // 满了：淘汰尾部最旧节点
            Node* old = tail_->prev;
            remove(old);
            map_.erase(old->key);           // 节点里存 key 就是为这一步
            delete old;
        }
        Node* n = new Node(key, value);
        map_[key] = n;
        pushFront(n);
    }
};

必须能说出的四个设计点：

  1. 双向链表：摘除任意节点需要前驱，单链表给不了 O(1)。
  2. 头尾哨兵：省去所有对空链表、首尾节点的特判。
  3. 节点里冗余存 key：淘汰尾节点时要反查哈希表删除对应项。
  4. get 也要移动节点：读也算"使用"，这是 LRU 语义的一部分。

延伸一句：工程版还要考虑线程安全（整体一把锁，或分片锁降低竞争）和过期时间；Redis 用的是近似 LRU 采样淘汰，省掉全局链表的维护。

常见面试追问

追问 1：为什么操作系统用 Clock 這类近似算法，软件缓存却能用精确 LRU？

频率差几个数量级。内存访问每秒数十亿次，精确 LRU 要求每次访存都更新链表，硬件做不起，只能用 MMU 自动置访问位这种零成本信息做近似；软件缓存（Redis、业务 LRU）的 get/put 每秒最多百万级，链表维护开销可以接受。

追问 2：Belady 异常是什么？为什么 LRU 没有？

FIFO 下增加页框数缺页率反而上升的现象。LRU 和 OPT 属于栈算法：k 个页框时的驻留集恒为 k+1 个页框时驻留集的子集，页框越多驻留内容只增不减，缺页率单调不升，所以无此异常。FIFO 的驻留集不满足包含关系。

追问 3：LRU 在什么访问模式下表现很差？怎么改良？

一次性顺序扫描：大量只访问一次的冷页把热页全部挤出（缓存污染）。改良思路是"进门先考察"：LRU-K 要求命中 K 次才算热；MySQL 缓冲池把链表分 young/old 两段，新页先进 old 区、停留超过阈值再晋升 young；Linux 用 active/inactive 双链表同理。

追问 4：手写 LRU 为什么要在链表节点里存 key？

淘汰发生在链表尾部：拿到的是节点指针，但删除哈希表项需要 key。节点不存 key 就得反向遍历哈希表找值等于该指针的项，O(1) 直接破功。这是实现里最容易漏的点。

追问 5：缺页率和置换算法、页框数是什么关系？

三者共同决定性能：同样的访问串，页框越多缺页率越低（栈算法保证单调），算法越接近 OPT 越低。页框少到覆盖不了工作集时，再好的算法也救不了——先加内存或降并发，再谈算法。

追问 6：脏位在置换中起什么作用？

区分换出成本：干净页（与磁盘副本一致）直接丢弃，零 IO；脏页必须先写回，多一次磁盘写。改进 Clock 优先挑"冷且干净"的页，就是为了少写盘。内核还会用后台线程提前把脏页刷盘（回写机制），让置换时刻尽量都是干净页。

易错点

  • OPT 当成可实现算法来答；它是基准线。
  • 说不出 FIFO 的两宗罪：踢热页 + Belady 异常，或举不出 Belady 的存在性。
  • 认为操作系统内核用的是精确 LRU。内核用访问位近似（Clock/分代链表），精确 LRU 在这个频率下不可行。
  • 手写 LRU 用单链表（摘除拿不到前驱）、忘了哨兵（边界特判出错）、节点不存 key（淘汰时删不掉哈希项）、get 不移动节点（违背语义）。
  • put 已存在的 key 时只更新值、忘了刷新位置。
  • 抖动只会背定义，说不出"工作集覆盖不了"的原因和"降并发/加内存"的对策。

面试回答模板

如果面试官问"页面置换算法"，可以这样回答：

物理内存满了要调入新页时，得挑一个牺牲页换出，目标是最小化缺页率。OPT 淘汰未来最久不用的页，缺页率理论最低，但要预知未来，只能当评测基准。FIFO 淘汰最早进来的页，实现最简单，问题是进入早晚和是否常用无关，会把热页踢掉，还有 Belady 异常——页框增多缺页率反而可能上升，根源是它不满足栈算法性质，而 LRU 和 OPT 满足所以没有这个问题。LRU 淘汰最久未访问的页，用时间局部性拿过去预测未来，效果接近 OPT，短板一是顺序扫描会造成缓存污染，改良有 LRU-K 和 MySQL 缓冲池的 young/old 分区，二是精确实现每次访问都要维护结构，内存访问频率下硬件做不起，所以操作系统实际用 Clock：靠页表访问位，环形指针扫描，R 为 1 清零给第二次机会、为 0 淘汰，改进版再看脏位优先淘汰又冷又干净的页。置换救不了的情况叫抖动：页框覆盖不了进程工作集，全系统忙着换页等磁盘，CPU 利用率断崖下跌，对策是降低并发度或加内存。落地题是 O(1) LRU 缓存：哈希表做查找、双向链表维护访问顺序，头尾哨兵省特判，节点里要冗余存 key 供淘汰时删哈希项，get 命中也要把节点摘下重插头部。

8. Linux 文件系统详解（inode、软硬链接与文件描述符）

题目

inode 是什么，里面存了什么？软链接和硬链接有什么区别？文件描述符、打开文件表和 inode 三者是什么关系？

这道题在考什么

视角从内存转到磁盘：文件在 Linux 里到底是怎么组织的？这道题最大的"不明所以"点在于 inode 这个设计——文件名居然不属于文件本身，而是目录里的一条映射记录。面试官问它，就是想看你有没有建立"文件 = inode + 数据块，文件名只是指向 inode 的名字"这个模型，因为软硬链接的区别、"删了文件磁盘没释放"这类线上怪象，全都是这个模型的推论。

建议的思考顺序：先立住"名字与实体分离"的模型 → 硬链接立刻好懂（同一 inode 的第二个名字，两个名字完全平等）→ 软链接对照着看（独立的小文件，内容是一条路径，所以能跨文件系统、也会悬空）→ 最后把视角切到进程侧：fd → 打开文件表 → inode 三层结构，重点想通"为什么中间要垫一层打开文件表"（偏移量等'打开状态'既不属于进程也不属于文件本身）。第 9 章的零拷贝、《网络篇》的 socket fd 都建在这层理解上。

面试核心结论

Linux 文件系统把一个文件拆成两部分存储：inode 存元数据（权限、大小、时间戳、数据块位置——唯独不含文件名），数据块存内容；文件名保存在目录里，目录本质是"文件名 → inode 号"的映射表。硬链接是同一 inode 的又一个名字，两个名字完全平等，inode 里的链接计数减到 0 且无进程打开时数据才真正释放；软链接是独立的小文件，内容是目标路径，可跨文件系统、可指向目录，目标删除后变成悬空链接。进程访问文件经过三层：进程私有的文件描述符表 → 系统级打开文件表（记录偏移量和打开模式）→ inode 表；fork 后父子共享同一个打开文件表项所以共享偏移，两次独立 open 则各有偏移。

文件在磁盘上的存储模型

文件系统把磁盘分成几个区域，核心两类：

┌──────────┬─────────────────┬──────────────────────────┐
│ 超级块    │  inode 区        │        数据块区            │
│(文件系统  │  每个文件一个     │  文件内容按块（典型 4KB）   │
│ 元信息)   │  inode 结构      │  存放，可以不连续           │
└──────────┴─────────────────┴──────────────────────────┘

inode（索引节点）里有什么（高频背诵点）：

  • 文件类型与权限（rwx，详见第 11 章权限部分）、属主 UID/GID
  • 大小、时间戳（访问/修改/inode 变更三个时间）
  • 链接计数（多少个文件名指向它）
  • 数据块指针：直接指针 + 一级/二级/三级间接指针——小文件直接定位，大文件通过间接块逐级索引，这个多级结构也解释了单文件大小上限的由来
  • inode 里没有文件名

目录也是文件：内容是一张"文件名 → inode 号"的目录项（dentry）列表。查找 /home/a.txt 的过程：根目录 inode → 读出目录内容找到 home 的 inode 号 → 读 home 目录内容找到 a.txt 的 inode 号 → 拿 inode 定位数据块。

两个直接推论：

  • 文件名与文件本体解耦——重命名、移动（同文件系统内）只改目录项，数据一字节不动，所以 mv 大文件瞬间完成。
  • inode 数量在格式化时就定死，inode 用光后磁盘还有空间也创建不了新文件——海量小文件场景的经典故障，df -i 查看（详见第 11 章）。

硬链接

ln 源文件 链接名：在目录里再添一条指向同一个 inode 的目录项，链接计数 +1。

a.txt ──┐
        ├──→ inode 1024 ──→ 数据块
b.txt ──┘        （链接计数 = 2）
  • 两个名字完全平等，没有"原件/副本"之分；修改任一名字看到的内容，另一个立即同步（本来就是同一份数据）。
  • 删除（rm）只是删目录项、计数减一；计数为 0 且没有进程打开时，inode 和数据块才回收。
  • 两个限制：不能跨文件系统（inode 号只在本文件系统内唯一）；不允许对目录建硬链接（会造成目录环，破坏树形结构；. 和 .. 是系统预留的例外——这也解释了目录的链接数为什么是"2 + 子目录数"）。

软链接（符号链接）

ln -s 目标 链接名：创建一个独立的新文件（有自己的 inode），内容存的是目标路径字符串，访问时由内核自动跳转解析。

link ──→ inode 2048（类型：符号链接，内容："/home/a.txt"）
              ↓ 内核按路径再次解析
a.txt ──→ inode 1024 ──→ 数据块
  • 类似 Windows 快捷方式：可跨文件系统、可指向目录、可指向暂不存在的路径。
  • 目标被删除后成为悬空链接，访问报"No such file or directory"——文件明明列得出来却打不开的经典谜题。
  • 删除软链接本身只删这个小文件，不影响目标。

硬链接 vs 软链接对比

维度 硬链接 软链接
本质 同一 inode 的别名（目录项） 独立文件，内容是目标路径
inode 与目标相同 自己的新 inode
跨文件系统 不行 可以
链接目录 不允许 可以

文件描述符、打开文件表与 inode 的三层结构

进程 open 一个文件后，内核里有三层结构（本章最深考点）：

进程 A 的 fd 表          系统级打开文件表              inode 表（每文件一项）
┌────────────┐        ┌──────────────────┐
│ 0 → stdin  │        │ 表项 X：           │
│ 1 → stdout │        │  偏移量 offset     │──────→ inode 1024
│ 3 ─────────┼──────→ │  打开模式 O_RDONLY │        （文件元数据）
└────────────┘        │  引用计数          │
进程 B 的 fd 表         └──────────────────┘
│ 3 ─────────┼──────→ 表项 Y（自己的偏移量）──────→ inode 1024
  • fd 表：进程私有，fd 就是这张表的下标。
  • 打开文件表：系统级，每次 open 产生一个表项，记录文件偏移量、打开模式、引用计数。
  • inode 表：每个文件一份，多少次打开都指向同一个。

三种共享关系（判断题高发）：

  1. 两次独立 open 同一文件：两个打开文件表项，各自偏移互不干扰（如上图 A、B）。
  2. fork：子进程复制 fd 表，但表项指向同一个打开文件表项——父子共享偏移量，一方写入推进偏移，另一方接着写不会覆盖（这是重定向和日志共写不乱的基础；fork 详见第 4 章）。
  3. dup/dup2：同进程内两个 fd 指向同一打开文件表项，共享偏移——shell 重定向 2>&1 的实现（详见第 11 章）。

配套结论：删除一个正被进程打开的文件，空间不会立即释放——目录项没了、链接计数归零，但打开文件表还持有引用，进程关闭 fd 后才真正回收。工程名场面：日志文件被 rm 后 df 显示空间没回来，用 lsof | grep deleted 找到持有进程，重启或让它 reopen 才释放（详见第 11 章）。

常见面试追问

追问 1：为什么 inode 不存文件名？

文件名归目录管，好处是名与实体解耦：一个 inode 可以有多个名字（硬链接的基础）、重命名移动只改目录项不动数据、同名文件可以共存于不同目录。设计上"名字是目录的属性，不是文件的属性"。

追问 2：rm 一个文件后数据一定没了吗？

不一定，两道保险：还有其他硬链接时链接计数未归零，数据完好；有进程打开着该文件时，即使计数归零，打开文件表的引用仍撑着 inode，进程关闭后才释放。所以"删了但空间没回收"要查 lsof，"防误删"可以靠预建硬链接。

追问 3：mv 和 cp 在 inode 层面有什么区别？

同一文件系统内 mv 只改目录项（数据与 inode 不动，瞬间完成，inode 号不变）；跨文件系统的 mv 实际是 cp + rm（新 inode 新数据块）。cp 永远创建新 inode、拷贝数据。用 ls -i 看 inode 号即可验证。

追问 4：磁盘还有空间却提示 No space left on device，怎么回事？

inode 耗尽的典型症状：df -h 显示有空间、df -i 显示 inode 100%。海量小文件（缓存、session 文件、邮件队列）每个占一个 inode，把格式化时定死的配额吃光。清理小文件或重新格式化时调大 inode 数量。

追问 5：软链接和硬链接分别在什么场景用？

软链接用于"可切换的指针"：/usr/bin/python → python3.11、部署目录 current → releases/v2.3，切版本改一个链接即可，且可跨盘、可链目录。硬链接用于同文件系统内去重与防删：增量备份工具对未变化文件建硬链接省空间（同一 inode 零拷贝）。

追问 6：目录的链接计数为什么至少是 2？

目录自身的名字算一个，目录内的 . 指向自己又算一个，所以空目录计数为 2；每个子目录的 .. 指回父目录，父目录计数再加一——于是"计数 = 2 + 直接子目录数"，反过来还能用计数推子目录个数。

易错点

  • 说 inode 里存文件名。文件名在目录项里，这是本章第一考点。
  • 把硬链接理解成"复制了一份数据"。它只是同一 inode 的又一个名字，零数据拷贝。
  • 认为删除软链接会删目标，或认为目标删除后软链接还能用。
  • 硬链接跨文件系统、硬链接目录——两个"不允许"记不住。
  • 三层表关系混乱：说 fork 后父子偏移独立（实际共享），或说两次 open 共享偏移（实际独立）。
  • 不知道"文件被删但进程占着空间不放"的现象与 lsof 排查法。
  • 忽略 inode 耗尽这种"有空间却写不进"的故障形态。

面试回答模板

如果面试官问"讲讲 inode 和软硬链接"，可以这样回答：

Linux 把文件拆成两部分：inode 存元数据——权限、属主、大小、时间戳、链接计数和指向数据块的多级指针，数据块存内容；文件名不在 inode 里，而在目录中，目录本质是文件名到 inode 号的映射表，所以同文件系统内 mv 只改目录项瞬间完成，inode 数量格式化时定死，海量小文件会出现磁盘有空间却因 inode 耗尽建不了文件，用 df -i 排查。硬链接是给同一个 inode 再添一个名字，两个名字完全平等、共享数据，链接计数加一，rm 只删名字减计数，计数归零且无进程打开才真正释放；它不能跨文件系统也不能链接目录。软链接是独立的小文件，内容是目标路径，访问时内核二次解析，所以能跨文件系统、能指向目录，目标删除后它变悬空。进程层面访问文件有三层结构：进程私有的 fd 表、系统级打开文件表（存偏移量和打开模式）、inode 表。两次独立 open 各有偏移；fork 后父子指向同一个打开文件表项、共享偏移；dup 在进程内共享表项，这是 shell 重定向的原理。由此还有个名场面：日志文件被删空间不回收，因为进程还开着，打开文件表撑着 inode，用 lsof 找 deleted 状态的文件让进程重开即可。

9. IO 与零拷贝详解

题目

缓冲 IO 和直接 IO 有什么区别？传统文件传输为什么慢？零拷贝是什么，mmap、sendfile、splice 分别怎么优化的？

这道题在考什么

这道题几乎是后端面试的必考题，因为它背后站着 Kafka 和 Nginx——"Kafka 为什么快"问到底就是 sendfile。它综合了前面所有铺垫：用户态/内核态切换（第 1 章）、页缓存（内存与磁盘之间）、DMA，考察的是你能不能算清一笔账：一次"读文件发网络"到底切换几次、拷贝几次，每一次优化到底省掉了哪一步。这也是"背名词"和"真理解"区分度最大的一道题。

答题就是画账本：先把传统路径的 4 次拷贝、4 次切换一步步列出来，指出其中"数据进用户态只是过个路"的荒谬之处——这就是优化的靶子。然后 mmap、sendfile、splice 逐个对着账本划账：各省了哪次拷贝、哪次切换，还剩几次。最后留意边界：零拷贝依赖页缓存，所以大文件顺序传输反而可能选择绕过页缓存的直接 IO——能主动讲出"零拷贝不是万能"的场景，是加分项。

面试核心结论

一次传统的"读文件再发网络"要 4 次拷贝（磁盘→内核页缓存→用户缓冲区→socket 缓冲区→网卡，中间两次是 CPU 拷贝）和 4 次用户/内核态切换，数据在用户态只是过了个路。零拷贝的思路是让数据不再绕道用户空间：mmap 把页缓存直接映射进用户地址空间，省掉"内核→用户"一次 CPU 拷贝；sendfile 一个系统调用在内核内完成"文件→socket"，配合网卡 SG-DMA 能把 CPU 拷贝降到 0 次、切换降到 2 次；splice 借管道在任意两个 fd 之间做内核内搬运。Kafka 和 Nginx 传静态文件用 sendfile，大文件顺序读写还可以考虑绕过页缓存的直接 IO。

前置：页缓存与缓冲 IO / 直接 IO

内核在内存里维护页缓存（page cache）：读文件先查缓存，命中免磁盘 IO；写文件先写缓存标脏，由内核异步刷盘（详见第 7 章脏页回写）。

  • 缓冲 IO（默认）：read/write 都经过页缓存。收益是缓存命中、预读、写合并；代价是多一次"页缓存 ↔ 用户缓冲区"的 CPU 拷贝。
  • 直接 IO（O_DIRECT）：绕过页缓存直达磁盘。适合自己管理缓存的数据库和一次性大文件拷贝（避免污染页缓存把热数据挤掉，缓存污染详见第 7 章）。对齐要求严格、失去内核预读，用错反而更慢。
  • 再往上还有 C 库缓冲（printf/fread 的用户态缓冲，详见第 1 章库函数与系统调用之辨）：攒够再发 write，减少系统调用次数。三层缓冲各管一段。

传统方式的账：4 次拷贝 + 4 次切换

把磁盘文件发到网络，朴素写法 read(file, buf, len); write(sock, buf, len);：

read:  ① DMA 拷贝：磁盘 → 内核页缓存          （DMA 干活，CPU 闲）
       ② CPU 拷贝：页缓存 → 用户缓冲区 buf     ← 白绕用户态一圈
       （切换 2 次：进内核 + 回用户）
write: ③ CPU 拷贝：buf → socket 发送缓冲区     ← 又拷回去
       ④ DMA 拷贝：socket 缓冲区 → 网卡
       （切换 2 次）

合计：4 次拷贝（2 次 CPU + 2 次 DMA）、4 次状态切换

问题一目了然：数据在用户态没有做任何加工，②③两次 CPU 拷贝纯属搬运工开销。零拷贝的目标就是消灭它们——"零拷贝"指零次 CPU 参与的多余拷贝，DMA 拷贝无法省也无需省。

方案一：mmap + write

mmap 把文件的页缓存直接映射进进程地址空间（映射机制详见第 6 章），用户代码读"内存"就是读页缓存：

mmap:  ① DMA：磁盘 → 页缓存（用户空间直接可见，无需拷出）
write: ② CPU：页缓存 → socket 缓冲区
       ③ DMA：socket 缓冲区 → 网卡

3 次拷贝（1 次 CPU）、4 次切换
  • 省掉一次 CPU 拷贝；用户态还能访问和修改数据，灵活性保留。
  • 适合需要处理内容的场景、随机访问大文件；小文件不划算（建立映射、缺页的固定开销）。

方案二：sendfile（经典零拷贝）

sendfile(out_fd, in_fd, offset, count) 一个系统调用完成"文件 → socket"，数据全程不出内核：

基础版：① DMA：磁盘 → 页缓存
        ② CPU：页缓存 → socket 缓冲区
        ③ DMA：socket 缓冲区 → 网卡        —— 3 次拷贝、2 次切换

SG-DMA 版（网卡支持 scatter-gather）：
        ① DMA：磁盘 → 页缓存
        ② 只把"页缓存中数据的位置和长度"写入 socket 缓冲区（描述符，非数据）
        ③ SG-DMA 直接从页缓存搬到网卡      —— 2 次拷贝、0 次 CPU 拷贝、2 次切换
  • 切换也从 4 次降到 2 次（一个系统调用替代 read+write 两个）。
  • 局限：用户态完全接触不到数据，只适合"原样转发"；输出端历史上要求是 socket。
  • 名场面：Kafka 消费者拉取消息、Nginx 发送静态文件（sendfile on;）都靠它扛高吞吐。

方案三：splice 与 tee

splice 在任意 fd 与管道之间移动数据，内核内完成，原理是移动页缓存的引用（管道此处充当内核缓冲区的句柄）：

splice(file_fd → pipe) + splice(pipe → sock_fd)：0 次 CPU 拷贝
  • 比 sendfile 通用（两端可以是 socket→socket 等组合），代理场景可用它做内核级转发。
  • tee 在两个管道间"复制"数据引用，不消耗源数据。

对比总表

方案 CPU 拷贝 总拷贝 状态切换 用户态可见数据 场景
read + write 2 4 4 可见可改 需要加工数据
mmap + write 1 3 4 可见可改 大文件、需访问内容
sendfile 1 3 2 不可见 文件→网络原样转发
sendfile + SG-DMA 0 2 2 不可见 同上，硬件支持时
splice 0 2（引用移动） 2 不可见 任意 fd 间内核转发

常见面试追问

追问 1：零拷贝里的"零"到底指什么？

指 CPU 参与的内存间拷贝为零。DMA 拷贝（磁盘↔内存、内存↔网卡）由外设控制器完成，不占 CPU，也无法避免——数据总得物理移动。所以严格说 sendfile+SG-DMA 是"零 CPU 拷贝、两次 DMA 拷贝"。

追问 2：mmap 和 sendfile 怎么选？

看用户态要不要碰数据：要读取或修改内容（模板渲染、加密压缩）用 mmap，保留访问能力还省一次拷贝；纯转发（静态文件、消息拉取）用 sendfile，拷贝和切换都最少。另外小文件走 mmap 的映射与缺页开销可能得不偿失。

追问 3：Kafka 为什么快？和零拷贝什么关系？

三板斧之一就是 sendfile 零拷贝：消费者拉消息时数据从日志文件的页缓存直达网卡，不进用户态。另两板斧：顺序写磁盘（追加日志，磁盘顺序写接近内存速度）、批量与压缩。把零拷贝放进具体系统里讲，比背流程图更打动面试官。

追问 4：既然页缓存这么好，为什么数据库常用 O_DIRECT 绕过它？

双重缓存问题：数据库自己有精心设计的缓冲池，再叠内核页缓存等于同一份数据存两遍、两层各自淘汰互相干扰；数据库对刷盘时机还有严格的持久性要求。让专业的上层缓存接管，内核靠边站。

追问 5：写文件时数据什么时候真正落盘？断电会丢吗？

write 返回只代表进了页缓存（脏页），内核由回写线程按脏页比例/时间阈值异步刷盘，断电时未刷的脏页丢失。强持久化要显式 fsync（连元数据）/fdatasync（仅数据）；数据库每次提交 fsync WAL 日志就是为此。所以"write 成功 ≠ 数据安全"是必须点破的认知。

追问 6：sendfile 发送前想给数据加个头怎么办？

头部单独 write（或用 TCP_CORK 攒包避免小包），正文继续 sendfile；FreeBSD 的 sendfile 原生支持带 headers/trailers。追问的考点是"零拷贝路径上用户态改不了数据"这一局限的工程绕法。

易错点

  • 把 4 次拷贝说成全是 CPU 拷贝，或算不清 mmap/sendfile 各省了哪一次。
  • 认为零拷贝连 DMA 都省了。
  • 认为 sendfile 万能，忽略"用户态不可见数据"的前提——需要加工内容时它用不了。
  • 把页缓存和用户缓冲区混为一谈，或不知道 C 库缓冲、页缓存、硬件缓存是三层。
  • 认为 write 返回数据就安全落盘，不知道 fsync 的必要性。
  • O_DIRECT 当性能银弹随手用，忽略对齐要求和预读损失。

面试回答模板

如果面试官问"讲讲零拷贝"，可以这样回答：

先算传统方式的账：read 加 write 发一个文件，数据走磁盘到页缓存（DMA）、页缓存到用户缓冲区（CPU）、用户缓冲区到 socket 缓冲区（CPU）、再到网卡（DMA），共 4 次拷贝 4 次状态切换，中间两次 CPU 拷贝纯属搬运，因为用户态根本没加工数据。零拷贝就是消灭 CPU 的无效拷贝：mmap 把文件页缓存直接映射进用户地址空间，省掉内核到用户那次拷贝，还保留了访问修改数据的能力，适合要处理内容的场景；sendfile 一个系统调用在内核内完成文件到 socket，切换降到 2 次，配合支持 scatter-gather 的网卡，socket 缓冲区里只放数据位置描述符，DMA 直接从页缓存搬到网卡，CPU 拷贝归零，Nginx 发静态文件和 Kafka 消费拉取就靠它；splice 更通用，借管道在任意 fd 间做内核内引用移动。注意零拷贝的零指 CPU 拷贝，DMA 拷贝省不掉；sendfile 的局限是用户态碰不到数据，只适合原样转发。相关的还有缓冲与直接 IO 的取舍：默认缓冲 IO 享受页缓存的命中和预读，数据库这类自带缓冲池的系统用 O_DIRECT 绕开双重缓存；还要记住 write 返回只是进了页缓存，真正落盘要 fsync，数据库提交时刷 WAL 就是这个原因。

题目

这道题在考什么

从这章起画风一转：不考原理，考熟练度。面试官问 Linux 命令，是在探你的真实工作状态——简历上写着"熟悉 Linux"，一句"查看 8080 端口被谁占了"就能验出成色。这类题没有推导过程，答不上来就是答不上来，所以它考的其实是你有没有真在 Linux 环境下干过活。

常见面试追问

追问 1：怎么查看某个端口被哪个进程占用？

ss -tlnp | grep 8080 或 lsof -i:8080，输出里直接有 PID 和进程名。老系统用 netstat -tlnp。追问延伸：ss 读取内核 netlink 接口，比遍历 /proc 的 netstat 快得多，大量连接时差异明显。

追问 2：kill、kill -9、kill -15 有什么区别？

kill 默认发 SIGTERM(15)，进程可捕获后做清理优雅退出；kill -9 发 SIGKILL，不可捕获不可忽略，内核直接终结，进程没有任何善后机会（可能留下没刷盘的数据、没删的锁文件）。规范做法：先 -15 等几秒，不退再 -9。杀不掉的 D 状态与僵尸情形详见第 3、4 章。

追问 3：uniq 为什么要先 sort？

uniq 只合并相邻的重复行，乱序数据直接 uniq 会漏统计。sort 把相同行聚到一起后 uniq -c 才能得到正确计数。这是"Top N 统计"题最常见的丢分点。

追问 4：tail -f 和 tail -F 有什么区别？

-f 跟踪的是打开时那个 fd，日志轮转（logrotate 把 app.log 改名并新建）后它还盯着旧文件；-F 按文件名跟踪，检测到文件被替换会自动重新打开。生产看日志用 -F。背后正是第 8 章"fd 指向 inode 而非文件名"的机制。

追问 5：find 和 grep -r 都能搜，什么时候用哪个？

对象不同：find 按文件属性搜（名字、大小、时间、类型），不看内容；grep -r 按内容搜。组合拳：find . -name "*.log" -mtime -1 | xargs grep "ERROR"——先按属性筛文件，再在其中搜内容。

追问 6：xargs 是干什么的？和管道直接接有什么区别？

管道把前一命令的输出接到后一命令的 stdin；但 kill、rm 这类命令只认命令行参数不读 stdin，xargs 负责把 stdin 内容转成参数拼给命令。所以 ps ... | awk '{print $2}' | kill 无效，必须 | xargs kill。

易错点

  • tar 的压与解参数记混：czf 创建、xzf 解开，方向靠 c/x 区分。
  • 统计题忘了 sort 就 uniq，结果错还不自知。
  • rm -rf 配合变量 rm -rf $DIR/ 时变量为空即灾难，工程上先 echo 检查或用 ${DIR:?} 保护。
  • 分不清 >（覆盖）与 >>（追加），日志被清空才发现。
  • 用 kill -9 当第一选择，跳过 SIGTERM 的清理机会。
  • grep 进程时忘了排除 grep 自身（grep -v grep 或 pgrep）。
  • 只会单条命令，不会用管道把 grep/awk/sort/uniq 组合成统计流水线——面试官真正想看的是组合能力。

面试回答模板

如果面试官问"平时用哪些 Linux 命令，怎么排查问题"，可以这样回答：

按对象分四类。文件类：ls、find 按属性找文件、du 配 sort 找大文件、df 看磁盘和 inode、tar 打包，大文件用 less 和 tail -F 看，tail -F 按文件名跟踪、日志轮转后不丢。进程类：ps -ef 配 grep 找进程，top 里按 P、M 排序看资源大户，kill 先发 15 给清理机会、再 9 强杀，lsof 看进程打开的文件和端口。网络类：ss -tlnp 查监听端口和占用进程，ss -s 看连接状态分布，curl -v 调接口，tcpdump 抓包。文本三剑客分工是 grep 找行、sed 改行、awk 拆列统计：grep -rn 搜代码、-A -B 看上下文，sed 做替换和抽取行段，awk 按列过滤求和。真正的威力在管道组合，比如统计日志 Top10 IP：awk 取第一列、sort、uniq -c、sort -rn、head——要点是 uniq 只合并相邻行所以必须先 sort；再比如按名字批量杀进程要经过 xargs，因为 kill 只认参数不读标准输入。排障时这些命令按"先定位资源瓶颈、再锁定进程、最后看日志"的套路串起来用。

11. Linux 系统知识与排障实战详解

题目

Linux 的文件权限是怎么管理的？重定向和环境变量的原理是什么？/proc 是什么？线上机器 CPU 飙高、内存吃紧、磁盘打满，分别按什么套路排查？

这道题在考什么

这是操作系统部分的"毕业考"：把前面十章的知识揉进真实的线上排障场景。面试官抛出"CPU 飙高怎么查"，考的不是任何单个知识点，而是你有没有一套自己的排查方法论——有方法论的人答案是"先看什么、再看什么、每一步在排除什么"，没有的人只能报菜名式地念命令。这类题在面试评价里权重很高，因为它最接近真实工作。

前半部分（权限、重定向、环境变量、/proc）是排障的语言基础，理解到"重定向就是改 fd 表指向、/proc 是内核状态的窗口"即可，能和第 1、8 章的知识挂上钩。后半部分四大套路（CPU、内存、磁盘、load）要按"漏斗"记：每个套路都是"系统级现象 → 定位到进程 → 定位到线程/文件 → 定位到代码"的逐层收窄，背的时候记漏斗每层用什么工具、看什么指标，面试时顺着漏斗讲，条理自然清晰。

面试核心结论

系统知识四块：权限模型是"属主/属组/其他"各配 rwx，chmod 的数字法按 421 累加（755 = rwxr-xr-x），特殊位里 SUID 让程序以文件属主身份运行（passwd 能改 /etc/shadow 的原因）；重定向的本质是替换进程 fd 表里 0/1/2 指向的文件，2>&1 是让 fd2 复制 fd1 的指向，顺序写反则失效；环境变量随 fork/exec 传给子进程，export 决定是否传递，改 profile 要 source 才对当前 shell 生效；/proc 是内核状态的虚拟文件系统窗口，ps/top 的数据都来自它。排障有固定套路：CPU 高——top 找进程、top -Hp 找线程、转十六进制去堆栈里对号；内存高——free 看真实可用（buff/cache 可回收）、找 RSS 大户、警惕 OOM killer 和泄漏；磁盘满——df 加 du 逐层定位、df -i 查 inode、lsof 查已删未释放；load 高但 CPU 不高——查 D 状态进程和 IO（vmstat、iostat）。

文件权限模型

ls -l 输出的第一列共 10 位：

-rwxr-xr--  1 alice dev 4096 ...
│└┬┘└┬┘└┬┘
│ │  │  └─ 其他人 other：r--（只读）
│ │  └──── 属组   group：r-x（读+执行）
│ └─────── 属主   user ：rwx（全权限）
└───────── 类型：- 普通文件 d 目录 l 软链接

数字表示法：r=4、w=2、x=1，按位累加。755 = rwx(7) r-x(5) r-x(5)；644 = rw- r-- r--。常用命令：

chmod 755 script.sh        # 数字法
chmod u+x,g-w file         # 符号法：属主加执行、属组去写
chown alice:dev file       # 改属主和属组
chmod -R 755 dir/          # 递归

目录的 rwx 语义与文件不同（高频细节）：目录的 r 是列出文件名（ls）、w 是增删改名其中的文件、x 是进入（cd）和访问其中文件的 inode——没有 x，知道文件名也进不去；只有 w 没有 x 也删不了文件。所以"能否删除一个文件由其所在目录的 w+x 决定，与文件自身权限无关"，这是权限题的第一陷阱。

三个特殊位：

  • SUID（4）：可执行文件运行时以文件属主身份执行。passwd 是 root 属主带 SUID，普通用户运行它才能改 /etc/shadow。安全审计会全盘搜 SUID 程序。
  • SGID（2）：对文件同理作用于属组；对目录则让新建文件继承目录属组（团队共享目录常用）。
  • Sticky bit（1）：目录上生效，只有文件属主能删自己的文件——/tmp 的 1777 就是它，防止互删。

root 不受常规 rwx 约束；sudo 按 /etc/sudoers 授权临时提权。

重定向与管道的 fd 本质

回收第 8 章的三层结构：shell 启动进程前操纵其 fd 表，0=stdin、1=stdout、2=stderr。

cmd >  out.log        # fd1 指向 out.log（覆盖，O_TRUNC）
cmd >> out.log        # 追加（O_APPEND）
cmd 2> err.log        # 只重定向 stderr
cmd > all.log 2>&1    # 先让 fd1 指向文件，再让 fd2 复制 fd1 → 都进文件
cmd &> all.log        # 上一行的简写（bash）
cmd < in.txt          # fd0 从文件读
cmd > /dev/null 2>&1  # 全部丢弃（黑洞设备）

顺序陷阱：cmd 2>&1 > all.log 达不到目的——2>&1 执行时 fd1 还指向终端，fd2 复制的是"终端"这个指向，随后 fd1 才改指文件，结果 stderr 仍打到屏幕。2>&1 的准确语义是"把 fd2 变成 fd1 当前指向的副本"（dup2），指向的复制发生在执行那一刻。

管道 a | b：shell 创建匿名管道，把 a 的 fd1 和 b 的 fd0 接到管道两端（机制详见第 3 章），于是任意两个只会读写标准流的程序都能拼装——Unix 哲学"每个程序做好一件事，用文本流协作"的落地。

环境变量

进程属性的一部分，fork 时复制、exec 时按参数传递（详见第 4 章）：

echo $PATH                 # 查看；PATH 决定命令搜索路径，顺序敏感
export MY_ENV=1            # 设置并导出：子进程可见
MY_ENV=1 ./app             # 只对这一次运行生效
env / printenv             # 列出全部
  • export 的意义：不 export 的变量是 shell 本地变量，fork 出的子进程看不到。
  • 配置文件生效范围：/etc/profile 全局登录、~/.bashrc 每个交互 shell；修改后对已开终端无效，source ~/.bashrc 让当前 shell 重新执行它——source 在当前进程内执行脚本，直接运行脚本则是 fork 出子 shell、改的是子进程的环境，退出即失效。这组区别是高频题。
  • PATH 里不含 .，所以当前目录程序要 ./app 运行（安全设计，防止进入恶意目录后敲 ls 中招）。

/proc：内核状态的文件窗口

虚拟文件系统，内容由内核实时生成，读它就是读内核数据结构：

/proc/cpuinfo /proc/meminfo        # CPU、内存信息（top/free 的数据源）
/proc/loadavg                      # 负载
/proc/<pid>/status                 # 进程状态、内存用量
/proc/<pid>/fd/                    # 进程打开的所有 fd（lsof 数据源）
/proc/<pid>/limits                 # 该进程的资源限制（nofile 等）
/proc/sys/...                      # 内核参数，sysctl 的操作对象

ps、top、lsof 都是 /proc 的封装。排障时直接翻 /proc 是"工具不在也能查"的底牌；ulimit -n 与《网络篇》第 12 章的 fd 上限调优在 /proc/sys/fs/file-max 汇合。

排障套路一：CPU 使用率飙高

① top             # 定位进程：看 %CPU 最高的 PID；同时看 us/sy/si/wa 分布
② top -Hp <PID>   # 定位线程：该进程内哪个线程（LWP）在烧 CPU
③ printf '%x' <TID>   # 线程号转十六进制
④ 拿堆栈对号：Java 用 jstack 搜 nid=0x...；C++ 用
   gdb -p <PID> 后 thread apply all bt，或 perf top -p <PID> 直接看热点函数
⑤ 对着代码定位：死循环、忙轮询、正则回溯、频繁 GC/内存分配都是常客

看分布的经验：us 高是业务代码问题；sy 高是系统调用密集（频繁小 IO、锁竞争）；si 高看网络软中断（详见第 1 章）；wa 高说明 CPU 在等磁盘，转入 IO 排查。

排障套路二：内存吃紧与 OOM

① free -h         # 关键看 available（真实可用），buff/cache 属于页缓存可回收（第 9 章），
                  # 「内存被吃光」多数是错觉
② top 按 M        # 找 RSS 大户；smem/pmap -x <PID> 细看进程内存构成
③ 确认泄漏：同一进程 RSS 持续单调上涨不回落 → 用 valgrind/ASan（C++）或语言级工具定位
④ OOM killer：内存真耗尽时内核按 oom_score 杀分数最高的进程
   dmesg | grep -i "killed process" 验尸；重要服务可调 oom_score_adj 降低被杀概率
⑤ swap 持续换入换出（vmstat 的 si/so 列）→ 物理内存不足，已在抖动边缘（第 7 章）

"进程莫名消失"先查 dmesg 的 OOM 记录，这是运维一线的肌肉记忆。

排障套路三：磁盘打满

① df -h                          # 哪个挂载点满了
② du -sh /path/* | sort -rh | head    # 从挂载点逐层下钻找大目录/大文件
③ df -i                          # 空间没满却写不进 → inode 耗尽（第 8 章）
④ lsof | grep deleted            # 已删除但进程仍持有的文件占着空间（第 8 章名场面）
⑤ 处置：清日志（>app.log 截断比 rm 更稳，fd 不失效）、日志轮转 logrotate、大文件归档

排障套路四：load 高但 CPU 不高

load average 的含义先立正：处于可运行状态 + 不可中断睡眠（D）状态的任务数的 1/5/15 分钟指数平均。它统计的是"排队的任务"，队伍可能排在 CPU，也可能排在磁盘。

① uptime          # 三个值对比核数：单核 load 1 是满载；看趋势（1 分钟 vs 15 分钟）
② vmstat 1        # r 列（等 CPU 队列）高 → 真是 CPU 不够；b 列（阻塞任务）高 → IO 方向
③ ps -eo stat,pid,cmd | grep '^D'   # 揪出 D 状态进程（等磁盘/NFS，kill 无效，第 2 章）
④ iostat -x 1     # 看磁盘 %util 接近 100、await 飙升 → 磁盘瓶颈实锤
⑤ 根因常见：磁盘坏/满、NFS 挂死、数据库慢查询打爆 IO

这道题的分水岭在"load 包含 D 状态任务"这一知识点：CPU 空闲而 load 爆表，几乎就是 IO 或锁死的进程在排队。

常见面试追问

追问 1：chmod 777 有什么问题？合理的权限应该怎么给？

777 让任何用户可写可执行，等于放弃权限体系：恶意或误操作可以篡改程序被属主执行，Web 目录 777 更是挂马温床。原则是最小权限：程序 755、配置 644、私钥 600；需要共享用组权限（SGID 目录）解决，而非全开。

追问 2：为什么删文件看的是目录权限而非文件权限？

删除的动作是"从目录中移除一条目录项"（第 8 章：文件名存于目录），操作对象是目录内容，所以需要目录的 w+x。文件自身权限管的是读写文件内容。连带考点：/tmp 用 sticky bit 补丁——目录可写但只许删自己的文件。

追问 3：2>&1 > file 和 > file 2>&1 有什么区别？

后者正确：fd1 先指向 file，fd2 再复制 fd1 的指向，两路都进文件。前者 fd2 先复制了 fd1 当时的指向（终端），之后 fd1 才改指文件，结果 stderr 仍在屏幕。核心在 2>&1 是 dup2 语义的"当下复制"，与书写顺序强相关。

追问 4：source script.sh 和 ./script.sh 有什么区别？

./ 方式 fork 一个子 shell 执行，脚本里的变量、cd 都发生在子进程，退出即消散；source（或 .）在当前 shell 进程内逐行执行，环境改动保留下来。所以改完 bashrc 要 source，部署脚本里 export 的变量想留给当前会话也得 source。

追问 5：buff/cache 占了几十 G，是内存泄漏吗？

页缓存的正常形态：内核用空闲内存缓存文件数据加速 IO（第 9 章），有内存压力时自动回收。判断真实余量看 free 的 available 列。真泄漏的特征是某进程 RSS 单调增长且 available 持续下降。

追问 6：strace 是干什么的？什么时候用？

跟踪进程的系统调用序列（strace -p PID 或 strace ./app），能看到每个 syscall 的参数、返回值和耗时。适用："程序卡住不知道在干嘛"（看卡在哪个调用上，如 connect 超时、读某个文件）、"报错但日志没写原因"（看哪个 open/write 返回了错误码）。它与第 1 章的系统调用知识首尾呼应：理解了 syscall，strace 的输出就是一部实况剧本。

易错点

  • 权限题栽在目录语义：以为文件 644 就删不掉，忽略删除看目录 w+x。
  • 数字权限口算错：755 与 750、644 与 640 的差别要熟到条件反射。
  • 2>&1 与 > file 顺序写反。
  • 修改 bashrc 后新终端生效、当前终端没 source，误以为配置没写对。
  • 把 buff/cache 当泄漏，或者用 free 列而不看 available。
  • load 高就断言 CPU 不够，漏掉 D 状态与 IO 队列这半边天。
  • 清日志用 rm：进程还开着 fd，空间不释放（要用截断或先轮转）。
  • 不知道 dmesg 里能验 OOM 尸检记录，进程消失查成灵异事件。

面试回答模板

如果面试官问"CPU 飙高怎么排查"（此类题按套路答）：

先 top 定位进程，同时看 us、sy、wa、si 的分布判方向：us 高是业务代码，sy 高是系统调用密集，wa 高转去查磁盘，si 高看网络软中断。锁定进程后 top -Hp 找到烧 CPU 的线程，把线程号转十六进制，C++ 用 gdb 附上去 thread apply all bt 或直接 perf top 看热点函数，Java 用 jstack 按 nid 对号，最后落到代码上，常见元凶是死循环、忙轮询、正则回溯和频繁分配。如果是 load 高但 CPU 不高，思路换成查排队：load 统计的是可运行加不可中断睡眠的任务，vmstat 看 r 和 b 列，ps 揪 D 状态进程，iostat 看磁盘 util 和 await，多半是磁盘、NFS 或慢查询把 IO 打爆。内存问题先看 free 的 available，buff/cache 是页缓存可回收，别当泄漏；真泄漏看进程 RSS 是否单调涨，进程莫名消失先 dmesg 查 OOM killer 记录。磁盘满 df 定挂载点、du 逐层下钻，空间没满写不进查 df -i 的 inode，删了文件空间不回收用 lsof 找 deleted——这些套路串起来，基本能覆盖线上最常见的四类资源问题。

面向对象基础与设计模式思维

设计模式不是一组需要脱离代码背诵的名词，而是面向对象设计中反复出现的“变化点处理方案”。如果还没有形成类、对象、接口和组合的基本感觉，直接背 GoF 模式很容易变成把名字和结构图硬配对。因此先用这一章导读建立一套共同语言。

从类和对象开始

  • 类描述一类对象的状态和行为；对象是类在运行时的一个实例。
  • 封装把状态和操作状态的规则放在一起，并隐藏不应被外部直接修改的细节。
  • 抽象只暴露调用者真正需要的能力，例如“可发送消息”，而不要求调用者知道底层是 TCP、文件还是内存队列。
  • 接口是协作双方约定的能力边界，可以由纯虚函数、抽象基类、模板约束或普通的稳定 API 表达。

设计模式反复解决的核心问题是：当实现细节变化时，哪些调用方应该保持不变？答案通常不是“再加一个继承层”，而是找到正确的抽象边界，把变化隔离到一个小范围内。

继承、组合和依赖分别表达什么

关系 直观问题 适合表达
继承（is-a） 子类能否在任何需要父类的地方成立 稳定的类型替换关系、运行时多态
组合（has-a） 一个对象是否由另一个对象协作完成工作 可替换实现、行为拼装、资源管理
聚合 对象拥有或组织其他对象，但生命周期可以相对独立 集合、管理器、业务上下文
依赖 一个对象临时使用另一个对象的能力 参数、返回值、局部协作、服务调用

经验法则是“优先组合而不是继承”，但它不是禁止继承。继承适合表达真正稳定的 is-a 关系；如果只是为了复用几段代码，组合、委托或独立工具函数通常更容易维护。第 12 章的里氏替换原则会把这个判断讲得更严格。

多态不只有虚函数

面向对象语境下常说的多态，通常指通过基类接口在运行时选择派生类实现；C++ 还常用模板、重载、特化和 concepts 在编译期完成类似的“按能力或类型选择”。

  • 需要运行时切换实现、把不同类型放进同一容器时，常用虚函数和接口。
  • 类型在编译期已知、追求内联和零额外运行时开销时，常用模板和静态多态。
  • 两种方式都服务于解耦，差别在于变化发生的时间、可替换范围和编译成本。

用一个固定框架阅读每个模式

后面的每个模式都建议按下面五个问题学习：

  1. 痛点：没有这个模式时，代码在哪个变化场景下会变得僵硬？
  2. 变化点：真正会变化的是对象创建、算法、通知关系、接口还是实现维度？
  3. 结构：谁持有谁，谁调用谁，新增一种变化需要新增什么代码？
  4. 代价：引入了多少间接层、对象、虚调用、模板实例或生命周期管理？
  5. 边界：什么时候直接写条件分支更清楚，什么时候模式会构成过度设计？

例如，策略模式不是“把 if-else 改成几个类”这么简单，而是当算法有多个可替换版本且变化频繁时，把算法封装成独立策略；如果只有两个永远不会增加的分支，简单条件判断可能更合适。

设计模式部分的学习路线

  • 第 12 章先建立 GoF 三大类和设计原则的总地图。
  • 第 13 章关注对象如何创建，以及创建过程如何与使用方解耦。
  • 第 14 章关注已有类和对象如何组合，重点比较适配器、装饰器和代理。
  • 第 15 章关注对象之间如何分配职责、传递请求和协作。
  • 第 16 章把模式放到并发、IO 和服务端架构中，理解事件循环、生产者消费者和池化。
  • 第 17 章回到 C++ 与 STL，观察模板、RAII、迭代器和 pimpl 如何把模式变成语言惯用法。

读完一个模式后，最好能用一句话说清“它隔离了哪个变化”，再用一个真实的小例子说明取舍。能讲清为什么使用、为什么不用，通常比能背出更多模式名称更重要。

12. 设计模式总览与六大设计原则详解

题目

设计模式分哪几大类？六大设计原则分别是什么含义？面试被问"你熟悉哪些设计模式"应该怎么组织回答？

这道题在考什么

设计模式部分的开篇导航题。面试官问"你熟悉哪些设计模式"，其实不太关心你能报出几个名字——报菜名恰恰是最差的回答。这道题真正考的是：你知不知道模式的分类地图（三大类各管什么）、模式背后的立法精神（六大原则），以及最关键的——你会不会组织这个开放性问题的回答。它是后面五章的总目录，先把地图立起来，具体模式才有挂靠的地方。

三大类按解决的问题记：创建型管"对象怎么造出来"，结构型管"类和对象怎么组装"，行为型管"对象之间怎么协作"。六大原则不用平均用力，开闭原则是核心中的核心（几乎每个模式都是它的实现手段），单一职责和依赖倒置次之。回答"你熟悉哪些"的标准姿势本章末尾给了模板：报分类 → 挑三四个真用过的深讲 → 落到 STL 或项目实例，记住这个结构比多背五个模式有用。

面试核心结论

GoF 23 种模式按目的分三类：创建型（5 种）管"对象怎么造"——单例、工厂方法、抽象工厂、建造者、原型；结构型（7 种）管"类和对象怎么组装"——适配器、装饰器、代理、外观、桥接、组合、享元；行为型（11 种）管"对象之间怎么协作分工"——观察者、策略、模板方法、职责链、命令、状态、迭代器、访问者、中介者、备忘录、解释器。六大原则是模式背后的"宪法"：单一职责（一个类只有一个变化原因）、开闭（对扩展开放、对修改关闭——最核心）、里氏替换（子类必须能透明替换父类）、接口隔离（接口要小而专）、依赖倒置（依赖抽象接口，上层不依赖下层实现）、迪米特法则（只与直接朋友通信）。回答"你熟悉哪些"的正确姿势：报三类分类 → 挑三四个真用过的深讲（场景 → 解决什么 → 代码/工程实例）→ 落到 STL 与项目里的真实应用（详见第 17 章），切忌报菜名式罗列 23 个。

为什么需要设计模式

一句话定位：设计模式是面向对象设计中反复出现的问题的成熟解法命名集。价值三条：

  1. 复用经过验证的结构，少走弯路——前人踩坑的结晶。
  2. 建立团队词汇表："这里用观察者解耦"一句顶十行注释，沟通成本骤降。
  3. 落实设计原则：模式是原则的实操化——开闭原则说"不改代码扩展功能"，策略模式、工厂模式就是它的施工图。

反面也要立住（面试的成熟度信号）：模式是手段，解耦与可维护才是目的。小问题套大模式是过度设计——三行 if-else 能解决的事引入策略工厂只会徒增间接层；先写简单直接的代码，等变化真的来了再重构进模式（"用重构走向模式"）。

六大设计原则逐条讲

1. 单一职责原则（SRP）：一个类只应有一个引起它变化的原因。

  • 反例：一个 UserService 同时管用户逻辑、发邮件、写日志——邮件模板改动都要动它。
  • 判断标尺："描述这个类的职责时，是否需要用'和'字"。
  • 它同样适用于函数与模块，是粒度设计的第一原则。

2. 开闭原则（OCP）：对扩展开放，对修改关闭——新增功能靠加代码，尽量避免改老代码。

  • 反例：每加一种支付方式就在 pay() 里加一个 else if——每次都动老逻辑、回归全量测试。
  • 正解：抽象出 Payment 接口，新方式 = 新增一个实现类（策略 + 工厂，详见第 26、28 章）。
  • 它是六原则的核心，其余原则和大半模式都在为它服务。

3. 里氏替换原则（LSP）：所有用父类的地方，换成子类必须行为正确——子类可以扩展父类，但绝对能透明顶替父类。

  • 经典反例：Square 继承 Rectangle 并在 setWidth 里同时改高——调用方按矩形语义写的代码（设宽 4 高 5 期望面积 20）被正方形破坏。继承关系不成立，应改组合或抽象出共同基类。
  • 工程化落点：子类重写不该收窄前置条件、放宽后置约束；C++ 里"public 继承承诺 is-a"就是它的语言表达（《C++ 篇》第 8 章）。

4. 接口隔离原则（ISP）：客户端不应被迫依赖它用不到的接口——多个专用小接口优于一个万能大接口。

  • 反例：Worker 接口带 work() 和 eat()，机器人实现类被迫写一个空的 eat()。
  • 拆成 Workable / Eatable，各取所需。与 SRP 的关系：SRP 约束类的职责，ISP 约束接口的粒度。

5. 依赖倒置原则（DIP）：高层模块与低层模块都依赖抽象；细节依赖抽象，抽象不依赖细节。

  • 反例：OrderService 直接 new MySQLRepository()——换存储要改业务代码。
  • 正解：OrderService 依赖 IRepository 接口，具体实现从外部注入（依赖注入是 DIP 的实施手段）。
  • 收益直接体现在可测试性：注入 mock 即可单测（联动第 13 章工厂、第 17 章）。

6. 迪米特法则（LoD，最少知识原则）：只和直接朋友（成员、参数、返回值）交谈，不和"朋友的朋友"交谈。

  • 反例：a.getB().getC().getD().doSomething()——链上任何一环改动都会波及调用方。
  • 正解：让 A 提供一个封装了意图的方法，内部转达。降低耦合面，代价是可能增加转发方法，适度即可。

（有的资料把六原则加上"合成复用原则"（优先组合而非继承）称七大原则——组合优于继承这句话本身必须会说，呼应《C++ 篇》第 8 章。）

常见面试追问

追问 1：开闭原则听起来很理想，实际能做到完全不改代码吗？

做不到也不必教条。开闭针对的是已识别的变化维度：预判会频繁变的轴（支付方式、导出格式）预留扩展点；没预判到的变化第一次来时借重构建立扩展点，第二次起就"只加不改"。合理表述是"对高频变化封闭修改"，全局绝对封闭是过度设计。

追问 2：单一职责的"职责"粒度怎么把握？

以"变化的原因"为尺，以业务视角切分：报表的计算规则和展示格式由不同角色驱动变化，就该分两个类；两段逻辑永远同进同退，拆开反而碎片化。粒度没有公式，标准是"一次需求变更是否只需要动一个类"。

追问 3：里氏替换和多态是什么关系？

多态是语言机制（虚函数、动态绑定，《C++ 篇》第 12 章），LSP 是使用这套机制的语义纪律：机制保证"能调到子类方法"，LSP 保证"调到之后行为仍符合父类契约"。违反 LSP 的继承照样能编译运行，炸的是调用方的假设——正方形继承矩形就是机制合法、语义翻车。

追问 4：依赖倒置和依赖注入有什么区别？

DIP 是原则：依赖抽象。DI 是手段：把具体实现从外部塞进来（构造函数注入最常见），从而落实 DIP。还有一个词 IoC（控制反转）描述"对象获取依赖的控制权从自己 new 反转给外部容器/调用方"。一句话：IoC 是思想，DIP 是原则，DI 是技法。

追问 5：什么时候算过度设计？给个判断标准。

三个信号：为"想象中的变化"引入抽象层（YAGNI 违背）；间接层数超过当前问题复杂度（读代码要跳五个文件才见真逻辑）；模式带来的接口数量超过其消灭的分支数量。健康路径是"先直白实现 → 变化出现 → 重构成模式"，让模式被需求拉出来，别被简历推出来。

追问 6：C++ 和 Java 的设计模式实践有什么不同？

C++ 多了编译期武器：模板可以做静态多态替代部分运行时模式——策略可用模板参数注入（零虚函数开销）、CRTP 实现编译期模板方法（《C++ 篇》第 24 章）；RAII 让资源管理类模式（如某些场景的代理）语言内建化。Java 全员虚方法 + 反射 + 容器生态，运行时模式与框架化 DI 更普及。答出"C++ 把一部分模式做进了编译期"即显功力（详见第 17 章）。

易错点

  • 23 种全背名字、单个讲不深——面试官要深度抽样，宁可只精三个。
  • 六大原则只背中文名，给不出反例与修正——原则题的分全在例子上。
  • 里氏替换讲成"子类继承父类"同义反复，举不出正方形-矩形这类违例。
  • 分不清依赖倒置/依赖注入/控制反转三个词的层次。
  • 把模式当银弹，任何题都往模式上套，暴露"为模式而模式"的学生气。
  • 被问"项目里用过什么模式"时举不出真实场景——提前准备两个带上下文的实例（连接池单例、回调观察者）。

面试回答模板

如果面试官问"你了解哪些设计模式"，可以这样回答：

GoF 23 种按目的分三类：创建型管对象怎么造，有单例、工厂方法、抽象工厂、建造者、原型；结构型管类和对象怎么组合，有适配器、装饰器、代理、外观、桥接、组合、享元；行为型管对象怎么协作，观察者、策略、模板方法、职责链这些。我实际用得最多的三个：一是单例，做配置中心和连接池，C++ 里用函数内静态局部变量的 Meyers 写法，C++11 保证线程安全；二是策略加工厂，把支付渠道这类频繁新增的分支抽成接口，新渠道只加一个类不改老代码，这是开闭原则的落地；三是观察者做事件解耦，订单状态变化通知库存、积分各模块，新增订阅方零侵入。这些背后是六大原则：单一职责控制类的变化原因，开闭是核心目标——加代码而不是改代码，里氏替换保证子类能透明顶替父类否则继承就是错的，接口隔离要求接口小而专，依赖倒置让高层依赖抽象、配合依赖注入还带来可测试性，迪米特法则控制耦合面。另外 C++ 本身到处是模式：STL 迭代器、RAII、std::function 回调、模板做的编译期策略。我的原则是模式服务于解耦，简单问题先写直白实现，变化真来了再重构成模式。

13. 创建型设计模式详解（工厂三兄弟、建造者、原型与单例补遗）

题目

简单工厂、工厂方法、抽象工厂有什么区别，各自适用什么场景？建造者模式解决什么问题？原型模式呢？单例的饿汉和懒汉写法怎么选？

这道题在考什么

new 一个对象还需要模式？这是很多人对创建型模式的第一反应，也正是这道题的考点：当对象的创建逻辑复杂（要选型号、要配套、要分步骤组装）时，把"怎么造"的知识散落在每个使用方，改一次型号就要改一片代码——创建型模式全是为了把这些知识收拢到一处。工厂三兄弟的区别是本章最高频的考题，考的是你能不能说清三者的演进逻辑而不是背三段定义。

三兄弟按"扩展性递进"串：简单工厂一个方法包打天下，但加新产品要改它（违反开闭）→ 工厂方法把"造什么"下放给子类，加产品只加类不改代码 → 抽象工厂再升一维，管"一整套配套产品"（产品族）。判断用哪个就看变化维度：单产品扩展用工厂方法，成套切换用抽象工厂。建造者对付"构造参数爆炸"，原型对付"初始化昂贵"，单例部分直接给 C++ 最佳实践（Meyers 局部静态）——各记一个"它治什么病"即可。

面试核心结论

创建型模式的共同使命：把"造对象"的知识从使用方剥离，new 关键字集中管理，使用方只面对抽象。工厂三兄弟按扩展维度递进：简单工厂用一个静态方法按参数分支造对象，简单直接但新增产品要改工厂（违开闭）；工厂方法把"造什么"下放给子类——一个产品一个工厂类，新增产品只加类不改代码，代价是类数量膨胀；抽象工厂面向产品族——一个工厂造一整套配套产品（同一主题的按钮+文本框），切换产品族换一个工厂即可，新增族容易、给族加新品类难。建造者分离"复杂对象的构建步骤"与"表示"，链式 setter 分步组装，解决构造参数爆炸与不变式校验；原型靠克隆已有对象来创建，绕开昂贵的初始化，C++ 里就是虚函数版的拷贝构造（clone 惯用法）。单例的饿汉（程序启动即构造，天然线程安全、无法懒加载）与懒汉（首次使用才构造，须处理并发），C++ 首选 Meyers 局部静态写法。

简单工厂：入门与它的天花板

class Product {
public:
    virtual ~Product() = default;
    virtual void use() = 0;
};
class ProductA : public Product { public: void use() override; };
class ProductB : public Product { public: void use() override; };

class SimpleFactory {
public:
    static std::unique_ptr<Product> create(const std::string& type) {
        if (type == "A") return std::make_unique<ProductA>();
        if (type == "B") return std::make_unique<ProductB>();
        return nullptr;
    }
};
// 使用方：auto p = SimpleFactory::create("A");  只认 Product 接口
  • 价值：调用方与具体类解耦，创建逻辑（参数解析、依赖装配）集中一处。
  • 天花板：新增 ProductC 必须修改 create 的分支——在工厂内部违反开闭。产品少且稳定时它就够用（务实表态），产品频繁增加就升级到工厂方法。
  • 改良中间态：用"注册表"消灭分支——map<string, function<unique_ptr<Product>()>>，新产品向 map 注册创建 lambda，工厂只查表。C++ 里这是简单工厂通向开闭的常用路（配合第 17 章 std::function）。

工厂方法：一个产品一个工厂

把"造什么"延迟到子类决定：

class Factory {
public:
    virtual ~Factory() = default;
    virtual std::unique_ptr<Product> create() const = 0;   // 工厂方法
};
class FactoryA : public Factory {
public: std::unique_ptr<Product> create() const override { return std::make_unique<ProductA>(); }
};
class FactoryB : public Factory {
public: std::unique_ptr<Product> create() const override { return std::make_unique<ProductB>(); }
};

void client(const Factory& f) {        // 使用方依赖抽象工厂接口（依赖倒置，第 12 章）
    auto p = f.create();
    p->use();
}
  • 新增产品 = 新增一对（ProductC, FactoryC），任何老代码不动——开闭原则达成。
  • 工厂子类还可以封装各自的装配细节（连接参数、依赖注入），这是它比"注册表简单工厂"更强的地方。
  • 代价：类数量翻倍；产品维度单一（每个工厂只造一种东西）——产品成"族"时再升级。

抽象工厂：面向产品族

场景：跨风格 UI——亮色主题的按钮+输入框要配套出现，暗色一套同理；换主题必须整族切换。

class Button   { public: virtual ~Button() = default;   virtual void draw() = 0; };
class TextBox  { public: virtual ~TextBox() = default;  virtual void draw() = 0; };

class UIFactory {                       // 抽象工厂：一族产品的创建接口
public:
    virtual ~UIFactory() = default;
    virtual std::unique_ptr<Button>  createButton()  = 0;
    virtual std::unique_ptr<TextBox> createTextBox() = 0;
};
class LightFactory : public UIFactory { /* 造 LightButton / LightTextBox */ };
class DarkFactory  : public UIFactory { /* 造 DarkButton  / DarkTextBox  */ };
// 换主题 = 换传入的工厂对象，配套关系由工厂保证，永不混搭
  • 解决"产品族一致性"：使用方不可能拿到亮色按钮配暗色输入框。
  • 两个扩展方向的不对称（必考）：新增产品族容易（加一个工厂实现类）；给族里新增产品种类难（抽象工厂接口要加方法，全部工厂实现都得改）。所以它适合"族会增加、族内品类稳定"的场景。

维度 简单工厂 工厂方法 抽象工厂

建造者模式：分步构造复杂对象

痛点：对象有一堆可选参数，构造函数写成 HttpRequest(url, method, headers, body, timeout, retry, proxy...)——参数顺序灾难（telescoping constructor）。

class HttpRequest {
public:
    class Builder {
    public:
        Builder& url(std::string u)        { url_ = std::move(u); return *this; }
        Builder& method(std::string m)     { method_ = std::move(m); return *this; }
        Builder& timeout(int ms)           { timeoutMs_ = ms; return *this; }
        Builder& header(std::string k, std::string v) {
            headers_.emplace(std::move(k), std::move(v)); return *this;
        }
        HttpRequest build() {              // 统一出口：做不变式校验
            if (url_.empty()) throw std::invalid_argument("url required");
            return HttpRequest(*this);
        }
    private:
        friend class HttpRequest;
        std::string url_, method_ = "GET";
        int timeoutMs_ = 3000;
        std::map<std::string, std::string> headers_;
    };
private:
    explicit HttpRequest(const Builder& b);   // 只能经 Builder 构造
};

auto req = HttpRequest::Builder{}
               .url("https://api.example.com")
               .method("POST")
               .timeout(500)
               .header("Auth", "token")
               .build();
  • 三大收益：可选参数按名设置、顺序无关；build() 集中校验，杜绝半成品对象；产品可做成不可变对象。
  • 经典定义里还有 Director（指挥者）编排固定构建流程，工程中常省略——链式 Builder 是主流形态。
  • 生活中的原型：SQL 拼接器、各类 Client/Option 配置对象、std::ostringstream 的流式拼装思想同源。

原型模式：克隆代替构造

场景：对象初始化昂贵（解析大配置、加载模型、查库装配），而新对象与既有对象大同小异——复制现成的再微调，跳过昂贵初始化。

class Shape {
public:
    virtual ~Shape() = default;
    virtual std::unique_ptr<Shape> clone() const = 0;   // 原型接口
};
class Circle : public Shape {
public:
    std::unique_ptr<Shape> clone() const override {
        return std::make_unique<Circle>(*this);          // 委托拷贝构造
    }
};
// 使用方持有 Shape*，不知道具体类型也能复制出同类对象——这是 clone 的独特价值

C++ 视角两句话：clone 惯用法解决"通过基类指针进行多态拷贝"（直接拷贝构造会对象切片，《C++ 篇》第 12 章）；深浅拷贝的正确性由各类的拷贝构造负责（《C++ 篇》第 9 章）。原型注册表（预置一批原型按名克隆）常与简单工厂结合。

单例补遗：饿汉 vs 懒汉

线程安全实现（Meyers 局部静态、call_once、DCLP 的坑）已在《C++ 篇》第 25 章完整展开，此处补齐模式视角的对比：

// 饿汉：程序启动（main 前）即构造
class EagerSingleton {
    static EagerSingleton instance_;          // 静态成员，加载期初始化
public:
    static EagerSingleton& get() { return instance_; }
};

// 懒汉（Meyers）：首次调用才构造，C++11 起线程安全
class LazySingleton {
public:
    static LazySingleton& get() {
        static LazySingleton instance;        // 首次执行到这行才构造
        return instance;
    }
};
维度 饿汉 懒汉
构造时机 程序启动 首次使用
线程安全 天然（进 main 前单线程） 需保证（Meyers/call_once 已解决）
资源 不用也占着 按需
风险 静态初始化顺序问题（跨编译单元依赖它的其他全局对象可能先初始化） 首次调用有一次构造延迟

单例的批判面也要会讲：全局状态难测试（无法注入替身）、隐藏依赖关系、生命周期与销毁顺序难控——现代工程倾向"依赖注入传递单个实例"替代到处 Singleton::get()，答出这层是加分项（呼应第 12 章 DIP）。

常见面试追问

追问 1：工厂方法相比简单工厂到底多解决了什么？

把"新增产品要改工厂分支"变成"新增一对类"：修改闭合、扩展开放。附带收益是每个工厂子类可以封装专属装配逻辑。当产品创建无装配差异时，注册表版简单工厂同样满足开闭且类更少——能说出这个替代方案，说明理解的是原则本身。

追问 2：抽象工厂"新增一个产品种类"为什么难？

品类是抽象工厂接口的方法维度：加 createSlider() 意味着接口变更，所有已实现的工厂族全部跟着改——修改扩散到整个工厂体系。族维度（新增一套主题）只是新增实现类。两个维度的开闭不可兼得，选它之前先确认"族变、品类稳"。

追问 3：建造者和工厂的本质区别？

关注点不同：工厂管"选哪个类"，一步产出，重点在多态类型的决策；建造者管"一个复杂对象怎么一步步配出来"，多步组装 + 最终校验，产物类型通常固定。口诀：工厂选型号，建造者配参数。两者还能组合：工厂返回预设好的 Builder。

追问 4：C++ 里为什么原型模式常写成 clone 虚函数？

需求是"只有基类指针，也要复制出正确的派生类对象"。拷贝构造无法虚化（构造函数不能是虚函数，《C++ 篇》第 12 章），于是提供虚 clone 让各派生类调用自己的拷贝构造——多态拷贝的标准惯用法。要点：返回智能指针管理所有权、注意深拷贝正确性。

追问 5：单例为什么被称为"反模式"？你怎么看？

三宗罪：本质是全局变量，模块间隐式耦合；单测无法替换实例（依赖不可注入）；生命周期不可控（销毁顺序、多线程首次构造时机）。平衡的观点：进程级唯一且无状态/只读的基础设施（日志、配置、连接池）用单例合理；业务对象滥用单例是设计逃逸。给"用，但克制，优先注入"的答案最稳。

追问 6：new 一个对象也没什么问题，为什么要工厂？

三个触发条件：创建逻辑复杂（多依赖装配、参数解析）需要集中；使用方不应知道具体类型（按配置/环境切换实现）；创建点分散导致替换实现要全局搜 new。都不满足时直接 new 就是最好的设计——工厂解决的是"创建知识的归属"问题，没有这个问题就没有这个模式。

易错点

  • 三兄弟只会背名字，说不清"新增产品/新增产品族"两个扩展维度上各自的开闭表现。
  • 把抽象工厂讲成"工厂的工厂"之类玄学，落不到"产品族配套"这个场景词。
  • 建造者只答"链式调用好看"，漏掉参数爆炸、集中校验、不可变对象三个实际动机。
  • 原型模式与拷贝构造混为一谈，说不出"基类指针多态拷贝"这个 C++ 特有痛点。
  • 单例只会写代码，不知道它的测试与耦合问题，被"单例有什么缺点"一击即倒。
  • 所有工厂代码手写裸 new 裸指针——现代 C++ 一律 make_unique 返回智能指针（《C++ 篇》第 21 章）。

面试回答模板

如果面试官问"讲讲工厂模式家族"，可以这样回答：

三个层次按扩展维度递进。简单工厂是一个静态方法按参数分支返回不同产品，调用方与具体类解耦、创建集中，但新增产品要改工厂分支，违反开闭，适合产品少且稳定，C++ 里可以用注册表加 std::function 消灭分支。工厂方法把创建下放：抽象工厂接口一个 create，每个产品配一个工厂子类，新增产品只加一对类、老代码不动，开闭达成，工厂子类还能封装各自的装配逻辑，代价是类数量多。抽象工厂面向产品族：一个工厂负责一整套配套产品，比如暗色主题工厂造暗色按钮加暗色输入框，切换主题换工厂对象，保证族内一致不混搭；它的不对称在于新增一族容易、给族里加品类难——接口要动、所有工厂全改，所以适合族会扩张、品类稳定的场景。同属创建型的还有建造者，解决构造参数爆炸：链式按名设置可选项，build 统一做不变式校验，产物可以是不可变对象，各种 Client 配置和 SQL 拼接器都是它；原型模式靠克隆创建，C++ 落地就是虚函数 clone 委托拷贝构造，解决基类指针的多态拷贝——拷贝构造不能虚化，这是 C++ 的特有动机；单例管进程级唯一实例，Meyers 局部静态写法线程安全，但要知道它全局状态难测试的缺点，基础设施用、业务对象慎用，能依赖注入就注入。

14. 结构型设计模式详解（适配器、装饰器、代理三兄弟辨析）

题目

适配器、装饰器、代理三个模式长得很像，区别到底在哪？外观、组合、享元、桥接分别解决什么问题？

这道题在考什么

结构型模式的核心考题只有一个：适配器、装饰器、代理都是"包一层"，凭什么算三个模式？这是设计模式面试最经典的辨析题，答不好会显得所有模式都是背的。答案在意图而非形状——同样是包一层，包出来干什么完全不同。面试官用这道题测试你是"记形"还是"记神"，后者才能在真实代码里认出和用对模式。

辨析口诀先立住：适配器改接口（两边接口对不上，包一层做翻译），装饰器加功能（接口不变，动态叠 buff，可以套娃），代理控访问（接口不变，管"什么时候、能不能碰真对象"）。判断具体案例时问一句"包这层的目的是什么"，答案自然浮现。剩下四个模式各用一个生活化锚点记：外观是"一键点火"（隐藏发动机细节），组合是"文件和文件夹同接口"，享元是"棋子共享"，桥接是"两个维度独立变化就拆开组合"。

面试核心结论

三兄弟都"包一层"，辨析看意图：适配器转换接口——已有类接口不匹配目标接口，包一层做翻译，让不兼容的双方能协作（事后补救型）；装饰器增强功能——接口不变，动态叠加职责（缓冲、压缩、计日志），可以层层嵌套，替代"功能组合导致的子类爆炸"；代理控制访问——接口不变，管的是"能不能碰、什么时候碰真对象"（延迟加载、权限、远程、缓存）。一句话口诀：适配器改接口，装饰器加功能，代理控访问。其余四个各司一职：外观给复杂子系统一个简化的统一门面（点火键 vs 发动机原理）；组合用树形结构让"单个与整体"同接口（文件与文件夹）；享元共享大量细粒度对象的不变部分省内存（棋子共享、常量池）；桥接把两个独立变化的维度拆成组合关系，避免 M×N 子类爆炸。

适配器：接口翻译官

场景：系统期望 Target 接口，手里是一个接口不同但功能对路的 Legacy 类（老代码、第三方库）——改不了它，也不想改调用方。

class Target {                       // 调用方期望的接口
public:
    virtual ~Target() = default;
    virtual std::string request() = 0;
};

class LegacyLib {                    // 已有类：功能对、接口不对
public:
    std::wstring specificRequest();  // 返回宽字符
};

class Adapter : public Target {      // 对象适配器：组合被适配者
public:
    explicit Adapter(std::shared_ptr<LegacyLib> lib) : lib_(std::move(lib)) {}
    std::string request() override {
        return toUtf8(lib_->specificRequest());   // 翻译：格式/参数/调用方式转换
    }
private:
    std::shared_ptr<LegacyLib> lib_;
};
  • 两种形态：对象适配器（组合持有被适配者，推荐）与类适配器（多重继承，C++ 可写但耦合紧）。组合优于继承的又一例（第 12 章合成复用）。
  • 工程身影：数据库驱动对统一 DB 接口的适配、stack/queue 对底层容器的接口再包装（容器适配器这名字就是它，《C++ 篇》第 22 章）、新老系统迁移期的兼容层。
  • 定位记忆：事后补救——设计良好的新系统不该一开始就需要适配器。

装饰器：套娃式功能增强

场景：给对象叠加可选功能。用继承做组合会爆炸：带缓冲的流、带压缩的流、带缓冲又压缩的流……N 个功能 2^N 个子类。

class Stream {
public:
    virtual ~Stream() = default;
    virtual void write(const std::string& data) = 0;
};
class FileStream : public Stream {
public: void write(const std::string& data) override;   // 真正写文件
};

class StreamDecorator : public Stream {        // 装饰器基类：is-a Stream 且 has-a Stream
public:
    explicit StreamDecorator(std::unique_ptr<Stream> inner) : inner_(std::move(inner)) {}
protected:
    std::unique_ptr<Stream> inner_;
};
class BufferedStream : public StreamDecorator {
public:
    using StreamDecorator::StreamDecorator;
    void write(const std::string& data) override {
        buffer_ += data;
        if (buffer_.size() >= 4096) { inner_->write(buffer_); buffer_.clear(); }
    }
private:
    std::string buffer_;
};
class CompressedStream : public StreamDecorator {
public:
    using StreamDecorator::StreamDecorator;
    void write(const std::string& data) override { inner_->write(compress(data)); }
};

// 自由组合，运行期决定叠几层、什么顺序：
auto s = std::make_unique<BufferedStream>(
             std::make_unique<CompressedStream>(
                 std::make_unique<FileStream>()));
  • 结构要点：装饰器继承自同一抽象（保证可替换、可嵌套）同时组合一个同抽象成员（转发并增强）——"is-a + has-a"双关系是识别标志。
  • 收益：功能自由组合，2^N 个组合只需 N 个装饰类；运行期动态增减。
  • 工程身影：IO 流体系（Java 的 BufferedInputStream 家族是教科书案例，C++ iostream 的 streambuf 分层同思想）、HTTP 中间件按洋葱模型包 handler、给 RPC client 套重试/熔断/埋点层。

代理：访问控制的守门人

场景：不方便或不应该直接触碰真实对象——对象太贵想延迟创建、要加权限校验、对象在远端、想加缓存/日志但不动原类。

class Image {
public:
    virtual ~Image() = default;
    virtual void display() = 0;
};
class RealImage : public Image {
public:
    explicit RealImage(std::string path);      // 构造即加载大文件（昂贵）
    void display() override;
};

class LazyImageProxy : public Image {          // 虚代理：延迟加载
public:
    explicit LazyImageProxy(std::string path) : path_(std::move(path)) {}
    void display() override {
        if (!real_) real_ = std::make_unique<RealImage>(path_);  // 首次访问才创建
        real_->display();
    }
private:
    std::string path_;
    std::unique_ptr<RealImage> real_;
};
  • 代理家族按"控制什么"分类：虚代理（延迟昂贵对象）、保护代理（权限检查后放行）、远程代理（本地桩封装网络调用——RPC 框架生成的 stub 就是它）、缓存代理（结果缓存）。
  • 与《网络篇》第 24 章正反向代理神交：网络代理是"进程/服务器级"的同一思想——控制与转发访问。
  • C++ 特产：智能指针是最纯正的代理——重载 */-> 转发访问，同时加上所有权控制这一"访问策略"（《C++ 篇》第 21 章）；vector<bool> 的代理对象、写时复制句柄同属此列（第 17 章统一收编）。

三兄弟对比表（本章核心资产）

维度 适配器 装饰器 代理
意图 转换接口，让不兼容者协作 增强功能，动态叠职责 控制访问真实对象
接口是否改变 变（Legacy → Target） 不变 不变
包装对象由谁定 调用方拿着现成对象来包 调用方自由组合叠层 代理内部管理真实对象（常自己创建）
嵌套 一般一层 设计上就为多层嵌套 一般一层
时机气质 事后补救（接口不匹配才出现） 事前设计（预留扩展） 事前设计（访问策略）

判别流程：接口变没变？变了 → 适配器。没变，包一层是为了加功能还是管访问？加功能可叠加 → 装饰器；管创建时机/权限/位置 → 代理。

外观：给子系统装个总开关

场景：完成一件事要按顺序调一串子系统（下单 = 库存检查 + 锁定 + 扣款 + 生单 + 发消息），每个调用方都抄一遍这套流程。

class OrderFacade {
public:
    bool placeOrder(int userId, int skuId) {         // 一个门面方法编排全流程
        if (!inventory_.check(skuId)) return false;
        inventory_.lock(skuId);
        if (!payment_.charge(userId, price(skuId))) { inventory_.unlock(skuId); return false; }
        auto id = orderRepo_.create(userId, skuId);
        mq_.notify(id);
        return true;
    }
private:
    InventoryService inventory_; PaymentService payment_;
    OrderRepo orderRepo_; MessageQueue mq_;
};
  • 本质：封装交互流程，收窄依赖面——调用方从依赖 4 个子系统降为依赖 1 个门面，迪米特法则的直接施工（第 12 章）。
  • 子系统仍可被高级用户直接使用，门面只是"常用路径的快捷键"。微服务的聚合层/BFF、system() 之于 fork+exec+wait（第 4 章）都是门面气质。
  • 与适配器的区别：外观简化"一群接口"，不做接口转换；适配器转换"一个接口"。

组合：树形结构的统一接口

场景：文件与目录、单品与套餐、控件与容器——"个体"和"由个体组成的整体"要被一视同仁地处理。

class FsNode {
public:
    virtual ~FsNode() = default;
    virtual size_t size() const = 0;
};
class File : public FsNode {
public: size_t size() const override { return bytes_; }
private: size_t bytes_ = 0;
};
class Directory : public FsNode {
public:
    void add(std::unique_ptr<FsNode> child) { children_.push_back(std::move(child)); }
    size_t size() const override {                       // 递归聚合：整体的操作 = 部分操作之和
        size_t total = 0;
        for (auto& c : children_) total += c->size();
        return total;
    }
private:
    std::vector<std::unique_ptr<FsNode>> children_;
};
// 调用方算大小：node->size() —— 不关心手里是文件还是整棵目录树

要点：叶子与容器实现同一抽象，客户端代码消灭"是个体还是集合"的分支判断；天然递归。inode 的目录树（第 8 章）、UI 控件树、部门组织架构全是它。

享元与桥接（一段讲透）

享元（Flyweight）：海量细粒度对象大量字段重复——把内在状态（不随场景变的部分：棋子的颜色/形状/纹理）抽出共享一份，外在状态（位置等随场景变的）由使用方传入。围棋 361 子只需黑白两个享元 + 各自坐标。工程身影：字符串常量池、std::shared_ptr 共享对象、连接池/线程池的"池化"皆是共享思想（第 13 章单例是"只有一个"的极端享元）。代价：共享对象必须不可变，否则一处改动全局遭殃。

桥接（Bridge）：类有两个独立变化维度（形状 × 渲染器、消息类型 × 发送渠道），继承展开是 M×N 个子类。桥接把一个维度抽成接口用组合注入另一个维度：

class Renderer { public: virtual ~Renderer() = default; virtual void drawCircle(...) = 0; };
class OpenGLRenderer : public Renderer { /* ... */ };
class VulkanRenderer : public Renderer { /* ... */ };

class Shape {
public:
    explicit Shape(std::shared_ptr<Renderer> r) : renderer_(std::move(r)) {}
    virtual ~Shape() = default;
    virtual void draw() = 0;
protected:
    std::shared_ptr<Renderer> renderer_;   // 桥：抽象持着实现维度
};
class Circle : public Shape { public: void draw() override { renderer_->drawCircle(...); } };
// M 个形状 + N 个渲染器 = M+N 个类，组合出 M×N 种行为

一句话：桥接 = 用组合把"多维继承爆炸"拆成"维度相加"——"组合优于继承"的模式化表达。pimpl 惯用法（指针指向实现，隔离编译依赖）常被视作桥接的 C++ 亲戚（第 17 章）。

常见面试追问

追问 1：装饰器和代理代码结构几乎一样，怎么区分？

结构确实同构（实现同一接口 + 持有同一接口成员），分水岭在意图与控制权：装饰器为"加功能"，用户自由决定叠哪些层、什么顺序，功能是主角；代理为"控访问"，真实对象的创建与可达性由代理内部做主（延迟创建、拦截、转远端），用户通常感知不到包装存在。极端判据：去掉装饰器功能变弱但仍可用；去掉代理，访问策略（权限/远程）直接破坏。

追问 2：智能指针属于哪个模式？说说理由。

代理。重载 operator*/operator-> 把访问转发给真实对象，同时叠加访问控制策略：unique_ptr 控制独占所有权与自动销毁，shared_ptr 控制共享计数，weak_ptr 控制"可能失效的访问"（lock 检查即保护代理气质）。它不改变接口、不叠功能层，核心在所有权与生命周期的控制——代理三要素齐全（《C++ 篇》第 21 章）。

追问 3：外观和适配器都"包一层"，区别是什么？

对象数量与目的都不同：适配器包一个类，目的是接口转换（不匹配 → 匹配）；外观包一群子系统，目的是流程简化（多步调用 → 一键调用），接口是新定义的高层语义，不存在"转换成谁"的目标。记忆：适配器是翻译，外观是前台总机。

追问 4：什么时候该用桥接而不是继续加子类？

数一下变化维度：一个维度的扩展用继承/策略就好；两个及以上独立变化的维度（新增形状不影响渲染器、新增渲染器不影响形状）出现"每加一边就要乘一遍"的组合爆炸时上桥接。信号词是类名出现"甲乙拼接"：OpenGLCircle、VulkanSquare——名字里有两个变化轴，就该拆桥。

追问 5：享元的内在/外在状态怎么划分？错划会怎样？

内在 = 可共享的不变部分（字形的轮廓数据），外在 = 随使用场景变的部分（这个字出现在第几行第几列、什么颜色）。判据：会被并发共享的必须不可变。错把可变状态放进享元，一处修改污染所有共享者——等价于把局部变量提升成了全局变量的事故（与第 13 章单例的全局状态批判同源）。

追问 6：组合模式里"add/remove 放基类还是放容器类"有什么讲究？

透明式：add/remove 放抽象基类，客户端完全统一，但叶子被迫实现无意义操作（违反接口隔离，第 12 章）；安全式：只放 Directory，类型安全，客户端偶尔要区分叶子与容器。两难取舍没有标准答案，答出"透明性与类型安全的权衡"即达标——顺手把 ISP 拉进来论证更佳。

易错点

  • 三兄弟辨析只背"很像"，给不出"接口变不变、加功能还是控访问"的判别轴。
  • 装饰器写成纯继承（没有组合成员），退化回子类爆炸方案。
  • 把外观当"万能中间层"，什么都塞进 Facade——门面只该编排，业务下沉到子系统。
  • 桥接讲成"就是组合"——要点是"两个独立变化维度 M×N → M+N"这笔账。
  • 享元里塞了可变状态；或答不出字符串常量池、池化这类真实案例。
  • 说不出智能指针=代理、容器适配器=适配器这类 C++ 自带案例，错失把模式落地到语言的加分点（第 17 章）。

面试回答模板

如果面试官问"适配器、装饰器、代理的区别"，可以这样回答：

三个都是包一层，用两个问题区分：接口变不变？包这层是为了什么？适配器改变接口：手里有个功能对但接口不匹配的类，包一层做翻译让它适配目标接口，属于事后补救，典型是老系统兼容层和 stack、queue 这类容器适配器。装饰器不改接口，目的是动态叠加功能：装饰器继承自同一抽象同时组合一个同抽象成员，既 is-a 又 has-a，所以能层层嵌套自由组合，N 个功能 N 个装饰类就取代了两的 N 次方个子类，典型是 IO 流的缓冲压缩层和中间件洋葱模型。代理也不改接口，目的是控制访问：真实对象的创建时机、访问权限、所在位置由代理做主，分虚代理延迟加载、保护代理做鉴权、远程代理封装 RPC 桩、缓存代理，C++ 里智能指针就是最纯正的代理——转发访问加所有权控制。口诀是适配器改接口、装饰器加功能、代理控访问。剩下几个各管一摊：外观把一串子系统调用封装成一个高层门面，收窄依赖面，是迪米特法则的施工；组合用树形统一个体和整体的接口，文件系统就是它；享元抽出不变的内在状态全局共享，坐标这类外在状态调用时传入，字符串常量池和池化都是这个思想；桥接处理两个独立变化维度，把继承的 M 乘 N 拆成组合的 M 加 N，pimpl 是它的 C++ 亲戚。

15. 行为型设计模式详解（观察者、策略、模板方法与速览组）

题目

观察者模式和发布订阅是一回事吗？策略模式怎么消灭 if-else？模板方法和策略怎么选？职责链、状态、命令这些模式分别解决什么？

这道题在考什么

行为型模式数量最多（11 种），但面试火力集中在观察者和策略两个上，这道题的问法也暴露了考点所在："观察者和发布订阅是一回事吗"考概念辨析（差一个中间人 Broker），"策略怎么消灭 if-else"考工程落地（这是代码评审里出现频率最高的重构手法），"模板方法和策略怎么选"考设计权衡（本质是继承 vs 组合的选择）。都是实战中真会遇到的决策。

主力模式各抓一个灵魂问题：观察者——"状态变了谁需要知道？"让通知自动化、双方解耦；策略——"这一族算法会换来换去吗？"会换就封装成可注入的类；模板方法——"流程固定、步骤可变吗？"是就父类定骨架、子类填空。速览组（职责链、状态、命令）各记一句人话定位即可：审批流用职责链、状态机替代满屏 switch 用状态模式、要撤销重放就把请求封装成命令对象。面试深讲前三个，速览组点到为止，火力分配本身就是答题策略。

面试核心结论

行为型管对象协作。四大主力：观察者——一对多依赖，被观察者状态变化自动通知所有订阅者，双方只依赖抽象接口；它与发布订阅的区别在"有没有中间人"——观察者是主题直连观察者（进程内、同步为主），发布订阅加了 Broker（跨进程、异步、双方彻底互不相识）。策略——把一族可互换算法各自封装成类，运行期注入选用，配合工厂消灭 if-else，开闭原则的头号施工队。模板方法——父类定死算法骨架，可变步骤留虚函数给子类填空，"好莱坞原则：别调用我们，我们会调用你"；与策略的取舍即继承与组合的取舍。职责链——请求沿处理器链传递，谁能处理谁接手（审批流、中间件、异常处理）。速览组一句话各就位：状态——状态变了行为跟着变，用状态类替代满屏 switch；命令——把请求封装成对象，支持排队、撤销、重放；迭代器与备忘录等在 C++/工程中已内建化（第 17 章收编）。

观察者模式

场景：订单支付成功后要通知库存、积分、消息推送……直接在订单代码里逐个调用，每加一个下游就改一次订单（违开闭），订单模块被迫认识所有下游。

class OrderObserver {                        // 抽象观察者
public:
    virtual ~OrderObserver() = default;
    virtual void onPaid(int orderId) = 0;
};

class OrderSubject {                         // 被观察者（主题）
public:
    void subscribe(std::shared_ptr<OrderObserver> ob) { obs_.push_back(std::move(ob)); }
    void notifyPaid(int orderId) {
        for (auto& w : obs_)
            if (auto ob = w.lock()) ob->onPaid(orderId);   // weak_ptr 防悬垂（见追问）
    }
private:
    std::vector<std::weak_ptr<OrderObserver>> obs_;
};

class InventoryService : public OrderObserver {
public: void onPaid(int orderId) override { /* 扣减库存 */ }
};
class PointsService : public OrderObserver {
public: void onPaid(int orderId) override { /* 发积分 */ }
};
// 新增下游 = 写一个新观察者并 subscribe，订单代码零改动
  • 关系倒转是精髓：从"订单认识所有下游"变成"下游自己来登记"——依赖方向反转，主题只依赖抽象观察者接口。
  • C++ 现代形态：观察者接口常退化为 std::function 回调列表（信号槽，Qt 的 signal/slot、boost::signals2），第 17 章统一收编。

观察者 vs 发布订阅（高频辨析）：

维度 观察者 发布订阅
结构 主题直接持有观察者列表 中间加 Broker/事件总线，双方只认它
耦合 松耦合（依赖抽象接口） 零耦合（互相完全不知道存在）
范围与时序 进程内、通常同步调用 常跨进程、异步投递（MQ）
例子 GUI 事件监听、信号槽 Kafka/RocketMQ、Redis pub/sub

一句话：发布订阅 = 观察者 + 中间人，中间人带来异步、削峰、持久化，也带来运维成本。

策略模式

场景：calcPrice() 里按会员等级 if-else 五种折扣算法，每加一种改一次、每次全量回归。

class DiscountStrategy {
public:
    virtual ~DiscountStrategy() = default;
    virtual double apply(double price) const = 0;
};
class VipDiscount : public DiscountStrategy {
public: double apply(double p) const override { return p * 0.8; }
};
class NewUserDiscount : public DiscountStrategy {
public: double apply(double p) const override { return std::max(p - 30, 0.0); }
};

class PriceCalculator {                          // 上下文：持有并使用策略
public:
    explicit PriceCalculator(std::unique_ptr<DiscountStrategy> s) : strategy_(std::move(s)) {}
    double calc(double price) const { return strategy_->apply(price); }
private:
    std::unique_ptr<DiscountStrategy> strategy_;
};
// 配合工厂/注册表按用户类型取策略（第 13 章）：if-else 集中成一张映射表
  • 消灭 if-else 的完整链路：策略封装算法族 + 工厂（注册表）负责选取——分支从业务逻辑里消失，收敛到一处注册配置；新增算法 = 新增类 + 注册一行。
  • 诚实的另一半：类数量增加、逻辑分散——两三个稳定分支不值得上策略，分支多、变化频、组合复杂才是它的主场（呼应第 12 章过度设计）。
  • C++ 双形态：运行期策略如上（虚函数）；编译期策略用模板参数注入，零虚调用开销——STL 的比较器、分配器就是编译期策略（第 17 章）。

模板方法模式

场景：多种数据导出（Excel/CSV/PDF）流程一致——取数、转换、渲染、上传，只有"渲染"一步不同；每个导出类各抄一遍全流程。

class Exporter {
public:
    virtual ~Exporter() = default;
    void run() {                          // 模板方法：骨架定死，非虚
        auto data = fetch();
        auto rows = transform(data);
        auto file = render(rows);         // 可变步骤：延迟到子类
        upload(file);
    }
protected:
    virtual File render(const Rows& rows) = 0;        // 必须填的空
    virtual Rows transform(const Data& d) { return defaultTransform(d); }  // 钩子：可选覆盖
private:
    Data fetch();                          // 公共步骤：父类实现
    void upload(const File& f);
};
class ExcelExporter : public Exporter {
protected: File render(const Rows& rows) override;    // 只写差异
};
  • 关键设计：模板方法本身声明为非虚（骨架不许子类篡改），可变步骤纯虚（必须实现）或带默认实现的"钩子"（可选定制）。
  • "好莱坞原则"：控制流在父类手里，子类被回调——框架设计的基本气质（框架调你，你不调框架）。
  • 模板方法 vs 策略（必考取舍）：都在隔离变化，路径不同——模板方法用继承，复用整套骨架、改一小步，编译期定死；策略用组合，整个算法可整体替换、运行期切换、可独立测试。变化是"流程中一小步"选模板方法，变化是"整个算法"或需运行时切换选策略；吃不准时按"组合优于继承"偏向策略。C++ 的 CRTP 能做零开销的编译期模板方法（第 17 章）。

职责链模式

场景：请求要过一串检查/处理环节，且环节要能增删换序——审批流（组长→经理→总监按额度接手）、Web 中间件（鉴权→限流→日志）、GUI 事件冒泡。

class Handler {
public:
    virtual ~Handler() = default;
    void setNext(std::shared_ptr<Handler> next) { next_ = std::move(next); }
    void handle(Request& req) {
        if (!process(req) && next_) next_->handle(req);   // 处理不了交给下家
    }
protected:
    virtual bool process(Request& req) = 0;               // 返回 true 表示已处理终止
private:
    std::shared_ptr<Handler> next_;
};
  • 两种风味：拦截器式（每环都处理并放行，中间件洋葱模型）与接力式（首个能处理者终止链，异常 catch 匹配、审批）。
  • 收益：发送方只认链头，环节的增删排序变成配置问题；单环节可独立测试。
  • 注意链尾兜底（没人处理时的默认行为）与链过长的调试成本。

速览组：状态、命令、备忘录、访问者

状态模式：对象行为随内部状态改变——订单（待支付/已支付/已发货/已完成）每个动作都要 switch 状态。把每个状态封装成类，行为分派给当前状态对象，状态迁移逻辑内聚到状态类中：新增状态不再翻遍所有 switch。与策略结构同构，区别在意图：策略由外部选择且各策略互不知晓；状态由内部流转且状态间知道彼此（A 状态处理完把上下文切到 B）。游戏角色状态机、TCP 状态机（《网络篇》第 8 章）、订单流转都是它的地盘。

命令模式：把"一个请求"封装成对象（含动作与参数），调用者只管执行 command。收益全在"请求成了一等公民"：可排队（任务队列）、可撤销（undo 栈存反向命令）、可重放（redo/操作日志）、可远程序列化。编辑器的 undo/redo、事务日志、游戏按键映射（换绑=换命令对象）。C++ 里 std::function + lambda 就是轻量命令（第 17 章），提交线程池的任务对象亦然（《C++ 篇》第 25 章线程池）。

备忘录：不破坏封装地捕获对象内部状态存档，日后恢复——存档/快照/undo 的另一条实现路（与命令的反向操作互为替代：状态小存快照，状态大存操作）。

访问者：在不修改元素类的前提下给一族元素新增操作，双分派实现；AST 遍历（编译器、序列化）是主场，结构稳定、操作频增才用——反之元素类频增时它最脆弱。了解定位即可。

（迭代器、中介者、解释器：迭代器已内建为语言/库设施（第 17 章）；中介者=把网状对象通信收敛到中心协调者（聊天室服务器、机场塔台），与外观的区别是双向协调而非单向简化；解释器面试几乎不考，掠过。）

常见面试追问

追问 1：观察者模式的通知是同步的，会有什么问题？怎么演进？

同步逐个回调意味着：一个观察者卡住拖死主题（订单线程被积分服务的慢调用拖住）、一个抛异常可能中断后续通知、还有重入风险（回调里又触发 notify）。演进路径：通知只投任务进队列由线程池异步消费（《C++ 篇》第 25 章）→ 跨进程规模上 MQ，升级成发布订阅——回答画出"同步观察者 → 异步观察者 → 消息队列"的演进线即高分。

追问 2：C++ 观察者怎么防"观察者已销毁还被通知"？

裸指针列表会悬垂。标准解法：主题存 weak_ptr，通知时 lock() 成功才回调、失败顺手清理（上文代码）；或者订阅返回 RAII 的 connection 对象，析构自动退订（boost::signals2 的 scoped_connection）。本质是观察者生命周期与订阅关系解耦（智能指针语义见《C++ 篇》第 21 章）。

追问 3：策略模式消灭了 if-else，但选择策略时不还是要分支吗？

分支没有消失，它被收敛并降级了：从散落在业务流程里的逻辑分支，变成一处"key → 策略"的注册表查找（map + 工厂，第 13 章）。收益在于新增策略不再触碰业务代码、注册即生效，且这张表可以来自配置中心实现热切换。答出"分支收敛到配置化的一点"即说到本质。

追问 4：模板方法的钩子（hook）是什么？

带默认实现的虚函数，子类可选覆盖：与纯虚的"必须填空"相对，钩子是"默认给你，不满意再改"，还常用作流程开关（virtual bool needAudit() { return false; } 让子类决定是否启用某步骤）。骨架非虚 + 纯虚步骤 + 钩子三件套构成完整的模板方法。

追问 5：状态模式和一个 switch 状态机怎么选？

状态少（三四个）且迁移简单：switch/查表清晰紧凑，别上模式。状态多、每状态行为丰富、迁移规则复杂多变：状态类让"新增一个状态"从全局 switch 修改收敛为新增一个类。中间形态是表驱动状态机（迁移表 + 回调），游戏与协议栈常用——三档方案按复杂度选，答出光谱而非二选一。

追问 6：职责链会不会出现请求没人处理？怎么办？

接力式链存在漏接可能。工程守则：链尾挂兜底处理器（默认策略/记录告警/抛明确异常），或构建链时静态校验覆盖完整性。中间件式则相反要保证"每环必调 next 或明确终止"，漏调 next 导致请求悬挂是真实事故——两种风味的失败模式刚好相反，说清这点显出实战经验。

易错点

  • 观察者与发布订阅混为一谈——差一个 Broker，耦合度、同步性、跨进程能力全不同。
  • 观察者列表存裸指针/shared_ptr：前者悬垂，后者循环引用延长生命周期——weak_ptr 是标准答案。
  • 策略模式答"消灭了 if-else"就停，被追问"选择策略的分支去哪了"接不上。
  • 模板方法把骨架也写成 virtual，子类可篡改流程，模式意义崩塌。
  • 策略与状态因结构同构而混淆——记"外部选择 vs 内部流转"。
  • 职责链忘记兜底，或中间件忘调 next。
  • 全程只背 GoF 结构，举不出 MQ、中间件、undo 栈这类工程落点。

面试回答模板

如果面试官问"讲讲你常用的行为型模式"，可以这样回答：

最常用三个。观察者解决一对多通知：被观察者维护抽象观察者列表，状态变化时遍历通知，新增下游只需注册零改动，C++ 里主题存 weak_ptr 防观察者销毁后悬垂，现代写法常退化成 std::function 回调列表；它和发布订阅的区别是有没有中间人——加了 Broker 就是发布订阅，双方彻底解耦、可异步跨进程，Kafka 就是那条路，同步观察者拖死主题时就该沿"异步化、上 MQ"演进。策略解决同类算法的分支爆炸：算法族各自封装成类实现同一接口，上下文组合持有，配合注册表工厂把 if-else 收敛成一张 key 到策略的映射，新增算法加类加注册各一行，这是开闭原则的头号落地；C++ 还能用模板参数做编译期策略零开销，STL 的比较器就是。模板方法解决流程固定、步骤可变：父类非虚的模板方法定死骨架，可变步骤留纯虚让子类填空，可选步骤给带默认实现的钩子，控制流在父类——好莱坞原则，框架调你；它和策略的取舍就是继承和组合的取舍：改流程中一小步用模板方法，整个算法可替换或要运行时切换用策略。再补三个一句话：职责链让请求沿处理器链传递，审批流和中间件洋葱模型，注意链尾兜底；状态模式把 switch 状态机拆成状态类，行为随状态内部流转，和策略同构但一个外部选择一个内部迁移；命令把请求封装成对象，获得排队、撤销、重放能力，编辑器 undo 和线程池任务都是它，C++ 里 lambda 加 std::function 就是轻量命令。

16. 并发与架构模式详解（Reactor、Proactor、生产者消费者与池化）

题目

Reactor 模式是什么？单 Reactor 单线程、单 Reactor 多线程、主从 Reactor 有什么区别，Redis 和 Nginx 分别是哪种？Proactor 和 Reactor 的本质区别是什么？生产者消费者和池化模式在架构里扮演什么角色？

这道题在考什么

这一章从 GoF 经典模式跨到并发与网络架构模式，是设计模式部分含金量最高的一章——Reactor 三档演进是 C++ 后端/基础架构岗的必考题，因为你叫得出名字的高性能组件（Redis、Nginx、Netty、muduo）全是它的某档实现。面试官问"Redis 是哪种 Reactor"，考的是你能不能把抽象模式和真实系统对上号，这比背模式定义硬核得多。

三档演进沿"瓶颈在哪"推进：单 Reactor 单线程——一个事件循环全包，简单无锁，但一核封顶、业务一慢全场卡 → 把业务扔给线程池（单 Reactor 多线程），算力解决了，但所有 IO 事件还挤一个循环 → 连 IO 也分摊（主从 Reactor：主管 accept、从管各自一批连接的读写）。Proactor 与 Reactor 的本质区别一句话：Reactor 通知你"可以读了"（同步非阻塞，自己动手），Proactor 通知你"已经读完了"（异步 IO，内核代劳）。生产者消费者和池化是贯穿所有架构的两个原子构件，各记"解耦速率差"和"复用摊销成本"即可。

面试核心结论

Reactor 是"事件驱动 + IO 多路复用"的网络编程模式：一个事件循环用 epoll 等待就绪事件，按事件类型分发给对应处理器——同步非阻塞，就绪后的读写仍由用户线程自己做（IO 模型基础详见《网络篇》第 28 章）。三档演进：单 Reactor 单线程——一个线程包办 accept、读写、业务，无锁简单但一核封顶、业务一慢全场卡（Redis 6.0 前）；单 Reactor 多线程——事件循环只管 IO，业务丢线程池，算力上多核，但 accept 和所有 IO 事件仍挤在一个 Reactor 上；主从 Reactor——主 Reactor 专职 accept，新连接分发给多个从 Reactor，每个从 Reactor 独占线程管一批连接的 IO，业务再交线程池（Netty、muduo 的"one loop per thread"，Nginx 是多进程版变体）。Proactor 是异步 IO 版本：应用发起异步操作即返回，内核完成"等待 + 数据拷贝"后回调通知——Reactor 通知"可以读了"，Proactor 通知"已经读完了"，代表是 Windows IOCP 与 io_uring。生产者消费者用阻塞队列解耦生产与消费速率（实现详见《C++ 篇》第 25 章），是异步化与削峰的原子构件；池化（线程池/连接池/对象池）用复用摊销昂贵资源的创建成本，二者是几乎所有服务端架构的地基。

Reactor：事件驱动的骨架

朴素的"每连接一线程"在万级连接下线程内存与切换开销爆炸（C10K，《网络篇》第 12、28 章）。Reactor 的答案：

事件循环（Event Loop）:
    while (true) {
        events = epoll_wait();            // ① 等待：一个线程盯所有 fd
        for (e : events) {
            if (e 是新连接)  acceptor.handle();    // ② 分发（demultiplex & dispatch）
            else if (e 可读) handler.onRead();     //    就绪后的 read/decode/compute/
            else if (e 可写) handler.onWrite();    //    encode/write 由处理器完成
        }
    }

构成三角色：Reactor（事件循环与分发）、Acceptor（专处理新连接）、Handler（每连接的读写与业务）。所有 fd 必须非阻塞（ET/LT 与非阻塞的因果详见《网络篇》第 28 章）。

单 Reactor 单线程

一个线程干完等待、分发、读写、业务计算：

  • 优点：零锁零切换，逻辑天然串行原子，实现最简单。
  • 命门：单核封顶；任何一步慢（重业务、大 key）全体连接排队。
  • 代表：Redis。适用判据：业务处理足够快、逻辑要求强顺序。

单 Reactor 多线程

事件循环只负责 IO（读出完整请求、写回响应），解码后的业务计算投递给工作线程池：

  • 收益：业务算力横向扩展到多核，慢业务不再阻塞 IO 循环。
  • 残余瓶颈：一个 Reactor 线程承担全部连接的 accept + 读写，海量连接高频事件时它先饱和；业务结果写回要跨线程交还 IO 线程（队列 + wakeup），引入一次调度。
  • 新增代价：业务并发执行，共享状态回到"要加锁"的世界（《C++ 篇》第 25 章）。

主从 Reactor 多线程（工业主流）

主 Reactor（1 个线程）:  epoll 只盯 listen fd → accept 新连接
        │ 轮询/负载均衡分发 connfd
从 Reactor × N（每个独占一个线程，one loop per thread）:
        各自 epoll 管一批连接的全部读写事件（一条连接终身固定属于一个 loop）
        （可选）解码后把重业务再投工作线程池，轻业务就地做
  • 分工彻底：accept 洪峰不干扰已建连接的 IO；连接均摊到 N 个 loop，多核吃满。
  • "一条连接固定一个 loop"是精髓：连接的所有事件在同一线程串行处理，连接内无锁、缓存友好，跨连接才考虑并发——把并发粒度从"操作"提升到"连接"。
  • 代表：Netty（bossGroup/workerGroup）、muduo（one loop per thread + threadpool）；Nginx 是多进程变体——每个 worker 进程一个事件循环，SO_REUSEPORT/accept_mutex 分摊 accept（惊群问题的工程处理）。

三档对比表：

维度 单 R 单线程 单 R 多线程 主从 R 多线程
IO 并行度 1 1（仅业务并行） N 个 loop
业务并行度 无 线程池 线程池/loop 内
锁需求 无 业务层有 连接内无、跨连接有
瓶颈 单核+慢业务 单 Reactor 的 IO 基本均衡
代表 Redis 早期简单服务 Netty/muduo/Nginx(多进程)

Proactor：异步 IO 的对偶

Reactor 与 Proactor 的分界线就是同步 IO 与异步 IO 的分界线（《网络篇》第 28 章的两阶段模型）：

Reactor（同步非阻塞）:
    内核通知"fd 可读了" → 用户线程自己调 read 把数据从内核拷到用户缓冲 → 处理
Proactor（异步）:
    用户发起 async_read(buf) 立即返回
    → 内核完成 等待 + 拷贝到用户 buf 全过程 → 完成事件回调用户 → 直接处理数据
  • 记忆句：Reactor 通知"你可以做了"，Proactor 通知"我帮你做完了"。
  • 落地：Windows IOCP 是正统 Proactor；Linux 老 aio 残废，io_uring 补齐后 Proactor 模式在 Linux 真正可用；Boost.Asio 提供 Proactor 风格接口（Linux 上曾用 epoll 模拟）。
  • 取舍：Proactor 省掉用户态的读写调用与就绪竞争，吞吐上限更高；但编程模型（缓冲区生命周期由内核持有）更绕、可移植性历史包袱重。Linux 生态主流仍是 Reactor，io_uring 正在改变格局——答出这个现状即显跟进。

生产者消费者：异步解耦的原子构件

阻塞队列连接生产与消费两侧（条件变量实现、虚假唤醒等细节在《C++ 篇》第 25 章），架构视角的三重价值：

  1. 解耦：两侧只依赖队列接口，各自独立伸缩替换。
  2. 削峰：突发流量先进队列排队，消费侧按稳定速率处理——队列是缓冲垫。
  3. 速率匹配与背压：有界队列满时阻塞或拒绝生产者，把压力信号传回上游——无界队列 = 把 OOM 延后，生产纪律是必用有界并设计拒绝策略。

它无处不在：Reactor 各档之间传任务的通道、线程池的任务队列、日志异步刷盘、上面主从 Reactor 图里"投递业务到线程池"那条箭头，全是生产者消费者。

池化模式：复用昂贵资源

创建成本高的资源（线程、TCP+TLS 连接、大块内存、复杂对象）预先建好一批循环复用：

  • 线程池：省创建销毁与调度冲击，参数（核心数、队列长、拒绝策略）与实现见《C++ 篇》第 25 章；IO 密集与 CPU 密集的线程数经验（N 核：CPU 密集 ≈ N，IO 密集 ≈ N×(1+等待/计算)）。
  • 连接池：数据库/Redis/HTTP 连接握手贵（TCP+TLS 多个 RTT，《网络篇》第 8、20 章；连接初始化也有认证与内存开销），池化后取用归还，配最小/最大连接数、空闲回收、借出超时与健康探活。
  • 对象池/内存池：高频小对象绕过分配器；游戏帧内对象、网络缓冲块常用。
  • 共同要点：池是有状态的共享资源——归还时必须重置状态（连接残留事务、对象脏字段是经典事故）、防泄漏（借出不还，RAII 包装借据）、容量监控（池耗尽的排队与拒绝）。

一句话把三个模式串起来：Reactor 决定"事件怎么进来"，生产者消费者决定"任务怎么流转"，池化决定"资源怎么复用"——三者拼出一个典型高并发服务的骨架。

常见面试追问

追问 1：为什么 Redis 用单 Reactor 单线程也这么快，你的业务服务却不能抄？

成立前提是"处理一步足够快"：Redis 命令是纯内存操作，微秒级完成，单线程省锁省切换反而最优。一般业务服务要查库调 RPC，毫秒到百毫秒级，单线程会让所有连接陪一个慢请求排队——所以业务服务至少单 Reactor 多线程，长连接海量并发上主从。答题先给前提再给结论，避免"单线程崇拜"。

追问 2：主从 Reactor 里，"一条连接固定属于一个从 loop"有什么好处？坏处？

好处：该连接的读、解码、业务（轻量时）、写全在一个线程串行——连接内状态零锁，时序天然保证，CPU 缓存友好；这是 muduo/Netty 的核心设计契约。坏处：单条重连接可能压偏一个 loop（负载不均），跨连接交互（聊天室广播）要跨线程投递任务（eventfd/wakeup 队列）。缓解：连接分发时按负载挑 loop、广播走每个 loop 自己的任务队列。

追问 3：Reactor 模式下业务算完了，能直接在工作线程里 write 回 socket 吗？

不能直接写。socket 的事件与缓冲状态归属它的 IO 线程管理，跨线程写会与 IO 线程的读写并发冲突（发送缓冲区竞争、EPOLLOUT 注册竞态）。正确姿势：工作线程把响应投回该连接所属 loop 的任务队列，用 eventfd/管道唤醒 epoll_wait，由 loop 线程执行 write——"数据跨线程，操作不跨线程"。这是 Reactor 工程实现的高频深挖点。

追问 4：Proactor 为什么在 Linux 上长期不流行？io_uring 改变了什么？

Linux 老 aio 只支持 O_DIRECT 文件、网络支持残缺，"异步"常退化为线程池模拟，图有其表。io_uring 用提交/完成双环形队列提供了真异步：网络文件统一、批量提交收割、系统调用大幅减少（《网络篇》第 28 章）。这让 Proactor 在 Linux 首次有了正统地基，新一代高性能框架（如基于 io_uring 的存储与代理）开始转向；存量生态与人才惯性仍在 Reactor。

追问 5：连接池大小怎么定？越大越好吗？

不是。数据库连接池超过 DB 的最优并发（约核数的小倍数）后，只是把排队从应用侧挪到 DB 侧还加剧上下文切换与锁竞争。经验起点：连接数 ≈ DB 核数 × 2 上下再按压测调；应用侧多实例时要算总和。配套必答：借出超时与健康检查，防"池被挂死连接占满"。

追问 6：有界队列满了，生产者应该怎么办？

拒绝策略菜单：阻塞等待（背压传导，上游自然减速）、快速失败返回错误（配限流语义）、丢弃最老/最新（日志类可容忍）、降级旁路（写本地磁盘稍后补偿）。选择依据是业务对"延迟 vs 丢失"的容忍度；唯一错误答案是无界队列——那等于选择了 OOM。（线程池拒绝策略同款逻辑，《C++ 篇》第 25 章。）

易错点

  • 把 Reactor 说成"异步 IO"。它是同步非阻塞：就绪通知后读写仍由用户线程完成；异步的是 Proactor。
  • 三档 Reactor 只会背名字，说不出各档的瓶颈与升级动机（慢业务→加线程池；accept/IO 挤兑→主从分工）。
  • 不知道"一条连接固定一个 loop"的契约与跨线程写回的正确姿势——两问就穿。
  • 把 Nginx 说成多线程主从 Reactor（它是多进程 worker 各自事件循环），把 Redis 6.0 说成多线程执行命令。
  • 生产者消费者用无界队列；池化资源归还不重置状态、借出无超时。
  • 只背模式不落框架名（Netty/muduo/Nginx/Redis/IOCP/io_uring），工程感全无。

面试回答模板

如果面试官问"讲讲 Reactor 模式"，可以这样回答：

Reactor 是事件驱动加 IO 多路复用的网络编程骨架：事件循环用 epoll 等待一批 fd 的就绪事件，按类型分发给 Acceptor 或各连接的 Handler，就绪后的 read、业务、write 由用户线程自己做，所以它是同步非阻塞。三档演进按瓶颈推：单 Reactor 单线程一个线程包办所有事，零锁零切换，Redis 命令是微秒级内存操作所以用它最优，但业务一慢全场排队、单核封顶；于是单 Reactor 多线程把业务丢给线程池，IO 循环只管收发，代价是业务并发要加锁、且所有连接的 IO 还挤在一个 Reactor 上；最终主从 Reactor：主 Reactor 专职 accept，新连接分给 N 个从 Reactor，每个从 loop 独占线程管一批连接、一条连接终身固定一个 loop——连接内串行无锁、缓存友好，重业务再投线程池，Netty 的 boss/worker 和 muduo 的 one loop per thread 就是它，Nginx 是多进程版变体。工程细节两个：工作线程不能直接写 socket，要把响应投回连接所属 loop 的任务队列并用 eventfd 唤醒，由 loop 线程执行写；连接分发要考虑负载均衡。Proactor 是异步版对偶：应用发起 async_read 即返回，内核连等待带拷贝全做完再回调——Reactor 通知你可以读了，Proactor 通知已经读完了，代表是 Windows IOCP，Linux 靠 io_uring 才算真正落地。底下再垫两块地基：生产者消费者阻塞队列做解耦削峰和背压，必须有界并定好拒绝策略；线程池连接池的池化复用摊销创建成本，注意归还重置、借出超时和容量监控。

题目

C++ 标准库和惯用法里藏着哪些设计模式？RAII、迭代器、std::function、traits、CRTP、pimpl 分别对应什么模式思想？"C++ 把一部分设计模式编译期化"怎么理解？

这道题在考什么

设计模式部分的收官之章，也是 C++ 岗位的独特考点：把 GoF 模式对号入座到你天天在用的标准库设施。面试官问"STL 里有哪些设计模式"，是在检验两件事：你对模式的理解是否深到能在"不叫这个名字"的代码里认出它；你对 C++ 的理解是否深到能看出它与 Java 系的风格分野——很多运行期模式被 C++ 用模板做成了编译期版本。这道题答好了，前面五章的所有内容都升值。

学习方法就是做连线题并想通"为什么"：智能指针 = 代理（转发访问 + 控制生命周期），iterator = 迭代器模式内建化，比较器/哈希/分配器 = 编译期策略（模板参数注入算法，零虚函数开销），CRTP = 编译期模板方法，pimpl = 桥接的编译隔离版。最后收拢到核心论点——虚函数实现的运行期灵活性，C++ 常用模板换成编译期决策，灵活性换零开销。面试抛出这个论点再举两三个例子，是能让面试官眼前一亮的收束方式。

面试核心结论

把 GoF 模式对号入座到手边的 C++ 设施，是把"背模式"升华成"懂设计"的捷径：智能指针 = 代理模式（转发访问 + 所有权控制）；RAII = 资源管理的模式化身，逼近"作用域即事务"；iterator = 迭代器模式的语言级内建，统一容器遍历接口，算法与容器经由它解耦；std::function + lambda = 命令/回调的现代形态，观察者退化为回调列表；STL 的比较器、哈希、分配器 = 编译期策略模式（模板参数注入算法，零虚函数开销）；std::sort 内部小区间切插入 = 策略切换，integral_constant/tag dispatch 与 traits = 编译期的"按类型分派"；CRTP = 编译期模板方法/静态多态；pimpl = 桥接的编译隔离版；stack/queue = 适配器；string 的 SSO 与曾经的 COW、shared_ptr 控制块 = 享元与代理的组合拳。核心论点：虚函数实现的运行期模式，C++ 常用模板把决策提前到编译期——灵活性换零开销，这是 C++ 设计风格与 Java 系最大的分野。

代理模式：智能指针与各类句柄

unique_ptr/shared_ptr 是教科书级代理（第 14 章追问已论证）：

  • 重载 operator*/operator-> 转发访问，接口对真实对象透明；
  • 叠加访问策略：unique 独占并自动销毁、shared 引用计数、weak 的 lock() 是"访问前检查有效性"的保护代理（《C++ 篇》第 21 章）。
  • 同族案例：vector<bool>::reference 代理位访问（《C++ 篇》第 22 章的坑，本质是代理对象冒充引用）；写时复制句柄（读共享写复制，老 string 的 COW，《C++ 篇》第 23 章）。

RAII：无名却最重要的"模式"

GoF 没给它名字，它却是 C++ 设计的第一惯用法（完整机制见《C++ 篇》第 20 章）：构造获取、析构释放，把资源生命周期绑定到作用域。模式视角的解读：

  • 它把"资源管理"这个横切关注点对象化——lock_guard 之于锁、unique_ptr 之于内存、fstream 之于文件，同一形状反复出现，这正是"模式"的定义；
  • 对比其他语言的 finally/defer：RAII 把清理逻辑封装进类型一次编写处处生效，其他方案在每个使用点手写；
  • 观察者退订的 scoped_connection（第 15 章）、池化借据的自动归还（第 16 章）都靠 RAII 收尾——它是别的模式的安全网。

迭代器模式：STL 的立国之本

GoF 迭代器的诉求"不暴露内部表示地顺序访问聚合元素"，STL 给出超越原版的实现：

  • begin()/end() + ++/* 统一了数组、链表、红黑树、哈希表的遍历（各容器迭代器类别见《C++ 篇》第 22 章）；
  • 真正的飞跃是算法与容器的解耦：sort/find 只依赖迭代器概念，M 个算法 × N 个容器 = M+N 份代码——这笔账与桥接模式（第 14 章）如出一辙；
  • 迭代器同时是适配器的沃土：reverse_iterator 反向适配、back_insert_iterator 把"赋值"适配成 push_back、流迭代器把 IO 适配成序列。

命令与观察者：std::function 的天下

std::function + lambda 让"请求对象化"从仪式变成一行（可调用对象体系见《C++ 篇》第 16 章）：

// 命令模式现代形态：任务即命令对象，支持排队（线程池）与延迟执行
threadPool.submit([order] { settle(order); });

// 观察者现代形态：回调列表替代观察者接口
class Button {
public:
    void onClick(std::function<void()> cb) { cbs_.push_back(std::move(cb)); }
    void click() { for (auto& cb : cbs_) cb(); }
private:
    std::vector<std::function<void()>> cbs_;
};
  • GoF 时代一个命令一个类、一个观察者一个接口实现；闭包捕获上下文后，类被 lambda 吞掉了——模式没消失，仪式感消失了。撤销/重放需要显式结构时，命令类仍值得写（第 15 章）。
  • Qt 信号槽、boost::signals2 是带连接管理（RAII 退订、线程安全）的工业级观察者。

策略模式的编译期形态：模板参数注入

运行期策略用虚函数（第 15 章）；STL 全面选择了编译期策略：

std::sort(v.begin(), v.end(), std::greater<int>{});   // 比较器 = 策略对象
std::unordered_map<Key, V, MyHash, MyEq> m;           // 哈希/相等 = 类型级策略
std::vector<T, PoolAllocator<T>> pool_vec;            // 分配器 = 内存策略
  • 策略以模板参数注入：编译器为每种策略实例化专属代码，比较器调用可内联——零虚调用开销，代价是策略在编译期定死、二进制膨胀（模板代价见《C++ 篇》第 24 章）。
  • unique_ptr<T, Deleter> 的删除器同理，且靠 EBO 让无状态策略零空间占用（《C++ 篇》第 7 章空基类优化的实战）。
  • traits + tag dispatch（iterator_category 按标签选重载、if constexpr 按类型走分支）是"编译期的按类型分派"——运行期多态干的事，重载决议和模板特化在编译期干完（《C++ 篇》第 24 章 SFINAE/concepts 一脉）。

CRTP：编译期的模板方法与静态多态

template <typename Derived>
class ExporterBase {
public:
    void run() {                                     // 骨架：编译期模板方法
        fetch();
        static_cast<Derived*>(this)->render();       // "虚"步骤：静态分派到派生类
        upload();
    }
    void render() { /* 默认实现 = 钩子 */ }
private:
    void fetch(); void upload();
};
class ExcelExporter : public ExporterBase<ExcelExporter> {
public: void render();                               // 填空，无虚函数
};
  • 与第 15 章模板方法逐点对应：骨架、填空、钩子俱全，分派发生在编译期——无 vptr、可内联（CRTP 机制见《C++ 篇》第 24 章）。
  • 适用分界：类型集合编译期已知、追求零开销 → CRTP；需要运行期异构容器（基类指针数组）→ 虚函数。enable_shared_from_this 就是标准库里的 CRTP 实例（《C++ 篇》第 21 章）。

pimpl：桥接的编译隔离版

// widget.h —— 头文件只见指针，成员全藏进实现文件
class Widget {
public:
    Widget(); ~Widget();                 // 析构必须在 .cpp 定义（unique_ptr 完整类型要求）
    void doWork();
private:
    struct Impl;                         // 前向声明
    std::unique_ptr<Impl> pimpl_;
};
  • 结构与桥接同构（抽象持指针指向实现），动机偏工程：头文件不再暴露成员 → 私有成员变更不触发下游重编译（编译防火墙，编译依赖见《C++ 篇》第 2 章）、隐藏第三方依赖、稳定 ABI。
  • 代价：一次堆分配 + 一层间接访问；析构/移动的定义位置有讲究（Impl 完整类型可见处）。

常见面试追问

追问 1："C++ 把设计模式编译期化"到底指什么？收益和代价是什么？

GoF 模式的可变点大多用虚函数在运行期绑定；C++ 用模板把可变点提前到编译期绑定：策略经模板参数、模板方法经 CRTP、分派经重载决议与特化。收益：内联与零虚调用开销、类型错误提前暴露；代价：灵活性定格在编译期（不能运行时切换）、代码膨胀、报错与编译时间。选择的轴就是"变化发生在何时"——运行时变用虚函数，编译时定用模板。

追问 2：迭代器模式在 GoF 里平平无奇，为什么在 STL 里被说成基石？

GoF 版只解决"统一遍历"；STL 把迭代器提升为算法与容器之间的抽象界面：算法按迭代器类别（输入/前向/随机）写成模板，任何满足概念的容器（乃至裸数组、流）即插即用——解耦带来的 M+N 组合优势覆盖整个库。加上迭代器适配器的再组合能力，它承担了"库的架构"而非"一个模式"的角色。

追问 3：既然 lambda 能替代命令/观察者类，什么时候还值得写显式的类？

需要"请求"具备身份与状态管理时：undo/redo 要存反向操作与合并逻辑、任务要携带优先级/重试次数/审计信息、观察者要复杂的订阅生命周期——结构化数据 + 多方法的场景，类的表达力回归。lambda 适合"逻辑即全部"的轻命令。判据：这个可调用体需不需要被查询、比较、序列化、二次加工。

追问 4：CRTP 和虚函数实现模板方法，怎么选？

三问定案：运行期需要把不同派生类放进同一容器按基类指针处理吗？需要 → 虚函数（CRTP 各实例是不同类型，无公共基类可容器化）。热路径对虚调用开销敏感吗？敏感且类型编译期已知 → CRTP。二进制体积/编译时间受限吗？受限 → 虚函数。库代码（如数值计算、序列化框架）偏 CRTP，业务代码偏虚函数——默认可读性优先。

追问 5：pimpl 和桥接是不是一回事？

结构同构，意图两分：桥接面向双维度独立扩展（形状 × 渲染器，两边都会长）；pimpl 面向编译期工程收益（隔离头文件依赖、稳定 ABI），Impl 通常只有一个实现、不构成"可替换维度"。所以说 pimpl 是"桥接的形、封装的心"。若某天 Impl 真需要多实现切换，pimpl 一步就长成正牌桥接。

追问 6：能举一个"标准库同时叠了多个模式"的例子吗？

std::sort 一处三模式：对外接口接受比较器——编译期策略；内部 introsort 按递归深度在快排/堆排/插排间切换——运行状态驱动的算法选择（策略切换，《C++ 篇》第 28 章）；操作对象是迭代器对——迭代器模式解耦容器。再如 shared_ptr：代理（转发+计数）+ 享元气质的控制块共享 + 删除器的策略注入。拆解标准库组件的模式叠层，是"懂设计"的最佳证词。

易错点

  • 背了 23 种模式却答不出一个 C++ 内建实例——本章存在的意义就是消灭这个断层。
  • 把智能指针说成装饰器（它不加功能层，管的是所有权与访问——代理）。
  • 认为"lambda 时代模式过时了"——消失的是仪式（接口类），意图与结构仍在，需要状态与身份时类形态回归。
  • CRTP 只会名词，写不出 static_cast<Derived*>(this)->method() 的分派骨架，或不知道它没有公共基类不能异构容器化。
  • pimpl 忘记把析构函数放到 .cpp（unique_ptr 析构需要 Impl 完整类型），编译报错查半天。
  • 谈编译期模式只吹零开销，不提编译期定死、代码膨胀的代价——单边论述显浅。

面试回答模板

如果面试官问"C++ 里有哪些设计模式的影子"，可以这样回答：

标准库本身就是模式陈列馆。智能指针是代理：重载解引用转发访问，叠加独占、计数、weak 的有效性检查这些访问策略；RAII 是 C++ 第一惯用法，构造获取析构释放，lock_guard、fstream 都是它，还给观察者退订、连接池归还当安全网。迭代器模式在 STL 里被抬到基石高度：算法只依赖迭代器概念，M 个算法加 N 个容器只写 M+N 份代码，reverse_iterator、插入迭代器又是迭代器上的适配器；stack、queue 是容器适配器。行为类模式被 std::function 加 lambda 现代化了：线程池提交任务就是命令模式，回调列表和信号槽就是观察者，需要 undo、优先级这类状态时再回到显式命令类。最有 C++ 特色的是把模式编译期化：sort 的比较器、unordered_map 的哈希、vector 的分配器、unique_ptr 的删除器都是模板参数注入的编译期策略，零虚调用还能靠 EBO 零空间；traits 加 tag dispatch、if constexpr 是编译期分派；CRTP 用 static_cast 到派生类实现编译期模板方法，enable_shared_from_this 就是标准库实例——收益是内联零开销，代价是编译期定死和代码膨胀，运行时要切换或要异构容器就回虚函数。pimpl 是桥接的工程版，头文件只留指针做编译防火墙。一个组件叠多层模式也常见：std::sort 同时是策略注入、introsort 的算法切换和迭代器解耦——能这样拆标准库，比背二十三个名字有说服力。
