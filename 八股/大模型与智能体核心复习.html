LLM 与 Agent 核心复习

本册把 LLM 原理、训练、推理、RAG、评测、安全和 Agent 工程压缩成一份复习入口。每个主题只保留核心概念、关键关系及答案、易错点。

版本变化快的模型、框架和协议只作为工程坐标；真正需要掌握的是数据流、状态、权限、可靠性和评测方法。

第一部分 LLM 基础原理

1. LLM 全景与生命周期

核心概念

  • LLM 根据上下文中的 Token 分布预测后续 Token，本质上是概率生成模型。
  • 基础模型通过大规模预训练获得通用语言和模式能力。
  • 指令模型和对话模型通过后训练获得更好的遵循指令和交互能力。
  • Embedding 模型把内容映射到向量空间，Reranker 对候选结果重新排序。
  • 完整生命周期包括数据、预训练、后训练、评测、部署、监控和反馈闭环。
  • 模型能力、外部知识、工具执行和业务规则是不同层次。

关键关系与答案

LLM 为什么会产生幻觉？

模型的训练目标是生成概率上合理的文本，不是查询一个永远正确的事实数据库。知识缺失、上下文冲突、检索错误、提示歧义和随机采样都可能导致幻觉。

Prompt 能不能增加模型没有的知识？

Prompt 可以组织和约束已有能力，不能凭空写入可靠的新知识。实时知识通常通过 RAG、工具或数据库查询提供。

模型、应用和 Agent 如何区分？

模型负责生成和判断；应用负责组织输入输出和业务规则；Agent 在应用中增加状态、工具、多步决策和执行控制。

易错点

  • 参数量大不等于所有任务都更好。
  • 模型回答流畅不等于事实正确。
  • RAG、微调和 Agent 解决的是不同问题。

2. 数学与深度学习基础

核心概念

  • 向量和矩阵用于表示 Token、隐藏状态和参数。
  • Softmax 把 Logits 转成概率分布。
  • 交叉熵衡量目标分布与模型分布的差异，语言模型常用下一个 Token 的交叉熵训练。
  • 困惑度是交叉熵的指数形式，反映模型对序列的不确定程度。
  • 梯度下降根据损失对参数的梯度更新模型。
  • 反向传播使用链式法则计算梯度。
  • Adam/AdamW 使用一阶和二阶梯度统计，AdamW 将权重衰减与梯度更新解耦。

关键关系与答案

交叉熵和 KL 散度有什么关系？

交叉熵可以拆成目标分布的熵加上 KL 散度。目标分布固定时，最小化交叉熵等价于最小化模型分布与目标分布之间的 KL 散度。

为什么需要 Softmax？

模型输出的是未归一化的 Logits，Softmax 把它们转换成和为 1 的概率分布，便于计算交叉熵和进行采样。

为什么训练中会出现梯度爆炸或消失？

深层网络反复相乘的梯度可能变得极大或极小。残差连接、归一化、合适初始化、梯度裁剪和稳定优化器可以缓解这些问题。

易错点

  • 困惑度只能反映特定数据分布上的预测难度，不等于所有任务的质量。
  • Loss 下降不代表业务能力一定提升。
  • KL 散度不对称，方向不同含义不同。

3. Tokenizer 与 Embedding

核心概念

  • Token 是模型处理文本的基本单位，不一定等于一个汉字或一个单词。
  • BPE、WordPiece、SentencePiece 通过子词或字节组合平衡词表大小和序列长度。
  • 特殊 Token 用于区分开始、结束、角色、填充等结构。
  • Embedding 层把 Token ID 映射为向量。
  • 位置表示让模型区分 Token 的顺序。
  • 权重绑定可以让输入 Embedding 和输出词表投影共享参数。

关键关系与答案

为什么不直接按词切分？

纯词级词表会遇到未登录词、词表过大和跨语言泛化问题；子词或字节级 Token 可以组合未见过的词，但可能产生更长序列。

Token 数量为什么重要？

Token 数量直接影响上下文长度、Attention 计算量、KV Cache 显存、推理延迟和 API 成本。

Embedding 和 Reranker 有什么区别？

Embedding 通常独立编码查询和文档，适合高效召回；Reranker 通常同时读取查询和候选文档，判断相关性更精细，但计算成本更高。

易错点

  • Token 不等于字符数，中文、英文、代码和特殊符号的 Token 比例不同。
  • 向量相似不等于事实正确。
  • Embedding 模型和生成模型的训练目标不同，不能直接互换。

4. Attention 与 Transformer

核心概念

  • Query 表示当前查询，Key 用于匹配，Value 携带被聚合的信息。
  • Attention 通过 Query 与 Key 的相似度计算权重，再加权求和 Value。
  • Self-Attention 的 Q/K/V 来自同一序列；Cross-Attention 的 Q 和 K/V 来自不同序列。
  • Causal Mask 防止当前位置看到未来 Token。
  • MHA 使用多组独立的 Q/K/V 头。
  • MQA/GQA 共享部分 K/V 头，降低 KV Cache 和推理开销。
  • FFN 提供逐 Token 的非线性变换，残差和归一化帮助训练稳定。

关键关系与答案

为什么 Attention 需要缩放？

当维度增大时，点积结果的方差可能变大，Softmax 容易饱和，梯度变小。除以维度平方根可以改善数值稳定性。

为什么 Decoder-only 模型使用 Causal Mask？

自回归训练要求当前位置只能依赖过去 Token，不能偷看目标 Token；这样训练目标和生成过程保持一致。

MHA、MQA、GQA 如何取舍？

MHA 表达能力和头部独立性更强，但 KV Cache 大；MQA 共享所有 K/V，推理更省显存；GQA 在质量和效率之间折中。

易错点

  • Attention 不是简单的全局平均，而是基于 Query 的动态加权。
  • Mask 的作用取决于训练或推理目标，不是所有 Attention 都使用同一种 Mask。
  • MQA/GQA 主要减少 K/V 规模，不是把所有计算都减少。

5. 模型架构、位置编码与 MoE

核心概念

  • Encoder 更擅长理解，Decoder 更擅长自回归生成，Encoder-Decoder 适合输入输出转换。
  • 绝对位置编码把位置向量直接加入表示；相对位置方法关注 Token 间的相对距离。
  • RoPE 通过旋转变换把位置信息融入 Q/K 的相对关系。
  • ALiBi 通过注意力偏置表达距离关系。
  • Dense 模型每次激活大部分参数；MoE 每次只选择部分 Expert。
  • MoE 需要 Router 和负载均衡，否则会出现专家拥塞或训练不稳定。

关键关系与答案

长上下文为什么不只是扩大最大长度？

还要处理位置外推、Attention 计算量、KV Cache 显存、训练数据覆盖、检索噪声和 Lost in the Middle 等问题。

MoE 为什么能提升参数规模而控制计算量？

每个 Token 只激活少数 Expert，参数总量可以很大，但单 Token 的计算量主要由被选中的 Expert 决定。代价是路由、通信、负载均衡和部署更复杂。

易错点

  • 最大上下文长度不等于模型能同样有效地利用所有位置。
  • MoE 的总参数量和每 Token 激活参数量不是同一个概念。
  • 位置编码外推效果依赖训练方式和具体实现。

第二部分 训练、对齐与推理能力

6. 预训练与规模化训练

核心概念

  • Causal LM 预测后续 Token，MLM 预测被遮盖 Token，FIM 适合代码补全。
  • 训练数据需要采集、清洗、去重、过滤、配比和质量评估。
  • 数据污染会导致评测结果虚高，重复数据会降低有效信息密度。
  • Scaling Law 研究模型规模、数据规模和计算量之间的关系。
  • In-Context Learning 通过上下文示例影响当前推理，不等于更新参数。
  • 分布式训练包括数据并行、张量并行、流水线并行、序列并行和专家并行。
  • 混合精度、ZeRO、FSDP 用于降低显存和通信成本。

关键关系与答案

数据质量和数据规模如何取舍？

规模扩大可以增加覆盖面，但低质量、重复和污染数据会稀释训练信号。应结合去重、质量过滤、配比和能力评测，而不是只追求数据量。

数据并行、模型并行和流水线并行有什么区别？

数据并行复制模型、切分 Batch；模型/张量并行把单层或张量切到多个设备；流水线并行把不同层放到不同设备，通过微批次流水执行。

混合精度为什么能提高效率？

低精度计算和存储减少显存、带宽和计算成本，同时保留部分高精度状态以维持训练稳定性。

易错点

  • 训练速度不只由 FLOPs 决定，还受数据读取、通信、负载均衡和显存带宽影响。
  • 训练 Loss 下降不代表数据、评测或泛化没有问题。
  • 并行度增加可能带来通信开销和同步等待。

7. 后训练、偏好对齐与推理能力

核心概念

  • 继续预训练让模型适应领域语料，SFT 让模型学习指定输入输出格式和任务行为。
  • 偏好数据通常比较多个回答，Reward Model 学习相对偏好。
  • RLHF 通常包含 SFT、奖励模型和策略优化；PPO 使用概率比率和裁剪控制更新幅度。
  • DPO 直接用偏好数据优化策略，不显式训练在线 RL 策略流程。
  • GRPO 等方法通过组内相对奖励减少部分价值模型依赖。
  • 过程监督关注推理步骤，结果监督只关注最终结果。
  • Reward Hacking 是模型通过钻奖励函数漏洞获得高分。

关键关系与答案

SFT、RLHF、DPO 如何区分？

SFT 学习人工示范；RLHF 先学习偏好奖励，再通过强化学习优化策略；DPO 直接利用偏好对比较策略概率，流程更简单但仍依赖高质量偏好数据。

为什么偏好数据容易有偏差？

标注者标准不一致、问题难度分布不均、长度和格式偏好、奖励模型过拟合都会导致偏差，因此需要标注规范、交叉校验和分布外评测。

Test-time Compute 为什么能提升推理？

通过多次采样、验证、搜索或更长推理过程增加推理阶段计算，再选择或修正结果；代价是延迟、成本和错误累积可能增加。

易错点

  • 偏好分数高不等于事实正确。
  • SFT 不是简单把知识写入模型，数据格式和 Loss 作用区域很重要。
  • 增加推理长度不一定提升质量，必须有验证或选择机制。

8. 参数高效微调

核心概念

  • 全量微调更新全部模型参数，成本高但表达能力完整。
  • Adapter 在模型旁增加少量可训练模块。
  • LoRA 用低秩矩阵表示参数更新，只训练低秩参数。
  • QLoRA 在量化基础模型上训练 LoRA 参数，降低显存占用。
  • Rank、Alpha、Target Module 影响 LoRA 的容量和作用范围。
  • 多 Adapter 可以按任务加载，但要处理合并、冲突和版本管理。

关键关系与答案

LoRA 为什么省显存？

它冻结基础模型，只训练低秩增量矩阵，不需要为全部参数保存梯度和优化器状态，因此训练参数和显存明显减少。

QLoRA 比 LoRA 多解决什么问题？

QLoRA 进一步量化冻结的基础模型，使其占用更少显存；训练质量取决于量化格式、适配层和任务数据。

什么时候不适合只做 LoRA？

需要大幅改变模型能力、模型结构或多个层面都要调整时，低秩更新容量可能不足；仍要根据数据规模和效果评测决定。

易错点

  • LoRA 只改变适配器参数，不能自动解决数据质量和任务定义问题。
  • 量化降低显存但可能影响精度和推理兼容性。
  • 不同 Adapter 合并后可能出现能力冲突或遗忘。

第三部分 推理优化与模型服务

9. 解码、Prefill、Decode 与 KV Cache

核心概念

  • Greedy 每次选概率最大 Token；Beam Search 维护多个候选序列。
  • Temperature 调整分布尖锐程度；Top-k、Top-p、Min-p 限制候选集合。
  • Prefill 处理输入上下文，通常计算密集；Decode 逐 Token 生成，通常访存和延迟敏感。
  • KV Cache 保存历史 Token 的 Key/Value，避免每一步重复计算。
  • TTFT 是首 Token 延迟，ITL 是生成 Token 之间的间隔。

关键关系与答案

为什么 Decode 阶段要使用 KV Cache？

生成新 Token 时，历史 Token 的 K/V 不变。缓存后只需为新 Token 计算 Q/K/V，再与历史 K/V 交互，避免重复计算整段上下文。

Temperature 越高越好吗？

不是。Temperature 高会增加随机性和多样性，低则更确定；事实问答、代码和创作任务需要不同取值，并通过评测选择。

为什么长上下文会增加显存？

上下文越长，需要保存的 KV 越多；并发越高，所有请求的 KV Cache 共同占用显存。

易错点

  • TTFT 和生成阶段延迟不是同一个指标。
  • KV Cache 节省重复计算，但会增加显存占用。
  • 解码策略只能改变生成行为，不能修复检索错误或事实缺失。

10. 高性能推理、量化与 Serving

核心概念

  • FlashAttention 优化 Attention 的显存访问和中间矩阵存储。
  • PagedAttention 将 KV Cache 分页管理，减少碎片和动态分配问题。
  • Continuous Batching 在请求不断到达时动态合并不同阶段的请求。
  • Chunked Prefill 把长输入分块，避免单个请求长期占用调度资源。
  • Speculative Decoding 用小模型提出候选，大模型验证，提高生成速度。
  • PTQ 在训练后量化，QAT 在训练中模拟量化。
  • 量化、剪枝、蒸馏通过精度换取显存、吞吐或延迟收益。
  • Serving 通常包含 Gateway、Scheduler、Engine、模型副本和监控。

关键关系与答案

吞吐和延迟为什么可能互相冲突？

增大 Batch 可以提高硬件利用率和整体吞吐，但会增加排队和单请求等待；低延迟通常需要更快调度、更小批次或更合理的请求分层。

PTQ 和 QAT 如何选择？

PTQ 成本低、部署快，适合已有模型快速压缩；QAT 在训练中考虑量化误差，通常更有机会保持精度，但训练成本更高。

如何估算 LLM 服务容量？

需要同时估算权重显存、KV Cache、运行时开销和并发请求，再结合输入输出长度、TTFT、ITL、吞吐和峰值流量压测，不能只看模型参数量。

易错点

  • 量化位数越低不代表所有硬件都更快。
  • 只优化模型计算而忽略调度、网络、队列和数据拷贝，端到端延迟仍可能不变。
  • 平均延迟正常时，P95/P99 仍可能严重恶化。

第四部分 Prompt、Context 与 RAG

11. Prompt 与结构化输出

核心概念

  • System 消息通常表达全局行为约束，User 消息表达当前任务，具体优先级取决于模型和应用实现。
  • Zero-shot 不提供示例，Few-shot 提供示范输入输出。
  • Prompt 需要明确任务、输入、约束、输出格式和失败处理。
  • 结构化输出依赖 Schema、Grammar、解析和校验，不能只要求“请输出 JSON”。
  • Prompt 应版本化并通过固定评测集验证。

关键关系与答案

Few-shot 为什么可能有效？

示例向模型展示任务格式、推理模式和边界，降低指令歧义；但示例错误、风格偏差或上下文过长也会降低效果。

为什么结构化输出仍需要程序校验？

模型生成具有概率性，可能漏字段、类型错误、增加额外文本或违反业务约束。Schema 校验、重试和修复仍必须由程序控制。

Prompt Injection 是什么？

不可信输入试图改变系统原本的指令、诱导模型泄露信息或调用不该调用的工具。不能只依赖一条提示语防御，必须配合权限隔离和输出校验。

易错点

  • 把 Prompt 写得更长不等于信息更有效。
  • System 指令不是绝对安全边界，工具权限必须由程序控制。
  • 结构化输出格式正确不等于内容正确。

12. Context Engineering

核心概念

  • Context 是模型当前可见的输入，包括指令、历史、检索结果、工具结果和状态。
  • Context Engineering 关注信息选择、排序、压缩、更新和隔离。
  • 上下文有长度、成本、延迟和注意力分配限制。
  • 长对话需要摘要、状态提取、历史裁剪或分层存储。
  • Lost in the Middle 表示关键信息位于长上下文中间时可能被利用较差。

关键关系与答案

Context 和 Memory 有什么区别？

Context 是当前请求直接提供给模型的可见信息；Memory 是跨请求保存和管理的信息，需要经过选择、召回和更新后才能进入 Context。

为什么不能把所有历史对话都塞给模型？

会增加 Token 成本、延迟和噪声，也可能导致关键信息被稀释或泄露。应根据任务保留近期对话、摘要、结构化状态和相关记忆。

如何降低长上下文噪声？

先识别任务需要的信息，再进行检索、排序、压缩和去重；对不同来源设置优先级，并在输出中要求引用或依据。

易错点

  • 上下文长度大不等于有效利用率高。
  • 摘要会丢失细节，重要状态应结构化保存而不是只依赖摘要。
  • 不可信文档和工具结果进入上下文后仍可能影响模型行为。

13. RAG 基础链路

核心概念

  • RAG 先从外部知识库检索证据，再把证据放入上下文生成回答。
  • 离线链路包括文档解析、清洗、切分、Embedding、索引和元数据管理。
  • 在线链路包括 Query 分析、召回、过滤、重排、上下文组装、生成和引用。
  • 向量检索适合语义相似，BM25 适合关键词匹配，混合检索结合两者。
  • Search Index 通常是业务数据的派生数据，需要同步、重建和校准机制。

关键关系与答案

RAG 和微调如何选择？

需要引用频繁变化、可追溯的外部知识时优先 RAG；需要稳定改变输出格式、风格或任务行为时考虑微调。二者可以组合。

为什么切分会影响 RAG 效果？

切得过小会丢失上下文，切得过大则降低检索精度并浪费上下文。应结合文档结构、问题类型、模型上下文和评测数据选择。

为什么搜索引擎不是天然事实源？

索引可能异步更新、延迟刷新、同步失败或被误删。业务数据库或原始文档通常保留事实，索引需要支持增量修复和全量重建。

易错点

  • Embedding 相似度高不等于证据一定回答了问题。
  • 只优化召回率而不检查生成忠实性，系统仍可能幻觉。
  • RAG 不是简单地“向量库 + Prompt”。

14. 高级 RAG 与 RAG 排障

核心概念

  • Query 改写、查询扩展和查询分解用于改善问题表达。
  • Reranker 对初始候选重新排序，通常比纯向量相似更精细。
  • MMR 兼顾相关性和结果多样性。
  • HyDE 先生成假设文档，再用其向量检索真实文档。
  • Multi-hop、Corrective RAG、Self-RAG、Adaptive RAG 处理复杂检索流程。
  • GraphRAG 利用实体、关系和图结构处理跨文档关联问题。
  • RAG 评测要拆分检索召回、证据相关、答案正确和答案忠实。

关键关系与答案

检索为空、检索错误、答案错误如何区分？

检索为空是没有召回候选；检索错误是召回内容与问题不相关；答案错误可能是证据正确但模型理解或生成错误。应分别记录 Query、候选、重排结果、最终上下文和答案。

为什么需要 Rerank？

初始检索适合高召回，但排序可能不够精确。Reranker 读取 Query 和候选文本的交互关系，对较小候选集做精排，以提高证据质量。

如何判断答案是否忠于证据？

检查答案中的每个关键主张是否能被引用证据支持，区分证据相关性、答案正确性和引用完整性，并使用人工评测或经过校准的 Judge 辅助。

易错点

  • 引用存在不等于引用支持了结论。
  • LLM-as-a-Judge 也会有偏差，需要 Rubric、校准和人工抽检。
  • GraphRAG 不是所有问题都优于向量检索，维护图结构也有成本。

第五部分 评测、安全与 LLM 系统

15. LLM 评测、幻觉与不确定性

核心概念

  • 评测可分为模型、组件、系统和业务四层。
  • Benchmark 适合横向比较，Golden Set 更接近真实业务。
  • 人工评测、Pointwise、Pairwise、Ranking 和 LLM-as-a-Judge 各有适用场景。
  • 幻觉可能来自参数知识缺失、上下文冲突、检索错误、提示歧义和随机性。
  • LogProb、ECE、Brier、拒答和选择性预测用于研究不确定性。
  • 在线评测还要关注成本、延迟、错误率、用户反馈和数据漂移。

关键关系与答案

为什么不能只看一个 Benchmark？

Benchmark 可能与真实任务分布不同，还可能存在数据污染、饱和和指标偏差。应结合代表性 Golden Set、切片评测、人工抽检和线上指标。

LLM-as-a-Judge 有什么问题？

Judge 可能偏好更长、更像自己的答案，受位置、格式、模型能力和提示影响。需要明确 Rubric、随机化顺序、校准和人工抽样。

如何让模型在不知道时拒答？

提供可靠证据、定义拒答条件、要求引用、使用置信度或分类器校验，并在敏感场景引入人工审核。只在 Prompt 中说“不要胡编”通常不够。

易错点

  • 质量提升可能伴随成本和延迟上升，要看 Pareto 取舍。
  • 准确率高不代表长尾或安全场景可靠。
  • 线上用户反馈需要去噪和分层，不能直接当作真值。

16. LLM 安全与治理

核心概念

  • Jailbreak 试图绕过模型或系统安全约束。
  • Prompt Injection 通过不可信输入影响指令和工具行为。
  • RAG 投毒会污染检索证据，工具投毒会影响执行结果。
  • 模型窃取、隐私泄露和敏感信息回显属于数据与模型风险。
  • 防御需要纵深：输入过滤、上下文隔离、权限控制、输出校验、审计、人工审批和 Kill Switch。
  • 合规治理包括数据来源、权限、留痕、删除、版本和责任边界。

关键关系与答案

为什么不能只靠 Prompt 防 Prompt Injection？

模型看到指令和不可信内容后可能无法稳定区分优先级。真正的安全边界应由程序权限、工具白名单、参数校验、沙箱和人工审批提供。

RAG 系统如何防止数据泄露？

检索前做租户和资源级权限过滤，禁止模型自行扩大查询范围，对上下文和日志做脱敏，并对输出进行敏感信息检测和审计。

工具调用为什么必须由程序校验？

模型只是在预测参数，不能直接拥有真实世界权限。程序必须检查身份、资源范围、参数合法性、幂等性、副作用和审批状态。

易错点

  • 内容安全和执行安全不是一回事。
  • 过滤词表不能替代权限和隔离。
  • 只保护 Prompt，不保护工具和数据源，系统仍然不安全。

17. LLMOps、模型选型与系统设计

核心概念

  • 模型选型要比较质量、延迟、成本、上下文、工具能力、隐私和可运维性。
  • LLMOps 管理数据、模型、Prompt、评测集、配置和部署 Artifact 的版本。
  • 可观测性需要记录 Trace、Token、延迟、错误、模型版本、检索和工具调用。
  • 生产系统需要超时、重试、限流、降级、缓存、灰度、回滚和 SLO。
  • API、私有部署和混合部署分别在交付速度、控制力、成本和隐私上取舍。
  • 多模态系统还要处理图像/音频/视频解析、Token、分辨率和跨模态评测。

关键关系与答案

如何选择 API 模型还是自部署？

先确认数据合规、QPS、延迟、质量、模型定制和团队运维能力。API 交付快、初始运维低；自部署控制力和隐私更强，但承担 GPU、升级、容量和故障成本。

LLM 系统为什么需要 Trace？

一次回答可能经过路由、Prompt、检索、Rerank、多个模型和工具。只有 Trace 能把这些阶段串起来，定位延迟、质量下降或错误来源。

如何设计企业知识助手？

业务数据作为事实源，构建带权限过滤的文档接入和检索链路，生成时要求引用和拒答；同时记录评测、成本、延迟、反馈和删除传播状态。

易错点

  • 不能只按单次 Token 价格估算成本，还要计算检索、工具、存储、重试和人工审核。
  • 模型升级可能改变 Prompt、工具调用和评测结果，需要灰度和回滚。
  • 多模态输入的分辨率、压缩和解析错误会直接影响后续生成。

第六部分 Agent 工程

18. Agent 定义与核心边界

核心概念

  • Agent 是让模型参与目标驱动的多步决策和执行的系统。
  • Agent 通常包含模型、状态、工具、环境、权限、循环和停止条件。
  • Workflow 由程序预先定义步骤和分支，Agent 让模型根据状态选择下一步。
  • Copilot 强调辅助人完成任务，RPA 强调固定流程自动化，多智能体强调多个角色协作。
  • Agent 的核心问题不是“能不能调用模型”，而是“谁决定下一步、动作有什么副作用、如何判断完成”。

关键关系与答案

Agent 和普通 LLM 应用有什么区别？

普通 LLM 应用通常是一次输入到一次输出；Agent 增加状态、工具、多步循环和执行反馈，能根据中间结果决定下一步，但不确定性和安全风险也更高。

Agent 和 Workflow 如何选择？

步骤稳定、约束明确时优先 Workflow；路径需要根据环境动态选择时使用 Agent。生产系统常把 Agent 的决策限制在可控 Workflow 和工具集合中。

Agent 为什么必须有停止条件？

模型可能重复调用工具、不断修改答案或在错误状态中循环。停止条件、最大步数、预算、超时和人工接管是运行时必须具备的控制。

易错点

  • Agent 不等于给 LLM 套一个无限 while 循环。
  • 工具数量增加不一定提升能力，可能增加选择错误和攻击面。
  • 自主性越高，越需要状态、权限、评测和人工兜底。

19. Agent 运行时与控制循环

核心概念

  • Run 表示一次完整任务，Step 表示一次决策或动作，Attempt 表示一次尝试。
  • 典型循环：观察状态 → 规划或推理 → 调用工具 → 获取结果 → 验证 → 继续或结束。
  • 控制面负责策略、预算、权限和状态迁移；数据面负责工具和外部资源访问。
  • 状态应区分用户输入、任务状态、工具结果、错误信息和最终产物。
  • 运行时要记录步骤、输入输出、耗时、成本、重试和副作用。

关键关系与答案

为什么要区分 Run、Step 和 Attempt？

Run 便于追踪一项任务的整体结果，Step 表示任务进展，Attempt 区分同一步骤的重试。这样才能分析失败位置、重试次数和成本。

为什么 Agent 需要预算？

预算可以限制最大步数、Token、工具调用次数、时间和金钱，防止循环、误调用和成本失控。

状态和上下文有什么关系？

状态是系统保存的事实和进展；上下文是某次模型调用实际看到的内容。运行时需要从状态中选择、压缩和排序上下文，而不是把所有状态原样塞给模型。

易错点

  • 工具返回成功不代表任务成功，还要检查结果是否满足目标。
  • 重试前必须判断动作是否有副作用，不能盲目重复执行。
  • 只记录最终答案会丢失最有价值的轨迹信息。

20. Agent 推理、规划与自我修正

核心概念

  • ReAct 交替进行思考和行动，根据观察结果继续决策。
  • Plan-and-Execute 先生成计划，再执行子任务。
  • 任务分解把复杂目标拆成有依赖关系的子任务。
  • 动态重规划根据工具结果、失败和新信息调整计划。
  • Reflection 让模型检查或批评自己的结果，Verifier 使用规则、模型或外部执行结果验证。
  • 停止决策判断目标是否完成、是否需要重试或转人工。

关键关系与答案

ReAct 和 Plan-and-Execute 如何取舍？

ReAct 适合环境变化大、需要边观察边行动的任务；Plan-and-Execute 适合任务结构相对清晰、希望减少反复规划的场景。复杂系统常结合二者。

Reflection 一定能提高质量吗？

不一定。如果没有新的证据、明确的检查标准或独立验证，Reflection 可能只是重复生成。更可靠的做法是让 Verifier 检查格式、事实、执行结果或约束。

什么是好的停止条件？

不仅要判断模型说“完成”，还应验证目标状态、必需字段、工具结果、引用证据和副作用是否真正完成。

易错点

  • 规划文本写得很完整不代表计划可执行。
  • 自我反思不是独立验证，容易重复同一个错误。
  • 子任务拆得过细会增加上下文、调用和失败成本。

21. 工具调用、执行环境与协议

核心概念

  • Function Calling 让模型输出结构化工具名和参数，真正执行由程序完成。
  • 工具 Schema 定义名称、参数类型、必填字段、约束和错误格式。
  • 工具系统需要超时、重试、幂等、权限、审计和副作用控制。
  • 代码执行和 Computer Use 必须有沙箱、资源限制和人工审批。
  • MCP 提供模型与工具、资源、Prompt 之间的标准化连接方式。
  • A2A/Agent Card 用于描述 Agent 能力和 Agent 之间的任务交互。

关键关系与答案

为什么不能让模型直接执行工具？

模型只负责提出动作建议，参数可能错误、越权或重复。程序需要验证身份、资源范围、参数、风险和审批状态，再决定是否执行。

工具幂等是什么意思？

同一动作重复执行不会造成额外错误结果，例如通过幂等键避免重复下单、重复扣款或重复发送通知。

MCP 和 Function Calling 是什么关系？

Function Calling 更像模型调用工具的结构化能力；MCP 进一步定义了发现、连接和暴露工具、资源、Prompt 的协议边界，二者不在同一抽象层。

代码执行为什么需要沙箱？

代码可能访问文件、网络、进程、密钥或消耗过多资源。沙箱通过权限隔离、网络限制、CPU/内存/时间配额降低风险。

易错点

  • Schema 正确不等于权限正确。
  • 工具重试必须考虑副作用。
  • 浏览器和 Computer Use 的截图、点击和页面内容都可能包含不可信指令。

22. Agent 记忆与知识访问

核心概念

  • State 保存任务当前事实和进展；Context 是当前模型调用可见内容；Memory 是跨步骤或跨会话保留的信息。
  • 短期记忆服务于当前任务，长期记忆服务于未来任务。
  • 记忆系统需要写入、召回、更新、过期、删除和权限控制。
  • Agentic RAG 让 Agent 根据任务决定是否检索、查什么、是否继续检索和如何验证。
  • 结构化数据库适合精确查询，向量检索适合语义召回，图结构适合关系遍历。

关键关系与答案

为什么不能把所有对话都当长期记忆？

对话中可能有临时信息、错误信息和敏感信息。长期记忆需要经过抽取、确认、权限判断和过期管理，否则会污染后续任务。

Agentic RAG 和普通 RAG 有什么区别？

普通 RAG 通常由固定流程完成检索；Agentic RAG 让 Agent 根据任务动态选择查询、工具、检索轮次和验证步骤，灵活性更高但成本和不确定性也更高。

记忆删除为什么困难？

信息可能同时存在于原始文档、向量索引、摘要、缓存、日志和模型上下文中。删除需要定义传播范围、异步同步和验证机制。

易错点

  • 摘要不是完美记忆，会丢失细节或引入错误。
  • 记忆召回相似不等于当前任务相关。
  • 多租户系统必须在检索前做权限过滤，而不是让模型自己判断。

23. Workflow、持久执行与人工介入

核心概念

  • Workflow 用状态图、节点和边描述可执行流程。
  • Durable Execution 把任务状态和执行进度持久化，使进程重启后可以恢复。
  • Checkpoint 保存可恢复状态，重放时需要保证动作幂等。
  • Human-in-the-Loop 在高风险、低置信度或需要审批时暂停等待人类决定。
  • 外部副作用应有明确的提交点、补偿策略和审计记录。

关键关系与答案

为什么 Agent 不能只依赖内存状态？

进程重启、网络故障或长任务等待会丢失内存状态。持久化状态和 Checkpoint 让任务可以恢复、重试和审计。

断点恢复为什么要求幂等？

恢复时可能重复执行上一个步骤。如果工具动作不可重复，就可能重复扣款、发货或发送通知，因此需要幂等键、状态检查或补偿操作。

哪些情况需要人工介入？

高风险副作用、权限提升、敏感数据访问、证据不足、模型不确定或多次失败时，应暂停并请求人工审批或接管。

易错点

  • 保存了状态不等于保存了外部副作用的真实结果。
  • 重放执行必须区分纯计算和不可重复的外部动作。
  • 人工审批节点也需要超时、撤销和审计。

24. 多智能体系统

核心概念

  • Supervisor 负责分派和汇总，Router 负责选择 Agent，Handoff 负责任务转交。
  • Blackboard 让多个 Agent 通过共享状态协作。
  • 专家 Agent 可以按领域、工具或任务阶段分工。
  • 多 Agent 协作需要通信协议、共享状态、超时、冲突解决和失败处理。
  • 并行执行可以降低总延迟，但会增加合并、重复和资源竞争复杂度。

关键关系与答案

什么时候值得使用多智能体？

当任务具有相对稳定的专业分工、可以并行或需要不同权限隔离时，多 Agent 可能有价值。仅仅为了增加角色数量而拆分，通常只会增加通信和调试成本。

多 Agent 如何处理冲突？

定义角色权限、结果格式和优先级，由 Supervisor、规则或独立 Verifier 合并；不能让多个 Agent 无限制地互相覆盖结果。

多 Agent 的主要风险是什么？

通信膨胀、循环转交、错误传播、状态不一致、成本失控和权限扩散。

易错点

  • 多智能体不一定比单 Agent 更聪明。
  • 并行执行需要处理部分失败和结果合并。
  • Agent 之间传递的数据同样需要权限和可信度控制。

25. Agent 生产工程

核心概念

  • 生产 Agent 需要记录 Run、Step、Tool Call、输入输出、耗时、Token、成本和错误。
  • Trace 用于定位循环、错误工具和慢步骤，Trajectory 用于评估决策过程。
  • 可靠性依赖超时、重试、幂等、断点恢复、降级和人工接管。
  • 性能优化包括模型路由、上下文压缩、缓存、并行工具调用和结果复用。
  • 部署要考虑隔离、多租户、密钥、资源上限和版本兼容。

关键关系与答案

Agent 评测为什么不能只看最终答案？

最终答案可能碰巧正确，也可能工具调用错误但被后续步骤掩盖。还要评估任务成功、规划、工具选择、参数、轨迹、成本和安全违规。

如何控制 Agent 成本？

限制步数和工具次数，进行模型路由、缓存、上下文压缩和并行执行，并按任务统计 Token、外部 API、重试和人工审核成本。

如何排查 Agent 无限循环？

查看 Trace 中重复的状态、工具和错误，加入最大步数、状态去重、进展检测、结果验证和明确的失败退出条件。

易错点

  • 只记录最终答案会让 Agent 很难排障。
  • 重试、并发和人工恢复都可能导致重复副作用。
  • Agent 的可靠性不能只靠更换模型解决。

26. Agent 评测、安全与系统设计

核心概念

  • Agent 评测关注任务成功率、轨迹质量、工具选择、参数正确率、成本和安全性。
  • 离线测试验证稳定场景，在线评测验证真实流量、长尾和版本变化。
  • 安全风险包括 Prompt Injection、工具越权、恶意工具、数据外泄、隐私泄露和供应链风险。
  • 企业知识助手、Coding Agent、Deep Research、数据分析和 Computer Use 是典型系统设计场景。
  • 系统设计必须说明状态、工具、权限、失败恢复、评测和观测。

关键关系与答案

如何设计企业知识助手 Agent？

先做身份和权限过滤，再由 Agent 判断是否检索、改写 Query、召回和重排；生成时要求引用和拒答，工具只开放白名单能力，并记录完整 Trace 和审计。

如何设计 Coding Agent？

让 Agent 在隔离工作区中读取代码、修改文件、运行测试并根据结果迭代；代码执行需要资源和网络限制，修改需要 diff、测试和人工确认，不能直接操作生产环境。

如何设计 Deep Research Agent？

拆分问题、检索多来源资料、去重和交叉验证，保存来源与引用，最后由 Verifier 检查结论是否被证据支持，并对研究时间和调用次数设置预算。

易错点

  • 工具白名单不等于工具参数安全。
  • 研究报告有引用不等于结论被引用支持。
  • Agent 系统设计不能只描述 Prompt，还要描述运行时和故障路径。

28. 高频故障排查

  1. 训练异常：先看数据、Loss、梯度、学习率、显存和通信。
  2. 推理变慢：拆分排队、Prefill、Decode、KV Cache、网络和后处理。
  3. RAG 无效：依次检查解析、切分、Embedding、召回、重排、上下文和生成。
  4. 答案幻觉：确认是否有证据、证据是否相关、引用是否支持结论、模型是否应该拒答。
  5. Agent 循环：查看状态变化、重复工具、错误重试、预算和停止条件。
  6. 工具失败：检查 Schema、参数、权限、超时、幂等和外部服务状态。
