第一部分 数据库与数据组件基础

1. 数据库最小知识地图

题目

什么是数据库、DBMS、关系型数据库和 SQL？表、行、列、主键、外键、索引分别是什么？数据库和普通文件保存数据有什么区别？

这道题在考什么

面试官通常不是想让你立刻讲出存储引擎源码，而是在确认你能不能把“数据、数据结构、查询语言、并发和持久化”分层理解。只要先把数据库看成“带结构、约束、查询、并发和恢复能力的数据管理系统”，后续索引、事务和缓存就有了挂靠点。

面试核心结论

数据库是有组织的数据集合，DBMS 是管理这些数据的软件，MySQL、PostgreSQL 是关系型 DBMS，SQL 是描述查询和修改意图的语言。关系型数据库用表组织数据：行代表记录，列代表属性，主键标识一行，外键表达表之间的关系，约束负责阻止明显非法的数据。数据库相对普通文件的主要价值，不只是“帮你存东西”，还包括结构化查询、索引、事务、并发控制、权限和故障恢复。

数据库、DBMS、表和 SQL

概念 最低限度理解 面试中的说法
数据库 被管理的数据集合 保存和组织业务数据
DBMS 管理数据库的软件 负责查询、并发、权限和恢复
关系型数据库 用表和关系组织数据 MySQL、PostgreSQL、Oracle
SQL 描述数据操作的语言 说“查什么”，不直接描述每一步怎么执行
表 一类记录的集合 用户表、订单表、商品表
主键 唯一标识一行 通常要求唯一且非空
外键 表之间的关系约束 订单中的用户 ID
索引 加速检索的辅助结构 用空间和写入成本换查询速度

数据库和文件有什么区别

用文件也能保存数据，但应用通常需要自己处理：

  • 如何按条件查找，而不是每次从头扫描文件；
  • 多个线程或进程同时读写时如何协调；
  • 写到一半进程崩溃时如何恢复；
  • 如何保证字段类型、唯一性和引用关系；
  • 多个客户端如何共享访问和控制权限。

数据库把这些通用能力集中提供出来，代价是部署、运维、连接和学习成本更高。数据量很小、结构简单、访问模式固定时，文件或嵌入式数据库也可能更合适。

关系型数据库和 NoSQL 的基本区别

维度 关系型数据库 NoSQL 的常见取向
数据模型 表、行、列、关系 键值、文档、列族、图
查询方式 SQL，表达能力强 通常围绕访问模式设计
约束 结构和事务能力较完整 约束可能更多交给应用
扩展方式 传统上先强调单机能力 常强调水平扩展和灵活模型
典型选择 订单、账户、库存 缓存、日志、文档、海量特定访问

不要把关系型数据库和 NoSQL 说成绝对的“谁更先进”。选型取决于数据关系、事务要求、访问模式、规模和团队运维能力。

高频追问

追问 1：主键和唯一索引有什么区别？

主键表达“这张表用什么字段唯一标识记录”的业务和结构约束，通常只能有一个且不允许为空；唯一索引主要是为了保证某列或列组合不重复，一张表可以有多个。不同数据库对空值和索引实现的细节可能不同，面试时先说概念边界，再补充具体数据库差异。

追问 2：外键一定要在数据库里建立吗？

不一定。外键约束能让数据库帮忙保证引用完整性，但高并发、分库分表或跨服务场景中，物理外键可能增加写入和迁移成本，团队也可能选择由应用和校验任务维护逻辑关系。关键不是“必须建”或“绝对不建”，而是说明一致性责任由谁承担。

追问 3：数据库是不是一定比文件快？

不是。数据库有连接、解析、事务和网络开销；对简单的顺序读写，文件可能更直接。数据库的优势在于复杂查询、并发访问、数据约束、索引和恢复能力，而不是所有场景下的单次读写延迟都最低。

易错点

  • 把数据库、DBMS 和 SQL 当成同一个概念。
  • 认为 NoSQL 就是“不需要设计结构”。
  • 认为索引只带来收益，忽略空间、写入和维护成本。
  • 把主键、唯一索引、外键混成“都是保证唯一”。

30 秒回答模板

数据库是有组织的数据集合，DBMS 负责查询、并发、权限和恢复，SQL 是描述数据操作的语言。关系型数据库用表组织数据，行是记录，列是属性，主键唯一标识一行，外键描述表间关系，索引用额外空间换取更快检索。相比普通文件，数据库的核心价值是结构化查询、约束、事务和并发恢复能力；NoSQL 则根据键值、文档或其他模型优化特定访问模式，不能简单理解为关系型数据库的替代品。

学习停止线

本章不展开具体存储引擎、日志格式、复制协议和分布式事务；只要能把数据模型、DBMS 能力和关系型/NoSQL 的选型边界讲清，就达成防守目标。

2. SQL 基础与表结构设计

题目

如何写一条基础 SQL？WHERE 和 HAVING 有什么区别？内连接和左连接怎么选？三大范式解决什么问题，为什么又经常反范式？

这道题在考什么

这一章考的是“能不能读懂常见 SQL”和“有没有基本的数据建模意识”。重点不是背语法，而是理解查询的逻辑步骤：先确定数据来源，再过滤、分组、投影、排序和限制结果。

面试核心结论

SQL 的基本思路是从一个或多个数据源中选择记录，再按条件过滤、分组统计、选择列、排序和限制数量。WHERE 过滤分组前的明细行，HAVING 过滤分组后的统计结果；内连接只保留两边都匹配的行，左连接保留左表全部行。范式主要减少重复和更新异常，反范式则是为了在明确访问模式下减少 JOIN、降低查询成本；二者是取舍，不是绝对规则。

CRUD 和 SQL 分类

目标 常见语句 作用
Create INSERT 新增记录
Read SELECT 查询记录
Update UPDATE 修改记录
Delete DELETE 删除记录
Definition CREATE、ALTER、DROP 修改表结构
Transaction COMMIT、ROLLBACK 提交或回滚事务

一个简单查询通常可以按这个顺序阅读：

SELECT department, COUNT(*) AS employee_count
FROM employee
WHERE status = 'active'
GROUP BY department
HAVING COUNT(*) >= 5
ORDER BY employee_count DESC
LIMIT 10;

逻辑上可以记成：FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT。数据库实际执行时可能通过索引、改写和不同执行计划优化这个过程，但写 SQL 时先用这个逻辑顺序检查语义。

JOIN 的最低限度理解

连接类型 保留什么 常见场景
内连接 两边都匹配的记录 只看有对应关系的数据
左连接 左表全部，右表匹配则补充 查所有用户及其可选订单
右连接 右表全部，左表匹配则补充 可以改写成左连接，使用较少
交叉连接 两边组合 特殊生成或测试场景，谨慎使用

左连接最容易出错的地方是过滤条件的位置。把右表条件写在 WHERE 中，可能会把没有匹配右表的行过滤掉，从效果上变成内连接；需要保留左表行时，要认真判断条件应该放在 ON 还是 WHERE。

三大范式和反范式

  • 第一范式：字段尽量保持原子性，不把多个值塞进一个字段。
  • 第二范式：非主属性依赖完整主键，主要针对组合主键的部分依赖。
  • 第三范式：非主属性不通过另一个非主属性间接依赖主键，减少传递依赖。

范式化可以减少重复和更新异常，但查询时可能需要更多 JOIN。反范式可以把高频查询需要的结果预先放在一起，代价是写入和一致性维护更复杂。面试时说“为了性能反范式”还不够，要补充“基于稳定访问模式、接受冗余，并配套更新策略和校验”。

高频追问

追问 1：WHERE 和 HAVING 的区别是什么？

WHERE 在分组前过滤明细记录，HAVING 在分组后过滤聚合结果。例如“先筛选在职员工，再统计部门人数，最后只保留人数不少于 5 的部门”：在职条件写 WHERE，人数条件写 HAVING。

追问 2：左连接后为什么结果变少了？

常见原因是把右表条件放在了 WHERE，导致右表为空的行被过滤；也可能是连接条件写错或后续 GROUP BY、DISTINCT 改变了结果。排查时先单独查看连接结果，再逐步加过滤和聚合。

追问 3：为什么不把所有数据放一张大表？

一张大表会产生大量重复数据，修改时容易不一致，字段含义也会混乱；拆表能表达关系、减少冗余并支持独立约束。也不能机械拆分，查询路径过长、跨表 JOIN 过多时需要结合访问模式适度反范式。

易错点

  • 把 SQL 的书写顺序和逻辑执行顺序混为一谈。
  • 忘记 NULL 不是普通字符串，不能简单用 = NULL 判断。
  • 只会说“范式减少冗余”，说不出更新、插入、删除异常。
  • 连接条件缺失导致笛卡尔积，却只去怀疑数据库性能。

30 秒回答模板

写 SQL 时我会先确定 FROM 和连接关系，再用 WHERE 过滤明细，必要时 GROUP BY 聚合，HAVING 过滤聚合结果，最后选择列、排序和分页。内连接只保留匹配行，左连接保留左表全部行。范式主要通过拆分关系减少冗余和更新异常；如果某个查询路径非常稳定、JOIN 成本高，可以在评估一致性维护成本后做反范式，而不是为了性能无条件堆字段。

学习停止线

本章不要求背完整 SQL 语法，也不要求掌握复杂窗口函数和存储过程；能读懂基础 CRUD、JOIN、聚合和范式取舍即可。

3. 索引与查询性能基础

题目

索引为什么能加快查询？B+ 树为什么常用？联合索引的最左匹配是什么？什么是回表和覆盖索引？如何用 EXPLAIN 做基础排查？

这道题在考什么

面试官想确认你知道索引不是“给字段加个标记”，而是一种额外维护的数据结构。它用空间和写入成本换取更少的数据扫描；索引是否有效，取决于查询条件、数据分布和优化器选择。

面试核心结论

索引通过维护有序或可快速定位的辅助结构，减少查询需要检查的数据范围。关系型数据库常用 B+ 树，是因为它适合范围查询、树高较低、节点可存多个键并且叶子通常有序连接。联合索引要遵循从左到右的匹配规律；覆盖索引可以直接从索引拿到所需列，避免再访问主表。索引不是越多越好，它会增加写入、存储和维护成本。

为什么 B+ 树适合数据库索引

只记住三个特点即可：

  1. 一个节点可以放很多键，树的高度通常比二叉树低，减少磁盘或页访问次数。
  2. 叶子节点按顺序组织，适合范围查询和排序。
  3. 非叶子节点主要存键和指针，更多空间留给叶子中的数据定位信息。

哈希索引适合等值查询，但不擅长范围查询和排序；普通二叉搜索树高度可能退化，也不适合磁盘页的批量访问。不要把 B+ 树说成“任何情况下都最快”，它只是综合访问模式和存储介质后的常见选择。

常见索引概念

概念 最低限度理解
主键索引 围绕主键组织的索引
二级/普通索引 主键之外的检索入口
联合索引 多个列按顺序组成一个索引
回表 先查二级索引，再根据主键取完整行
覆盖索引 查询所需列都在索引中，不必回表
选择性 一个条件区分数据的能力

最左匹配的直观例子

假设有联合索引 (user_id, status, created_at)：

  • WHERE user_id = ? 通常可以利用最左列；
  • WHERE user_id = ? AND status = ? 可以继续利用后续列；
  • 只查 status = ?，通常不能完整利用这个联合索引；
  • 范围条件出现在中间列后，后续列的继续匹配能力可能受到影响。

具体能否使用、使用到什么程度，仍要看数据库版本、统计信息和执行计划。面试回答“最左匹配是绝对规则”会显得过于机械。

EXPLAIN 看什么

防守级别关注：

  • 使用了哪个表和访问方式；
  • 是否命中预期索引；
  • 预计扫描多少行；
  • 是否出现全表扫描、临时表或额外排序；
  • 实际执行时间和扫描行数是否与估计差距很大。

优化的基本流程是：先确认慢在哪里，再看执行计划和数据分布，最后通过改 SQL、改索引或改访问方式解决。不要一看到慢就盲目加索引。

高频追问

追问 1：索引为什么会失效？

常见原因包括对索引列做函数或计算、隐式类型转换、前缀模糊匹配、联合索引不满足左侧条件、选择性太低，以及优化器判断扫描全表更便宜。回答时最好说“可能无法有效使用”，不要绝对断言“只要用了函数就一定失效”。

追问 2：索引越多越好吗？

不是。索引会占空间，插入、更新、删除时也要维护；重复或低选择性的索引还可能增加优化器选择成本。索引应该围绕真实查询建立，并通过执行计划和压测验证收益。

追问 3：深分页为什么慢？

OFFSET 很大时，数据库可能需要先扫描并跳过大量记录，再返回后面的少量结果。常见改进是基于稳定排序键做游标/范围分页，或者限制允许的页数；具体方案取决于是否需要随机跳页。

易错点

  • 把索引等同于哈希表，忽略范围查询和排序。
  • 把“命中索引”误认为“查询一定快”。
  • 只会背最左匹配，不会看 EXPLAIN 和实际数据量。
  • 为每个字段都建索引，忽略写入成本和索引冗余。

30 秒回答模板

索引是为了减少查询扫描范围的辅助数据结构，数据库常用 B+ 树，因为它树高低、适合页式存储，也支持范围查询和有序遍历。联合索引要遵循从左到右的匹配规律；如果查询所需列都在索引中，可以形成覆盖索引，减少回表。排查慢 SQL 时我会先看执行计划、扫描行数和排序临时表，再决定改 SQL、加合适索引还是调整分页方式，同时评估索引对写入和空间的成本。

学习停止线

本章不要求深入优化器源码、页分裂细节、索引下推实现和存储引擎内部页结构；能解释“索引的收益与代价”和完成基础执行计划判断即可。

4. 事务与并发控制基础

题目

什么是事务？ACID 分别是什么意思？脏读、不可重复读、幻读有什么区别？隔离级别怎么选？乐观锁、悲观锁和 MVCC 解决什么问题？

这道题在考什么

这类题主要考“多条操作如何保持业务正确性”。不需要一开始就进入 undo log、redo log 和 Read View 的实现细节，但要知道事务解决的是一组操作的原子性、并发可见性和故障恢复问题。

面试核心结论

事务把一组相关操作组织成一个逻辑单元，要求它要么整体成功，要么整体失败。ACID 分别强调原子性、一致性、隔离性和持久性；隔离级别是在并发性能与读一致性之间做取舍。锁和 MVCC 都是并发控制手段：锁通过限制同时访问保护共享数据，MVCC 通过保存多个版本让读写在一定程度上并行。事务不能替代幂等、重试和业务校验，也不能自动保证跨服务操作的一致性。

ACID 怎么解释

特性 面试级解释 关注点
Atomicity 一组操作整体成功或失败 出错时回滚
Consistency 事务前后满足约束和业务不变量 约束、状态转换
Isolation 并发事务之间相互隔离 脏读、幻读等
Durability 提交后的结果在故障后仍可恢复 持久化和恢复

“一致性”不是说所有副本永远同时一样，也不是数据库替你保证所有业务规则。它首先指事务提交前后应满足数据库约束和应用声明的不变量；分布式系统里的副本一致性是另一个层次的问题。

三类并发读问题

  • 脏读：读到了另一个尚未提交事务写入的数据，之后对方回滚，刚才读到的内容不存在了。
  • 不可重复读：同一个事务两次读取同一行，期间另一个事务提交了修改，前后结果不同。
  • 幻读：同一事务按范围查询，两次结果的行集合发生变化，像凭空出现或消失了记录。

不同数据库对隔离级别、快照读、当前读和幻读的具体边界可能不同。基础面试中先给标准定义，再说明“具体行为要看数据库实现”，比绝对化表述更可靠。

隔离级别的基本光谱

隔离级别 读一致性 并发能力 主要风险
Read Uncommitted 最弱 较高 可能脏读
Read Committed 读已提交数据 中等 可能不可重复读
Repeatable Read 同一事务读取更稳定 中等 仍需关注范围写入和实现差异
Serializable 近似串行执行 较低 吞吐和等待成本高

不要把隔离级别简单说成“越高越好”。高隔离通常意味着更多锁、等待或版本管理，选型要结合业务是否允许旧数据、并发量和写冲突。

锁、乐观锁和 MVCC

  • 悲观锁：假设冲突会发生，访问前先加锁。适合冲突频繁、必须强保护的场景，代价是等待和死锁风险。
  • 乐观锁：假设冲突较少，更新时检查版本号或时间戳是否变化。适合读多写少，冲突时让失败方重试或提示。
  • MVCC：通过保存版本信息，让读操作读取符合可见性规则的版本，减少读写互相阻塞。它不是“完全没有锁”，更新、范围保护和当前读仍可能需要锁。

业务上还要记住：数据库锁只能保护数据库里的并发访问，不能自动保护缓存、文件、远程服务或另一个数据库。

事务边界和幂等

事务边界太小，可能无法保证业务整体正确；边界太大，会长时间占用锁和连接，增加冲突与回滚成本。一个常见原则是：

  1. 在事务内只做必须和数据一致性绑定的操作；
  2. 不要在持有数据库事务时调用慢的外部 RPC；
  3. 对外部重试、消息重复和网络超时，使用业务幂等键、唯一约束或状态机兜底。

高频追问

追问 1：事务回滚是不是所有操作都能撤销？

通常只能可靠回滚事务管理范围内的数据库操作。已经发出的邮件、扣款请求、远程 RPC 和外部消息，不能因为本地事务回滚就自动撤销，所以跨系统操作要设计补偿、状态机、可靠事件或幂等重试。

追问 2：乐观锁失败怎么办？

根据业务选择重试、重新读取后合并、提示用户冲突或放弃本次更新。重试必须有上限和退避，不能无限循环；如果冲突本身意味着业务不允许覆盖，就应该返回明确的冲突结果。

追问 3：数据库死锁怎么处理？

先通过数据库日志或监控确认等待环，再缩短事务、统一访问顺序、减少锁范围和锁持有时间；运行时通常捕获死锁错误并在安全条件下重试。重试不是根治方案，根治仍是调整访问顺序和事务设计。

追问 4：为什么事务里不应该调用外部服务？

外部服务延迟不可控，可能让数据库锁长时间不释放；外部服务失败时，本地事务又无法回滚对方。更稳妥的方式是先完成本地必要状态变更，再通过消息或任务异步推进外部动作，并设计幂等和补偿。

易错点

  • 把 ACID 的“一致性”说成分布式副本强一致。
  • 认为 MVCC 完全不需要锁。
  • 认为加了事务就不会出现业务不一致。
  • 认为重试天然安全，忽略重复扣款、重复发货等副作用。
  • 只会说“加大隔离级别”，不会分析吞吐和等待成本。

30 秒回答模板

事务把一组相关操作作为一个整体执行，ACID 分别是原子性、一致性、隔离性和持久性。隔离级别是在并发性能和读一致性之间取舍，脏读、不可重复读、幻读是常见并发问题。锁通过限制并发访问保护数据，MVCC 通过版本可见性减少读写阻塞；但它们只覆盖数据库内部。涉及消息、缓存或 RPC 时，我还会配合幂等键、唯一约束、重试上限和补偿机制。

学习停止线

本章不要求背数据库日志恢复流程、复杂 MVCC 可见性算法和分布式事务协议；能讲清事务边界、隔离问题、锁与 MVCC 的定位，以及幂等和重试的关系即可。

5. 缓存与 Redis 基础

题目

为什么要使用缓存？Redis 常见数据类型有哪些？缓存穿透、击穿、雪崩分别是什么？数据库和缓存如何保持一致？Redis 分布式锁可靠吗？

这道题在考什么

缓存题考的是取舍：用更快但可能过期或丢失的数据副本，换取更低延迟和更高吞吐。面试官希望听到的不只是“Redis 很快”，还包括缓存失效、脏数据、热点、容量和故障时的降级方案。

面试核心结论

缓存通过保存近期或热点数据，减少后端存储和计算压力。常见 Cache Aside 模式是读缓存，未命中时读数据库并回填；写入时先更新数据库，再删除缓存。缓存天然存在过期、穿透、击穿、雪崩和一致性窗口，方案选择要在延迟、一致性、可用性和实现复杂度之间取舍。Redis 适合做高吞吐的内存数据组件，但不能在所有场景中替代数据库。

Redis 数据类型只记用途

类型 常见用途 需要知道的关键词
String 缓存值、计数器、分布式锁 原子自增、过期时间
Hash 对象字段、局部更新 按字段读写
List 简单队列、时间线 两端操作
Set 去重、集合运算 交集、并集
Sorted Set 排行榜、按分数排序 score、范围查询

选类型时先看访问模式，不要为了“用上 Redis”而把所有对象都塞成字符串。

Cache Aside 的基本流程

读请求通常是：

  1. 查询缓存；
  2. 命中则直接返回；
  3. 未命中则查询数据库；
  4. 把结果写入缓存并设置合理过期时间；
  5. 返回结果。

写请求通常是：

  1. 更新数据库；
  2. 删除缓存；
  3. 下一次读请求再从数据库加载并回填。

“更新数据库后删除缓存”不是强一致方案，只是比“先删缓存再更新数据库”更不容易留下长期脏缓存。对强一致要求高的业务，要考虑版本校验、消息驱动更新、读写屏障或直接绕过缓存。

三类缓存问题

问题 典型原因 基础防守方案
穿透 请求大量不存在的 key 参数校验、空值缓存、布隆过滤器
击穿 一个热点 key 同时失效 互斥重建、逻辑过期、预热
雪崩 大量 key 同时失效或缓存整体故障 随机过期、多级缓存、限流降级

不要把三者混成“缓存失效”。穿透强调查不存在的数据，击穿强调单个热点，雪崩强调成片失效或缓存集群不可用。

过期、淘汰和容量

缓存中的“过期”与“淘汰”不是同一件事：过期是数据到达生命周期，淘汰是内存不足时选择清理对象。工程上还要考虑：

  • 热点 key 是否集中在少数节点；
  • 过期时间是否同时到期；
  • 大 key 是否造成网络和内存压力；
  • 缓存失效后数据库能否承受回源流量；
  • Redis 故障时是否有降级、限流和恢复方案。

Redis 分布式锁的最低限度

一个基础锁至少要满足：加锁原子、带过期时间、释放时验证持有者身份。简单地执行 SETNX 后再单独设置过期时间，可能在进程崩溃时留下永久锁；释放时直接 DEL，可能误删其他客户端后来获得的锁。

Redis 锁还可能受到主从切换、时钟、网络分区和租约过期的影响。它适合配合幂等和业务兜底解决“减少重复工作”，不应未经评估就被当成绝对可靠的分布式互斥协议。

高频追问

追问 1：为什么不直接更新缓存？

并发写入时，不同请求可能乱序到达缓存，后写入数据库的旧值可能反而最后覆盖缓存。删除缓存把重建动作交给下一次读请求，通常更容易控制；但它仍是最终一致，删除失败要有重试、消息或对账机制。

追问 2：缓存击穿怎么处理？

可以让只有一个请求负责回源重建，其余请求等待或返回旧值；也可以使用逻辑过期，让数据物理上暂时保留，后台异步刷新。前者偏一致性，后者偏可用性和低延迟。

追问 3：缓存和数据库谁是最终事实来源？

多数 Cache Aside 架构中数据库是事实来源，缓存是可重建的副本。缓存可以丢失、过期或被淘汰，因此不能把无法恢复的唯一数据只放在缓存里。

易错点

  • 只背“缓存三大问题”，说不清成因和影响范围。
  • 把缓存一致性说成强一致。
  • 分布式锁只会说 SETNX，不提过期、误删和主从风险。
  • 忽略大 key、热 key 和回源风暴。

30 秒回答模板

缓存用空间换时间，减少数据库和计算压力。常见 Cache Aside 读流程是先查缓存，未命中查数据库再回填；写流程通常先更新数据库，再删除缓存。穿透是查不存在的数据，击穿是单热点失效，雪崩是成片失效或缓存整体故障，分别通过参数校验、互斥重建、随机过期、限流降级等方式处理。Redis 适合做高吞吐缓存和数据组件，但它不是天然可靠的事实数据库，分布式锁也必须考虑租约、误删和故障切换。

学习停止线

本章不深入 Redis 源码、跳表、RDB/AOF 文件格式和 Cluster 选主细节；能完成缓存方案的基础选型、风险识别和故障兜底说明即可。

6. 消息队列基础

题目

为什么需要消息队列？消息如何保证不丢？重复消费怎么办？如何处理顺序、积压和消费失败？Kafka、RabbitMQ、RocketMQ 大致有什么区别？

这道题在考什么

消息队列的核心不是“换一个 API 发消息”，而是把生产者和消费者解耦，并把处理从同步调用变成可排队、可重试、可削峰的异步流程。代价是引入延迟、重复、顺序、积压和运维复杂度。

面试核心结论

消息队列主要用于异步、解耦和削峰。生产者把消息写入队列，消费者稍后读取并确认处理结果。可靠消息系统通常需要持久化、确认、重试和失败转移，但“至少一次投递”往往意味着消费者可能收到重复消息，因此业务必须幂等。顺序性、吞吐量、延迟、可靠性和运维成本之间不能同时无限优化。

基本角色

角色 作用
Producer 产生并发送消息
Broker 接收、保存、分发消息
Topic/Queue 按业务或消费关系组织消息
Partition 把数据拆分以并行扩展
Consumer 读取并处理消息
Consumer Group 多个消费者协作消费一组消息
ACK/Offset 记录消息是否被确认或消费到哪里

消息可靠性的基本链路

需要分别考虑三段：

  1. 生产端到 Broker：发送是否成功确认，失败如何重试，重试是否产生重复。
  2. Broker 持久化：消息是否写入可靠介质，副本是否足够，故障时能否恢复。
  3. Broker 到消费端：消费者处理成功后何时确认；确认过早可能丢数据，确认过晚可能重复消费。

因此“消息不丢”不是某一个开关，而是生产、存储、消费和业务落库共同完成的结果。

重复消费与幂等

常见幂等方式包括：

  • 业务唯一键或去重表；
  • 数据库唯一约束；
  • 状态机限制非法重复转换；
  • 更新时带版本号或条件；
  • 记录消费进度和处理结果。

不要把“消息队列只投递一次”当成业务设计前提。网络重试、消费者崩溃、确认超时和重新分配都可能导致同一消息再次被处理。

顺序和积压

严格顺序通常只能在有限范围内保证，例如同一个订单或同一个用户的消息进入同一分区并由同一消费顺序处理；全局顺序会严重限制并行度。

消息积压时先判断：

  • 生产速度是否突然升高；
  • 消费者是否变慢或频繁失败；
  • 下游数据库或 RPC 是否成为瓶颈；
  • 是否可以扩容消费者；
  • 是否可以降级、丢弃低价值消息或延迟处理。

盲目增加消费者可能把压力转移给数据库和下游服务，甚至造成更大故障。

三类产品的定位级理解

类型 更适合强调 面试级记忆
Kafka 类日志系统 高吞吐、分区、流式处理 适合大规模事件流和日志
RabbitMQ 类消息代理 路由、确认、灵活投递 适合业务消息和复杂路由
RocketMQ 类业务消息系统 事务消息、延迟消息等 常见于业务异步和电商场景

具体选型还要看团队经验、已有基础设施、可靠性要求和运维能力，不要只背产品标签。

高频追问

追问 1：消息重复了怎么办？

把消费设计成幂等：用业务 ID、唯一约束、状态判断或去重记录确保同一消息多次执行不会重复产生副作用。先确认副作用是什么，再决定数据库约束、缓存标记还是业务状态机。

追问 2：消息消费失败怎么办？

短暂故障可以重试并退避；持续失败应进入死信或人工处理队列，同时记录原因和告警。重试次数要有限，避免坏消息无限阻塞整个消费链路。

追问 3：消息队列能解决所有异步问题吗？

不能。它增加了排队和最终一致性，不能替代事务、缓存、RPC 或任务调度器。对于必须同步得到结果的请求，消息队列可能只适合作为后续异步通知，而不是主流程替代品。

易错点

  • 把异步等同于一定更快，忽略用户感知延迟和最终一致性。
  • 只谈生产者发送成功，不谈消费者处理和确认时机。
  • 说“保证 exactly once”却没有解释业务副作用如何去重。
  • 遇到积压只会扩容消费者，不分析下游瓶颈。

30 秒回答模板

消息队列主要解决异步、解耦和削峰。生产者把消息交给 Broker，消费者异步读取并确认处理结果。可靠性要分别看生产确认、Broker 持久化和消费确认；实际系统常采用至少一次投递，所以消费者必须用业务 ID、唯一约束或状态机保证幂等。顺序只能在有限范围内保证，积压时要先判断生产突增、消费失败还是下游瓶颈，再选择扩容、降级、重试或死信处理。

学习停止线

本章不深入 Kafka 副本协议、消息存储文件、RocketMQ 事务消息源码和复杂流处理语义；能讲清消息队列的价值、可靠性链路和幂等边界即可。

7. 一个 Web 请求的完整路径

题目

从用户在浏览器输入地址，到服务端返回结果，中间大致经历了什么？DNS、CDN、网关、应用服务、缓存、数据库、消息队列分别处在什么位置？

这道题在考什么

这道题考的是能不能把网络、应用、数据和运维知识串成一条链，而不是要求背某一家公司的固定架构。回答时要区分“用户必须等待的同步主链路”和“可以稍后完成的异步副作用”，还要知道每一层都可能引入延迟、失败和重试。

面试核心结论

一个典型 Web 请求会经过域名解析和网络接入，可能命中 CDN 或负载均衡，再由网关转发到应用服务。应用服务先做鉴权、参数校验和业务编排，然后查询缓存；缓存未命中时访问数据库，并视情况回填缓存。下单、发通知、写审计日志等不必阻塞主请求的工作，可以通过消息队列交给异步消费者。日志、指标和链路追踪贯穿整个过程。真实架构会按业务取舍删减或拆分这些组件，关键是明确每个组件解决的问题和失败后的影响。

一条请求链路

客户端
  ↓
DNS / CDN / 网关
  ↓
应用服务 ──→ 缓存命中 ──→ 返回响应
  │
  ├────→ 缓存未命中 ──→ 数据库 ──→ 回填缓存
  │
  ├────→ 消息队列 ──→ 异步 Worker
  │
  └────→ 日志 / 指标 / 链路追踪

各层只记最小职责

层次 最低限度理解 典型问题

同步主链路和异步副作用

应先问“这个结果是不是用户必须立即知道”。余额扣减、库存校验等通常在同步主链路中完成；发送邮件、更新搜索索引、生成报表等通常可以异步化。异步不是免费提速，它会引入消息可靠性、最终一致性、重试和排查成本。

一个实用判断方式是：

  • 必须立即返回的结果：同步调用，并设置明确超时；
  • 允许稍后完成的动作：事件或消息异步处理；
  • 失败后不能悄悄丢失的动作：需要持久化、重试、死信或补偿；
  • 可能重复执行的动作：从接口和数据库约束上设计幂等。

高频追问

追问 1：为什么要先查缓存，再查数据库？

缓存的访问延迟和并发承载能力通常优于数据库，适合承接热点数据。未命中时以数据库作为事实来源，再回填缓存。回填和失效策略需要结合数据变化频率、允许的旧数据时间和一致性要求决定。

追问 2：请求为什么会变慢？

先按链路拆分：DNS、网络、网关排队、应用线程池、外部 RPC、缓存、数据库、序列化和下游队列。不能只看平均耗时，还要看 P95/P99；也不能只看应用 CPU，因为连接池耗尽、锁等待和下游超时同样会造成慢请求。

追问 3：一个下游服务故障，为什么可能拖垮整个系统？

如果上游没有超时、限流、熔断和隔离，调用线程会持续等待，连接池和线程池逐渐耗尽，故障就会沿依赖链扩散。重试还可能把压力放大，因此重试必须有上限、退避和幂等条件。

追问 4：为什么要有链路追踪？

单个请求可能跨越多个服务和异步任务。通过请求 ID、Trace ID 和 Span 可以把同一条链路串起来，定位到底是哪一跳慢或失败。它不能替代日志和指标，而是提供跨组件的关联视角。

易错点

  • 把所有组件都当成系统必选项，忽略架构取舍；
  • 只描述“请求成功路径”，不说明超时、重试和降级；
  • 把缓存或消息队列当成数据库的替代品；
  • 把异步理解成没有一致性成本的免费性能优化；
  • 只看平均延迟，不看尾延迟和资源耗尽。

30 秒回答模板

一个 Web 请求通常先经过 DNS 和接入层，再由网关路由到应用服务。应用完成鉴权和业务编排后优先查缓存，未命中再查数据库并回填；不必阻塞用户的通知、索引更新等动作通过消息队列异步处理，日志、指标和链路追踪负责观察全过程。设计时我会把同步主链路、超时重试、缓存一致性、消息幂等和下游故障隔离分别考虑，而不会把这张架构图当成固定模板。

学习停止线

本章不深入 CDN 内核、网关源码、服务网格数据面或具体云厂商网络；能画出请求链路，并能指出每层的价值、延迟来源和故障边界即可。

8. 分布式系统最小知识地图

题目

什么是分布式系统？为什么把一个程序拆到多台机器后会复杂很多？CAP、强一致性、最终一致性、分片、副本和分布式 ID 分别解决什么问题？

这道题在考什么

面试官主要想确认你是否理解：分布式的难点不是“机器变多”本身，而是网络通信和局部故障让系统无法直接观察全局状态。回答不需要背完整理论，但要能从一致性、可用性、扩展性和运维成本之间说明取舍。

面试核心结论

分布式系统把一个逻辑系统部署在多个独立节点上，以获得容量、性能、可用性或组织上的收益，但节点之间只能通过网络通信，网络可能延迟、丢包、重复或分区，节点也可能单独故障。因此必须明确数据由谁负责、多个副本何时算一致、请求失败如何重试以及操作是否幂等。CAP 讨论的是发生网络分区时，一致性和可用性之间的取舍；它不是“任意情况下只能三选二”的产品标签。

CAP 的最低限度理解

CAP 中的三个词是：

  • Consistency：对一次读操作而言，系统表现得像访问一个一致的数据副本；
  • Availability：每个请求都能得到非错误响应，但不代表一定读到最新值；
  • Partition tolerance：网络发生分区或消息互不可达时，系统仍尝试继续工作。

现实分布式系统通常必须面对网络分区，因此分区发生时往往要在“返回最新数据的确定性”和“继续对外服务”之间选择。这个选择应落到业务：支付余额、库存扣减更重视一致性；推荐列表、点赞数展示可能允许短暂最终一致。

强一致、最终一致和业务一致

  • 强一致：写成功后，后续读取在约定范围内立即看到新值，代价通常是等待协调或牺牲部分可用性；
  • 最终一致：系统暂时可能读到旧值，但在没有继续更新和故障的情况下，副本最终收敛；
  • 业务一致：即使底层组件是最终一致，业务也可通过状态机、补偿、对账和幂等保证最终结果正确。

不要把“最终一致”说成“不一致也没关系”，而应说明允许的旧数据窗口、异常期间的用户体验和最终修复机制。

高频追问

追问 1：CAP 是不是说系统只能满足三个中的两个？

不是。CAP 讨论的是网络分区发生时的取舍；在没有分区时，一个系统可以同时表现出较强的一致性和较高的可用性。面试回答应补上具体故障前提，而不是机械地说“只能二选一”。

追问 2：为什么重试会带来重复操作？

客户端可能在服务端已经成功处理后才因网络超时，于是无法知道结果，随后再次发送。网络层无法替业务判断“重复是否有害”，所以需要请求 ID、幂等键、唯一约束或状态查询接口。

追问 3：分布式锁能解决所有并发问题吗？

不能。它只能在锁的正确性、租约、故障恢复和业务边界都设计好的前提下，限制某段临界区的并发执行；还要考虑锁持有者暂停、租约过期、误删他人锁和下游操作不可回滚等问题。很多场景用数据库唯一约束或状态机更直接。

追问 4：为什么不能用时间戳简单生成全局有序 ID？

多台机器的时钟可能不同步、回拨或同一毫秒生成多个 ID。实际方案通常把时间、节点标识和序列号组合起来，或由专门服务分配，并明确是否只要求唯一、趋势递增还是严格全局有序。

易错点

  • 把 CAP 背成没有网络分区前提的口号；
  • 把最终一致说成不需要修复和对账；
  • 认为加副本就天然高可用，忽略副本延迟和切换；
  • 认为分布式锁一加就安全，不谈租约和幂等；
  • 看到“分布式”就直接引入复杂中间件，没有先明确约束。

30 秒回答模板

分布式系统的主要复杂性来自网络和局部故障：节点之间可能超时、重复、分区，多个副本也可能暂时不一致。因此设计时要先明确一致性和可用性的业务要求，再选择分片、副本、协调和故障恢复方式。CAP 只讨论网络分区时的一致性与可用性取舍；无论采用什么方案，都要补上超时、重试、幂等、监控和人工或自动补偿。

学习停止线

本章不展开共识算法证明、Raft 日志复制细节、CRDT 数学形式和复杂分布式事务协议；能正确解释分布式故障模型、CAP 边界和常见组件职责即可。

9. 高可用与服务治理基础

题目

如何提高一个服务的可用性？限流、熔断、降级、超时、重试、负载均衡和健康检查分别解决什么问题？

这道题在考什么

这道题考的是故障设计，而不是“多部署几台机器”。面试官希望听到从冗余、流量控制、依赖隔离、优雅退化到故障恢复的完整思路，并且知道可用性提升会增加一致性、运维和成本。

面试核心结论

高可用的基础是消除单点并让故障可隔离、可发现、可恢复。常见手段包括多实例和负载均衡、健康检查和自动摘除、超时与有限重试、限流与舱壁隔离、熔断和降级、数据副本与备份，以及演练和发布回滚。它们不是互相替代的开关：超时控制等待时间，重试处理瞬时失败，熔断阻止持续调用，限流保护系统容量，降级定义业务在资源不足时保留什么。

保护链路的基本工具

机制 解决的问题 常见误区
超时 防止请求无限等待 所有下游都使用一个过长固定值
重试 应对少量瞬时失败 无上限重试、没有退避、重复副作用
限流 控制进入系统的流量 只限入口，不保护关键资源
熔断 下游持续失败时快速失败 熔断后没有探活和恢复策略
降级 资源不足时保留核心功能 没有定义可接受的旧数据或空结果
舱壁隔离 防止一个依赖耗尽全部线程/连接 所有资源池仍然共享
健康检查 发现异常并摘除实例 只检查进程存活，不检查服务能力
负载均衡 分散请求和故障影响 忽略会话、热点和不均匀流量

超时、重试和熔断要一起设计

假设服务 A 调用服务 B：

  1. A 必须给 B 设置小于自身请求预算的超时时间；
  2. 只有判断为瞬时错误且操作具备幂等性时才重试；
  3. 重试要限制次数，并使用退避和抖动，避免同时重试形成风暴；
  4. B 持续失败时，A 通过熔断快速失败或走降级路径；
  5. 经过探测确认 B 恢复后，再逐步放量关闭熔断。

如果每层都重试 3 次，五层调用链可能把一次请求放大为大量下游请求，因此重试预算要在链路上统一考虑。

可用性和数据安全不是同一个指标

服务能够返回响应，不代表数据没有丢失；数据库有备份，也不代表接口一定可用。面试时可以把目标拆成：

  • 可用性：用户请求多大比例能在约定时间内成功；
  • 可靠性：系统在故障和恢复过程中是否维持正确行为；
  • 持久性：成功写入的数据在故障后能否恢复；
  • 恢复能力：故障发生后多久恢复（RTO），最多允许丢失多久数据（RPO）。

高频追问

追问 1：服务部署多个实例就高可用了吗？

不一定。还要确认实例是否跨故障域、负载均衡是否能摘除异常实例、依赖的数据库和配置中心是否有单点、发布是否支持回滚，以及连接池和线程池是否会在故障时耗尽。多实例只是冗余的一部分。

追问 2：重试次数越多越可靠吗？

不是。重试可以提高对瞬时网络抖动的容忍度，但会增加延迟和下游压力，还可能重复执行写操作。重试前要判断错误类型、剩余时间和幂等性，持续失败应快速失败或降级。

追问 3：限流应该按什么维度做？

按业务可以按用户、租户、接口、IP、令牌或资源类型限流；算法可用固定窗口、滑动窗口、漏桶或令牌桶。关键不是背算法名字，而是说明保护对象、超限响应和突发流量是否允许。

追问 4：什么是灰度发布？

先把小比例流量导向新版本，观察错误率、延迟和业务指标，再逐步扩大范围；异常时可以快速回退。灰度需要版本兼容、流量标记、数据库变更兼容和明确的停止条件。

易错点

  • 只说“加机器”，不谈单点、故障域和数据层；
  • 把重试、熔断、限流当成同一种机制；
  • 认为重试能够解决所有失败；
  • 只设置存活探针，不检查实例是否真的能提供服务；
  • 讨论 99.99% 可用性，却不说明统计窗口和降级目标。

30 秒回答模板

提高可用性要从冗余、隔离、控制和恢复四方面做：多实例和跨故障域消除单点，健康检查与负载均衡摘除异常实例，超时、有限重试、限流、熔断和舱壁防止故障扩散，降级和备份保证核心能力与数据可恢复。重试只适用于有限的瞬时错误，并且必须结合幂等、退避和整体超时预算设计。

学习停止线

本章不深入服务网格控制面、复杂流量调度算法和多地域容灾实现；能把常见治理机制放到正确的故障场景中，并知道它们的副作用即可。

10. 容器、云计算与 DevOps 基础

题目

容器和虚拟机有什么区别？Docker 镜像、容器、Pod、Deployment、Service 分别是什么？CI/CD、滚动发布、蓝绿发布和灰度发布解决什么问题？

这道题在考什么

这道题主要防止把一组运维名词混在一起。面试中应先讲清“应用如何被打包、运行、扩缩容和发布”，再补充 Kubernetes 或云服务名词，不需要假装自己是集群运维专家。

面试核心结论

虚拟机通常虚拟出完整硬件并运行独立操作系统，隔离更重；容器共享宿主机内核，通过镜像和隔离机制封装应用及其依赖，启动更快、密度更高，但隔离边界与虚拟机不同。镜像是不可变的打包产物，容器是镜像的运行实例。Kubernetes 这类平台负责把容器按照期望状态部署、发现、扩缩容和自愈；CI/CD 则把代码变更自动经过构建、测试、发布和回滚流程。

只记这些对象

概念 最低限度理解
镜像 Image 应用和运行依赖的只读打包产物
容器 Container 镜像启动后的隔离运行实例
虚拟机 VM 带独立客户操作系统的虚拟化环境
Pod Kubernetes 中共同调度和网络命名空间的最小运行单元
Deployment 描述副本数、版本和滚动更新的控制对象
Service 为一组 Pod 提供稳定访问入口和负载分发
Config/Secret 将配置和敏感信息与镜像解耦
Registry 存放和分发镜像的仓库

CI/CD 的基本流水线

一条简化流水线可以是：代码提交 → 静态检查 → 单元测试 → 构建镜像 → 安全扫描 → 部署测试环境 → 集成测试 → 灰度或滚动发布 → 观测 → 自动或人工回滚。

这里最容易被忽略的是“可回滚”和“可观测”。如果数据库变更不可逆、镜像没有版本号或发布后没有错误率和延迟指标，自动化流水线反而可能把故障传播得更快。

发布策略只记定位

  • 滚动发布：逐步替换旧实例，资源利用率较好，但新旧版本会同时存在；
  • 蓝绿发布：准备两套环境，切换流量，回滚直观但成本更高；
  • 灰度/金丝雀发布：只给小部分用户或流量新版本，根据指标逐步放量；
  • 特性开关：代码已发布，但通过配置决定功能是否开放，适合快速关闭风险功能。

高频追问

追问 1：容器是不是轻量级虚拟机？

这是便于入门的类比，但不严谨。容器通常共享宿主机内核，主要通过命名空间、资源限制等机制隔离；虚拟机包含独立客户操作系统，隔离和启动开销通常更大。两者都能封装运行环境，但安全边界和运维方式不同。

追问 2：为什么镜像要尽量不可变？

不可变镜像能让同一版本在不同环境中更容易复现，便于审计、回滚和定位差异。运行时状态应放到外部卷、数据库或对象存储中，不能把容器本地文件系统当成可靠持久化存储。

追问 3：Pod 和容器有什么关系？

容器是进程运行环境，Pod 是 Kubernetes 的调度和网络边界；一个 Pod 可以包含一个或多个需要共享网络和生命周期的容器。常见应用是一 Pod 一主容器，辅助容器用于代理、采集或初始化等场景。

追问 4：为什么发布后新旧版本要兼容？

滚动发布和灰度期间新旧实例会同时处理请求，客户端、消息和数据库也可能处于不同版本。接口字段新增应尽量向后兼容，数据库变更通常采用“先扩展、迁移、再收缩”的步骤。

易错点

  • 把容器当成天然安全隔离；
  • 把容器本地文件当成持久化数据；
  • 只讲自动部署，不讲测试、观测和回滚；
  • 认为 Kubernetes 本身能修复所有应用缺陷；
  • 忽略资源请求、限制和 OOM 对服务的影响。

30 秒回答模板

镜像是应用及依赖的不可变打包产物，容器是它的运行实例；容器通常共享宿主机内核，和带独立操作系统的虚拟机在隔离和开销上不同。Kubernetes 用 Pod、Deployment、Service 等对象管理容器的调度、发现和滚动更新。CI/CD 的完整目标不只是自动发布，还包括自动测试、安全检查、灰度观测和可回滚。

学习停止线

本章不深入 Kubernetes 调度器、CNI/CSI、Linux 容器隔离实现和云厂商产品矩阵；能理解打包、部署、服务发现、扩缩容和发布回滚的基本关系即可。

11. 监控、日志与故障排查基础

题目

日志、指标、链路追踪有什么区别？线上服务变慢或报错时如何排查？什么是 SLI、SLO、SLA？

这道题在考什么

这道题考的是“能不能观察系统并形成排查闭环”。不仅要知道三个可观测性信号的定义，还要能从现象、范围、时间、依赖和变更记录出发缩小问题范围，而不是上来就重启服务。

面试核心结论

日志记录单个事件的上下文，指标把大量事件聚合成时间序列，链路追踪把一次请求跨服务的调用关系串起来。三者互相补充：指标适合发现趋势和告警，日志适合看具体错误，追踪适合定位调用链中的慢点。排障时先确认影响范围和开始时间，再对比发布、流量、资源和下游依赖，最后通过回滚、限流、降级或修复验证结果，并沉淀复盘。

三类信号的分工

信号 回答的问题 例子
日志 Logs 某个请求或事件具体发生了什么？ 错误堆栈、用户 ID、请求 ID
指标 Metrics 系统整体趋势和比例怎样？ QPS、错误率、P99、CPU
追踪 Traces 一次请求经过哪些组件，哪一跳慢？ Span、依赖调用耗时

最低限度的指标集合

可以从四类指标开始：

  • 流量：请求数、消息生产和消费速率；
  • 错误：HTTP 5xx、业务失败、重试、死信；
  • 延迟：平均值、P95、P99 和超时数；
  • 饱和度：CPU、内存、线程池、连接池、队列长度和磁盘空间。

这和常说的 RED（Rate、Errors、Duration）以及 USE（Utilization、Saturation、Errors）思路相近。不要只监控机器 CPU：线程池耗尽时 CPU 可能很低，数据库锁等待也可能只表现为延迟升高。

故障排查的基本顺序

  1. 确认事实：什么时候开始，影响哪些接口、用户、地域和版本；
  2. 看变化：是否刚发布、扩容、改配置、流量突增或下游异常；
  3. 看四类指标：流量、错误、延迟、饱和度是否同步变化；
  4. 沿链路下钻：用 Trace ID 找慢请求，再查对应日志和下游；
  5. 先止损：回滚、限流、熔断、降级、摘除实例或切换备用；
  6. 验证恢复：确认业务成功率、尾延迟和队列积压恢复，而不是只看进程存活；
  7. 复盘改进：补监控、测试、容量评估、自动化和操作手册。

日志至少要有的字段

时间、级别、服务名、实例、环境、请求 ID/Trace ID、接口、耗时、结果码和关键业务标识通常比一段不可检索的自然语言更有价值。敏感信息应脱敏，不能为了排障把密码、令牌或完整身份证号写进日志。

高频追问

追问 1：平均延迟很低，用户为什么仍然觉得慢？

平均值会掩盖少量极慢请求。高并发场景通常要看 P95/P99 等尾延迟，并按接口、地域、版本和依赖拆分；还要确认客户端、网络和页面渲染是否贡献了用户感知延迟。

追问 2：日志、指标和 Trace 能互相替代吗？

不能。指标适合聚合和告警，日志适合具体上下文，追踪适合跨服务链路。只保留一种信号通常会导致发现、定位或关联其中一环缺失。

追问 3：什么是 SLI、SLO、SLA？

SLI 是实际测量的服务指标，例如成功率和 P99；SLO 是团队希望达到的目标；SLA 是对外约定的服务等级及可能的责任或补偿。面试中应说明统计窗口、请求范围和错误预算，而不是只报一个百分比。

追问 4：为什么告警太多也会造成问题？

告警疲劳会让真正重要的故障被淹没。告警应面向用户影响或可操作的风险，设置合理阈值、持续时间、分级和负责人；详细诊断信息可以放在仪表盘和日志中。

易错点

  • 只收集日志，不做结构化字段和关联 ID；
  • 只监控 CPU/内存，不监控错误、延迟、线程池和依赖；
  • 用单个阈值告警所有波动；
  • 排障时直接重启，导致现场和证据丢失；
  • 忽视观测系统本身的成本、采样和敏感信息保护。

30 秒回答模板

日志回答具体发生了什么，指标回答整体趋势，Trace 回答一次请求在哪一跳变慢或失败。排障时我会先确认影响范围和时间，再对比发布、流量、资源和依赖变化，沿 Trace 下钻到日志，必要时先回滚、限流或降级止损，最后用成功率、尾延迟和队列积压验证恢复。SLI 是测量，SLO 是目标，SLA 是对外承诺。

学习停止线

本章不深入 Prometheus 存储、日志采集链路、采样算法或具体 APM 产品；能建立信号分工、基础指标和排障闭环即可。

第三部分 编程语言与计算机基础防守

12. 程序从源码到运行

题目

一段源代码是如何变成可以运行的程序的？编译、链接、加载、解释执行和 JIT 分别是什么？静态库和动态库有什么区别？

这道题在考什么

这道题用于建立“代码不是直接跑起来的”这条基础链路。对非主攻语言不需要记编译器内部算法，但要能分辨编译期错误、链接期错误、运行期错误，以及依赖如何被装配进最终程序。

面试核心结论

典型编译型语言会经历预处理、编译、汇编和链接：源文件先被转换为目标文件，再和库及其他目标文件链接成可执行文件或动态库；运行时由操作系统加载，建立虚拟地址空间、栈、堆和共享库映射后开始执行。解释器直接或间接执行中间表示，JIT 则在运行过程中把热点代码编译成本地机器码。静态链接把库代码复制进产物，部署相对简单但体积和升级成本更高；动态链接在运行时共享库，节省空间但引入版本和加载依赖。

一条最低限度的编译链

源代码 -> 预处理 -> 编译为汇编/目标文件 -> 链接库和目标文件 -> 可执行文件
                                                         |
                                                         v
                                                   加载并运行

不同语言会有差异：Java 常见是源码编译为字节码，再由虚拟机解释或 JIT；Python 等语言通常先生成字节码并由运行时执行。面试回答时先说明“具体语言不同”，不要把所有语言硬套成 C/C++ 的流程。

四类错误放在哪一层

类型 典型时机 例子
语法/类型错误 编译或解释前检查 括号不匹配、类型不兼容
编译错误 源码到目标代码 不支持的语法或模板实例化失败
链接错误 组合目标文件和库 找不到函数实现或符号冲突
运行时错误 程序执行后 空指针、越界、权限或依赖缺失

栈、堆和虚拟地址空间只记用途

  • 栈：通常保存函数调用帧、局部变量和返回信息，生命周期与调用关系相关；
  • 堆：动态分配的区域，生命周期由程序或运行时管理；
  • 代码段/只读数据：保存指令和部分常量；
  • 虚拟地址空间：进程看到的逻辑地址范围，由操作系统映射到物理内存，并提供隔离和权限控制。

具体布局和优化会因平台、编译器与运行时而变化，基础回答不要把它们说成绝对固定。

高频追问

追问 1：为什么编译能通过，运行时仍然会崩？

编译器只能检查语言规则和部分静态条件，无法穷尽所有输入、资源状态和并发交互。空指针、越界、文件不存在、网络超时和竞态都可能在运行时出现。

追问 2：静态库和动态库怎么选？

静态库在链接时把实现合并进产物，依赖更直接但体积可能变大，升级库通常要重新链接；动态库由多个程序共享，便于独立升级和节省空间，但要处理加载路径、ABI 兼容和版本冲突。选择取决于部署方式和依赖管理能力。

追问 3：编译器优化会不会改变程序结果？

在满足语言规则和可观察行为的前提下，优化可以重排或消除代码；如果程序依赖未定义行为、数据竞争或错误的内存假设，优化可能暴露问题。不能把“Debug 能跑”当成正确性的证明。

追问 4：为什么需要 ABI？

ABI 规定二进制层面的调用约定、数据布局、符号和异常等规则，使不同编译单元或库能够互相调用。源码兼容不一定代表二进制兼容，编译器、编译选项和标准库版本变化都可能影响 ABI。

易错点

  • 把编译、链接和加载混为一个步骤；
  • 认为解释型语言完全不编译，或编译型语言完全没有运行时；
  • 把栈和堆的区别简化成“快和慢”；
  • 看到运行时崩溃就归因于编译器；
  • 只讲静态/动态库优点，不讲版本和部署代价。

30 秒回答模板

对典型编译型语言，源代码会经过预处理、编译、汇编和链接，生成可执行文件；运行时操作系统负责加载并建立进程地址空间。解释器执行中间表示，JIT 会把热点代码在运行时编译优化。静态库在构建时合入产物，依赖简单但体积和升级成本较高；动态库运行时共享，节省空间但要处理加载和 ABI 兼容。编译期、链接期和运行期错误要分开定位。

学习停止线

本章不深入编译器优化算法、链接器重定位格式、JIT 内联决策和具体 ABI 规范；能讲清从源码到运行的层次，以及常见错误所在阶段即可。

13. 数据结构与算法最低限度

题目

常见数据结构怎么选？如何解释时间复杂度和空间复杂度？哈希表、堆、二叉树、图、二分查找和 BFS/DFS 分别适合什么问题？

这道题在考什么

非算法主攻方向不需要刷完所有高级算法，但面试官可能用基础题判断编程和问题拆解能力。最低目标是看到需求能想到合适的数据结构，能说出复杂度、边界条件和为什么这样选。

面试核心结论

数据结构的选择取决于主要操作：数组适合按下标访问，链表适合局部插入但随机访问差，哈希表适合按键快速查找，堆适合持续维护最大或最小元素，队列适合先进先出，栈适合后进先出，树和图用于表达层级与关系。复杂度是输入规模增长时资源消耗的数量级，不是一次运行的精确耗时。先明确操作和约束，再选择结构并说明最坏或平均复杂度。

最低限度对照表

结构 典型操作/场景 常见复杂度直觉
数组/向量 下标访问、连续存储 访问 O(1)，中间插入通常 O(n)
链表 已知节点附近插入删除 查找 O(n)，局部修改可 O(1)
哈希表 key-value、去重、计数 平均查找 O(1)，需考虑冲突和扩容
栈 括号匹配、撤销、递归模拟 入栈出栈 O(1)
队列 BFS、任务排队 入队出队 O(1)
堆 Top K、优先级任务 插入/删除堆顶 O(log n)
有序树 范围查询、维护顺序 平衡时查找约 O(log n)
图 依赖、路线、网络关系 BFS/DFS 通常 O(V+E)

高频模式只记用途

  • 哈希表：两数之和、频次统计、判断重复、缓存映射；
  • 双指针/滑动窗口：连续区间、去重、左右边界；
  • 二分查找：序列有序，或答案满足单调性；
  • 栈：括号、单调栈、表达式和最近更大/更小元素；
  • 堆：只需要维护前 K 个或当前最小/最大元素；
  • BFS：无权图最短步数、按层扩散；
  • DFS/回溯：遍历、连通性、枚举选择；
  • 前缀和/差分：批量区间求和或区间更新；
  • 排序：把复杂关系转成有序后的线性扫描。

复杂度回答的正确姿势

先说明输入规模和核心操作，再说时间与额外空间。例如：用哈希表保存已经出现的元素，一次遍历即可把查找从每次 O(n) 降到平均 O(1)，整体平均 O(n)，额外空间 O(n)；如果要求最坏情况保证，就要补充哈希冲突或换用有序结构的影响。

高频追问

追问 1：哈希表为什么平均是 O(1)？

哈希函数把键映射到桶，理想情况下元素均匀分布，查找只需检查少量候选；冲突会让一个桶中有多个元素，扩容和好的哈希函数能降低冲突概率。O(1) 是平均或摊销意义，不是任何实现和输入下的绝对保证。

追问 2：什么时候用 BFS，什么时候用 DFS？

如果关心无权图从起点出发的最短层数，通常用 BFS；如果只需要遍历、判断连通或搜索一条路径，DFS 也常见。BFS 会保存一层队列，DFS 可以用递归或显式栈，空间特点也不同。

追问 3：二分查找为什么总写错？

因为边界定义不一致。写代码前要明确区间是闭区间还是半开区间、循环条件、目标不存在时返回什么，以及 mid 变化是否保证区间缩小。二分不只用于数组，也可用于满足单调性的答案空间。

追问 4：Top K 为什么常用小根堆？

维护大小为 K 的小根堆，堆顶是当前 K 个元素中最小的；新元素比堆顶大时替换，始终保留最大的 K 个。遍历 n 个元素的复杂度约为 O(n log K)，比完整排序 O(n log n) 更适合 K 远小于 n 的场景。

易错点

  • 只背复杂度，不说明前提、平均/最坏和空间；
  • 把链表插入 O(1) 说成查找也 O(1)；
  • 认为哈希表永远 O(1)，忽略冲突和扩容；
  • 使用二分时没有明确边界；
  • 为了炫技使用复杂算法，却不考虑代码可读性和约束。

30 秒回答模板

我会先看主要操作和约束：按下标访问选数组，按 key 查找或去重选哈希表，维护最小/最大元素选堆，先进先出选队列，层级和关系选树或图。复杂度要说明输入规模、平均还是最坏，以及额外空间。常见题型可以用哈希、双指针、二分、栈、堆和 BFS/DFS 解决，但实现前会先统一边界和异常情况。

学习停止线

本章不展开高级动态规划、网络流、字符串算法和复杂证明；能完成常见数据结构选择、基础复杂度分析和简单题的边界设计即可。

14. 软件工程与代码质量基础

题目

什么是高内聚低耦合？接口、抽象、重构、单元测试、集成测试、代码评审和持续集成分别解决什么问题？如何判断一段代码是否容易维护？

这道题在考什么

这道题考的是工程习惯，而不是背原则名词。面试官更关心你能否把需求拆成稳定边界，能否通过测试和评审降低改动风险，以及能否在速度、质量和复杂度之间做实际取舍。

面试核心结论

可维护代码通常具有清晰的职责边界、较少的隐式依赖、可测试的接口、可读的命名和足够但不过度的抽象。高内聚意味着一个模块内的代码围绕相近职责协同，低耦合意味着模块之间依赖少且依赖稳定契约。测试、代码评审、持续集成和可观测性共同降低变更风险；它们不能替代正确的需求理解和架构判断。

四个最实用的工程问题

写或改代码前，可以先问：

  1. 职责是什么：这个模块为什么存在，哪些事情不该由它负责？
  2. 依赖是什么：依赖的是具体实现还是稳定接口，失败如何处理？
  3. 变化在哪里：未来最可能变化的规则、数据源和策略是否被隔离？
  4. 如何验证：成功、失败、边界、并发和回滚路径如何测试和观察？

测试层次

类型 关注点 特点
单元测试 一个函数或小模块的逻辑 快、定位准，通常隔离外部依赖
集成测试 多模块与真实依赖的协作 更接近实际，成本和环境要求更高
端到端测试 从入口到用户可见结果 覆盖真实链路，但慢且排查成本高
回归测试 修改后原有能力是否仍正常 依赖稳定用例和自动化执行

测试不是越多越好。高价值测试应覆盖核心业务、不变量、边界和历史故障；对外部依赖可以使用测试替身，但不能永远只测替身而不做集成验证。

抽象和重构的边界

抽象的价值是隔离变化和复用稳定概念，不是把每个类都包装成接口。过早抽象会增加跳转和理解成本；重复出现、变化方向明确、测试难写或职责明显混杂时，重构收益更高。

重构应尽量小步进行：先补测试和观测，再做一个可回滚的结构改动，保持行为不变，最后再引入新功能。不要把功能变更、框架升级和大规模重构绑成一次不可定位的提交。

高频追问

追问 1：高内聚低耦合是不是模块越小越好？

不是。模块太小会产生大量跳转和胶水代码，反而增加理解成本。合理边界应围绕职责、变化方向和事务边界划分，并让接口稳定、依赖可控。

追问 2：单元测试为什么需要 Mock？

Mock 可以隔离网络、数据库、时间和随机性，让测试快速、稳定并聚焦当前逻辑。但 Mock 过多会测到实现细节、掩盖真实集成问题，所以仍需要少量高价值集成测试。

追问 3：代码评审主要看什么？

先看需求和行为是否正确，再看边界、异常、并发、资源释放、数据安全、可观测性和测试是否充分，最后看可读性与维护成本。评审不是只挑格式问题。

追问 4：如何处理技术债？

把它与线上故障、交付风险、开发效率或安全风险关联，记录影响和偿还成本，在需求迭代、专项治理或重构窗口中逐步处理。不是所有旧代码都值得重写，也不能因为“以后可能用到”就无限扩张抽象。

易错点

  • 把设计原则当成不可违背的口号；
  • 用接口、工厂和层次包装掩盖真实的职责混乱；
  • 只写成功路径测试，不测异常和边界；
  • 认为测试覆盖率高就代表系统正确；
  • 重构时没有小步提交、回滚方案和行为验证。

30 秒回答模板

我理解的代码质量首先是职责清晰、依赖稳定、行为可验证，而不是类和接口越多越好。高内聚低耦合要结合变化方向和边界判断；单元测试保证局部逻辑，集成和端到端测试验证真实协作，评审和 CI 降低变更风险。重构通常先补测试和观测，再小步改动、保持可回滚，避免把多个高风险变化绑在一起。

学习停止线

本章不深入形式化方法、复杂组织流程和某种敏捷框架；能说清模块边界、测试层次、重构策略和代码评审重点即可。

第四部分 安全基础

15. 安全与密码学最低限度

题目

认证和授权有什么区别？哈希、加密、签名分别做什么？HTTPS、密码存储、SQL 注入、XSS、CSRF 和 SSRF 如何用最基础的话解释？

这道题在考什么

安全题通常不是考你推导密码学，而是看你是否有基本的威胁模型和防御意识。回答应先区分保护目标，再说明攻击面、验证位置和失败后的影响。

面试核心结论

安全的最低限度目标可以记成机密性、完整性、可用性，并在此基础上做身份认证、权限控制、输入校验、最小权限、审计和密钥管理。哈希是单向摘要，适合完整性校验和密码验证；加密是可逆地保护机密性；数字签名用私钥签名、公钥验证来源和完整性。HTTPS 通过 TLS 保护传输过程，但不能替代服务端授权、输入校验和终端安全。

认证、授权和会话

  • 认证 Authentication：你是谁，例如密码、证书、一次性验证码；
  • 授权 Authorization：你能做什么，例如角色、资源和租户权限；
  • 审计 Audit：谁在什么时候对什么资源做了什么操作；
  • 会话 Session：服务端如何识别连续请求属于哪个已认证主体。

Cookie、Session、JWT 都是会话实现方式或载体，不应把“使用 JWT”直接等同于安全。仍需要过期、撤销、签名密钥保护、权限校验和防重放策略。

四个密码学概念

概念 主要目标 最低限度理解
哈希 摘要、完整性、不可逆验证 同一输入得到固定摘要，不能当加密使用
对称加密 机密性 加解密使用同一把密钥，速度快
非对称加密 密钥交换或机密性 公钥和私钥成对，计算成本通常更高
数字签名 来源认证和完整性 私钥签名，公钥验证，不等于加密

密码不能直接存明文，也不应使用裸哈希；通常使用专门的密码哈希算法和随机盐，并通过参数控制计算成本。密钥管理往往比“选哪个算法名字”更容易成为实际短板。

常见 Web 风险的最低限度

风险 本质 基础防御
SQL 注入 用户输入改变 SQL 语义 参数化查询、最小权限、输入约束
XSS 恶意脚本进入页面并执行 输出编码、内容安全策略、Cookie 属性
CSRF 借助用户已有会话伪造请求 CSRF Token、SameSite、关键操作再验证
SSRF 服务端被诱导访问不该访问的地址 URL 白名单、网络隔离、限制内网访问
越权 用户访问不属于自己的资源 服务端按资源和主体做授权校验
重放 合法请求被再次发送 nonce、时间窗、幂等键和状态校验

安全校验必须在服务端完成。前端隐藏按钮只能改善体验，不能作为授权依据。

HTTPS 只记握手目标

HTTPS 是 HTTP 运行在 TLS 之上。TLS 通过证书验证服务端身份，协商会话密钥，并用对称加密保护后续通信，同时检测篡改。它主要解决传输链路中的窃听、伪装和篡改；如果服务端本身越权、日志泄露密钥或客户端已被攻陷，HTTPS 不能兜底。

高频追问

追问 1：哈希和加密有什么区别？

哈希是单向摘要，通常无法从摘要还原原文，适合校验和密码验证；加密强调机密性，持有密钥的一方可以解密。密码存储通常不应使用可逆加密来代替专用密码哈希。

追问 2：JWT 一定比 Session 安全或先进吗？

不一定。JWT 便于跨服务携带声明，但撤销、过期、大小和泄露后的处理需要额外设计；Session 由服务端保存状态，撤销直接但需要共享或粘性存储。应根据部署、会话生命周期和安全要求选择。

追问 3：为什么参数化查询能防 SQL 注入？

它把 SQL 模板和用户数据分开传递，用户输入被当作值而不是 SQL 语法的一部分。拼接字符串、只在前端校验或使用黑名单替换都不如参数化可靠。

追问 4：授权为什么必须在服务端每次校验？

客户端提交的身份、角色和资源 ID 都可能被篡改；服务端才是可信边界。授权要校验当前主体对当前资源和当前操作的权限，并防止通过修改 ID 访问他人数据。

易错点

  • 把 Base64、编码或哈希说成加密；
  • 认为 HTTPS 后端就不需要鉴权和输入校验；
  • 只做登录认证，不做资源级授权；
  • 把 JWT 当成自动可撤销的登录状态；
  • 为了排障在日志中输出密码、Token 或完整敏感数据。

30 秒回答模板

安全基础可以从机密性、完整性和可用性出发，再落实到认证、授权、审计、最小权限和输入校验。哈希是单向摘要，加密保护机密性，签名用私钥证明来源和完整性；HTTPS 保护传输但不能替代服务端权限控制。常见 Web 风险要在服务端用参数化查询、输出编码、CSRF 防护、SSRF 限制和资源级授权处理，同时做好密码哈希、密钥管理和敏感信息脱敏。

学习停止线

本章不深入密码学证明、TLS 协议字段、渗透测试工具和合规条款；能正确区分保护目标、常见攻击面和基础防御即可。

16. 大数据与搜索基础

题目

什么是 OLTP、OLAP、数据仓库、数据湖、批处理和流处理？搜索引擎为什么需要倒排索引？Elasticsearch 和关系型数据库如何分工？

这道题在考什么

这一章只负责开拓眼界，防止面试中出现“大数据、实时数仓、全文检索、倒排索引”等词时完全陌生。重点是知道数据写入、分析和搜索的目标不同，不要把所有数据都塞进同一个数据库。

面试核心结论

OLTP 面向在线业务交易，强调单条或少量记录的并发读写、事务和低延迟；OLAP 面向分析，通常扫描大量数据并做聚合。数据仓库更强调结构化分析模型，数据湖以较低成本保存多种原始数据。批处理按批次处理历史数据，流处理持续处理事件。全文搜索常用倒排索引，把词项映射到包含它的文档，从而避免每次逐文档扫描；搜索引擎适合检索和相关性排序，关系型数据库通常仍是业务事实来源。

OLTP 和 OLAP 的直观区别

维度 OLTP OLAP
目标 完成业务交易 分析趋势和汇总
数据访问 少量行、频繁并发 大量行、聚合扫描
典型问题 下单、扣库存、更新用户 销售报表、指标分析
主要关注 事务、并发、低延迟 扫描效率、模型和成本

同一份业务数据常从交易库同步到分析系统，不能为了报表直接对线上主库执行大范围复杂扫描。

倒排索引怎么理解

正排可以理解为“文档 → 内容”，倒排是“词 → 包含该词的文档列表”。建立倒排后，搜索“分布式 系统”可以分别找到候选文档，再结合词频、位置、字段权重和其他算法排序。搜索引擎还会做分词、分析、索引刷新和分片，因此“写入成功”与“立刻可搜索”可能存在短暂延迟。

批处理和流处理

  • 批处理：积累一批数据再运行，吞吐高、重算和历史修复相对直观，延迟通常较高；
  • 流处理：事件到达后持续处理，延迟低，但要处理乱序、重复、迟到、状态和故障恢复；
  • Lambda/Kappa 等架构：尝试组合或统一批流路径，解决实时与历史重算之间的取舍，具体方案要看团队能力和业务要求。

Elasticsearch 的定位

只记四个词：文档、索引、分片、副本。业务数据写入关系库后，可以通过同步任务或消息更新搜索索引；搜索索引通常是可重建的派生数据，因此要设计全量重建、增量失败重试和版本兼容。不要把搜索引擎当成天然的唯一事实源，除非业务明确选择了它并承担相应的一致性和运维成本。

高频追问

追问 1：为什么不能直接用 LIKE '%关键词%' 做大规模搜索？

前缀通配和包含匹配可能无法有效利用普通 B+ 树索引，容易扫描大量数据；全文搜索还需要分词、相关性、词项组合和高亮等能力，倒排索引更适合。小数据量和简单条件仍可直接使用数据库查询。

追问 2：搜索结果为什么可能不是最新的？

业务库到搜索索引通常是异步同步，索引刷新也可能有延迟；消息丢失、重复或消费失败会造成更久的不一致。需要监控同步延迟、失败重试和全量校准，而不是简单地假设写库就立即可搜。

追问 3：数据仓库和数据库有什么区别？

数据库可以泛指数据管理系统；在这个语境下，业务数据库主要服务在线交易，数据仓库主要面向跨主题、历史数据和分析查询。二者在模型、负载、存储布局和查询习惯上不同，通常通过数据管道连接。

追问 4：流处理一定比批处理好？

不一定。流处理降低延迟，但状态管理、乱序、重放和运维复杂度更高。如果业务只需要小时级或天级报表，批处理更简单可靠。应按时效性、数据量、修正方式和团队能力选择。

易错点

  • 把“大数据”简单等同于某个产品；
  • 把 OLAP 查询直接压到线上交易库；
  • 认为搜索引擎写入后一定立即可见；
  • 把搜索索引当成不可丢失的唯一事实数据；
  • 只谈实时性，不谈乱序、重放、校准和成本。

30 秒回答模板

OLTP 负责在线交易，重视事务和低延迟；OLAP 负责大规模分析，重视扫描和聚合。批处理按批次运行，流处理持续处理事件，但要处理乱序、重复和状态恢复。全文搜索用倒排索引把词映射到文档，适合检索和排序；搜索引擎通常是业务库数据的派生索引，需要考虑同步延迟、失败重试和全量重建。

学习停止线

本章不深入 Hadoop/Spark/Flink 内核、搜索相关性算法和数仓建模全套方法；能区分交易、分析、搜索、批处理和流处理的定位即可。

17. AI、LLM 与 Agent 最小地图

题目

什么是大语言模型、Token、Embedding、RAG、微调和 Agent？为什么模型会幻觉？如何从效果、延迟、成本和安全角度评价一个 LLM 应用？

这道题在考什么

本章不是替代已有的 LLM 与 Agent 专题笔记，而是提供非主攻方向的最低限度连接。面试官可能并不要求你训练模型，但希望你能区分模型能力、外部知识、工具调用、工作流编排和评测治理。

面试核心结论

LLM 根据上下文中的 Token 预测后续 Token，擅长语言生成和模式归纳，但不天然保证事实正确、长期记忆或实时知识。Embedding 把文本映射为向量，用于相似度检索；RAG 先从外部知识库检索相关内容，再把证据放入上下文生成答案；微调改变模型参数以适应任务风格或能力。Agent 通常是在模型决策外增加工具、状态、循环和执行约束的系统，不等于简单调用一次模型。

这些概念不要混淆

概念 解决的问题 最低限度理解
Prompt 指导当前请求的行为 不会凭空增加模型已学会的事实能力
Context 当前可见的输入和历史 受长度、成本和信息噪声限制
Embedding 表示语义相似性 常用于检索、聚类和匹配
RAG 让回答参考外部知识 质量取决于切分、检索、重排和引用
微调 调整模型参数和行为 适合稳定任务模式，不等于实时知识库
Tool Calling 让模型调用外部能力 工具参数和权限必须由程序校验
Agent 让模型参与多步决策与执行 需要状态、停止条件、重试和观测
Evaluation 衡量回答和系统是否可靠 不能只看单个示例的主观效果

为什么会幻觉

模型的基本目标是生成概率上合理的文本，不是访问一个永远正确的事实数据库。幻觉可能来自知识缺失、上下文冲突、检索错误、提示歧义、长上下文噪声和生成随机性。基础治理包括提供可靠上下文、要求引用或拒答、结构化输出校验、工具结果验证、敏感场景人工审核和离线/在线评测。

LLM 应用的基本链路

用户请求 → 输入安全检查 → Prompt/上下文组装 → 可选检索和工具调用 → 模型生成 → 输出解析与事实/权限校验 → 返回或进入人工审核 → 记录成本、延迟、质量和失败原因。

这里的“模型回答正确”只是链路中的一个环节。检索召回错误、工具权限过大、上下文泄露和输出没有结构化校验，都可能造成系统级故障。

高频追问

追问 1：RAG 和微调怎么选？

需要引用不断变化的外部知识、希望可追溯时，优先考虑 RAG；需要稳定地改变输出格式、风格或任务行为时，可以考虑微调。二者也可以组合。微调不适合替代频繁更新的事实库，RAG 也不能解决模型全部推理和表达问题。

追问 2：Agent 和工作流有什么区别？

工作流通常由程序预先定义步骤和分支，确定性更强；Agent 让模型根据目标和当前状态选择下一步工具或行动，灵活性更高但不确定性和安全风险也更大。很多生产系统会把模型决策限制在可控工作流中。

追问 3：如何降低 LLM 应用延迟和成本？

减少无效上下文和检索量，选择合适模型，缓存可复用结果，流式返回，控制工具调用次数，设置超时和降级，并用真实流量统计 Token、P95/P99 延迟和失败率。不能只盯单次模型价格，还要算检索、工具、存储和人工审核成本。

追问 4：如何评价一个 RAG 系统？

至少分开看检索和生成：检索是否召回了正确证据，答案是否忠于证据、完整、可引用，系统是否满足延迟、成本、安全和拒答要求。离线测试集、人工评审、模型辅助评审和线上反馈应结合使用。

易错点

  • 把 LLM 当成实时、确定且永远正确的数据库；
  • 把 RAG、微调和 Agent 当成同一件事；
  • 允许模型直接执行未经校验的高权限工具；
  • 只看 Demo 效果，不看幻觉、延迟、成本和数据泄露；
  • 把增加 Prompt 长度当成解决所有问题的方法。

30 秒回答模板

LLM 是基于上下文预测 Token 的生成模型，能力强但不保证事实正确。Embedding 用于语义表示，RAG 通过检索外部知识增强回答，微调主要改变稳定的任务行为，Agent 则在模型外增加工具、状态和多步执行。做应用时我会把检索、工具权限、输出校验、拒答、评测、延迟、成本和数据安全一起设计，而不是只看模型能否生成一段流畅文字。

学习停止线

本章不深入 Transformer 推导、训练并行、量化内核和 Agent 框架源码；能辨认模型、检索、工具、工作流和评测治理的边界即可，深入内容见对应专题笔记。

18. 技术选型速查表

题目

面对一个新需求，如何选择数据库、缓存、消息队列、同步/异步通信、单体/微服务和部署方式？如果面试官问“为什么不用另一个技术”，怎么回答？

这道题在考什么

技术选型题考的是约束分析和取舍能力，不是产品排行榜。成熟回答应该先确认业务目标、数据特性、规模和团队条件，再比较一致性、延迟、吞吐、故障恢复、运维成本和迁移成本。

面试核心结论

选型没有脱离场景的最优答案。先确定核心事实、读写模式、规模增长、延迟和一致性要求，再选择最简单且能满足约束的方案；如果引入缓存、消息队列、搜索或微服务，应同时说明它们带来的失效、重复、最终一致性、运维和排障成本。面试中应先讲当前方案，再说明什么时候会切换到更复杂的方案。

常见场景的最低限度选择

场景 常见起点 需要补充的判断
事务、关联查询、强约束 关系型数据库 索引、事务边界、容量和读写分离
高速热点读取 缓存 失效、一致性、击穿和容量
异步解耦、削峰 消息队列 投递、幂等、顺序、积压和重试
文档结构灵活、特定访问模式 NoSQL 一致性、查询能力、迁移和运维
全文检索和相关性排序 搜索引擎 索引同步、刷新延迟和重建
必须立即得到结果 同步 RPC/HTTP 超时、重试、依赖隔离
可延后或可重试的副作用 异步事件/任务 最终一致、死信和幂等
业务规模较小、边界未稳定 单体优先 模块化、测试和未来拆分边界
团队和领域边界成熟 服务化/微服务 部署、网络、观测和数据一致性成本
环境一致性和快速交付 容器化 镜像、资源、网络、持久化和安全

一套通用的选型顺序

  1. 目标：要解决的是正确性、延迟、吞吐、可用性还是交付效率？
  2. 数据：结构、关系、读写比例、增长速度、保留周期和删除要求是什么？
  3. 一致性：哪些操作必须立即正确，哪些可以最终一致，是否需要事务？
  4. 规模：当前和未来的 QPS、数据量、热点、并发和峰值是多少？
  5. 故障：组件失败、重复、积压、数据损坏和网络分区时怎么办？
  6. 运维：团队是否会用、监控告警是否具备、备份恢复和升级谁负责？
  7. 成本：资源、托管、开发、迁移、培训和长期复杂度如何？

“为什么不用 X” 的回答方式

不要回答“X 不好”，而要回答“在当前约束下，Y 的收益更匹配”。例如：

目前数据量和团队规模不大，核心需求是事务和关联查询，所以先用关系型数据库，保持模型简单。若将来全文检索成为独立性能瓶颈，再把搜索能力拆到专门的搜索引擎；但业务库仍作为事实来源，并补上索引同步、重建和一致性处理。

这种回答同时说明了当前选择、替代方案的适用条件，以及引入新组件的成本。

面试防守的五层回答法

面对不熟悉的技术，可以按下面顺序回答：

  1. 定义：它是什么；
  2. 问题：主要解决什么痛点；
  3. 流程：最基本的工作方式；
  4. 风险：一个常见坑和一个故障边界；
  5. 边界：自己掌握到哪里，实际项目会如何继续验证。

例如被问到消息队列，不必从某个产品源码开始，而是先说异步解耦和削峰，再讲生产确认、持久化、消费确认、重复幂等和积压，最后说明具体产品差异需要结合吞吐、顺序、运维和团队经验评估。

高频追问

追问 1：是不是组件越多，系统越先进？

不是。每个组件都增加部署、监控、升级、故障和数据一致性成本。应优先使用能满足当前约束的最简单方案，再根据可观测的瓶颈演进，而不是为想象中的规模提前堆复杂度。

追问 2：什么时候该拆微服务？

当领域边界、团队职责、发布节奏、扩缩容需求或故障隔离确实不同，且组织已经能承担分布式运维成本时再考虑。代码目录拆开但数据库、发布和责任仍完全耦合，不一定带来真正收益。

追问 3：如何比较两个中间件？

从语义和约束比较：数据模型、读写模式、吞吐和延迟、顺序与一致性、持久化和恢复、扩缩容、监控运维、生态和团队熟悉度。不要只比较宣传中的峰值 QPS。

追问 4：面试时不会的技术怎么回答？

先说已知的抽象定位和相邻概念，再明确不确定的细节，不编造源码行为；可以给出验证路径，例如查官方文档、做最小实验、看监控指标或确认团队已有约束。基础防守的目标是避免概念混乱，不是伪装成专家。

易错点

  • 用“高并发”三个字替代具体 QPS、数据量和一致性要求；
  • 把成熟产品的默认架构当成所有场景的答案；
  • 只比较性能，不比较故障恢复和运维成本；
  • 为了展示知识引入不必要的缓存、队列和微服务；
  • 不会时硬背细节，导致在追问中前后矛盾。

30 秒回答模板

我会先确认业务目标、数据模型、读写模式、规模、延迟和一致性，再比较方案的吞吐、故障恢复、运维成本和团队能力。关系型数据库适合事务和关联查询，缓存适合热点读取，消息队列适合异步解耦，搜索引擎适合检索；但每引入一个组件都要补上失效、重复、积压、同步和观测方案。当前优先选满足约束的最简单方案，等瓶颈被数据证明后再演进。

学习停止线

本章不提供产品排名，也不要求记住所有中间件参数；能用统一的约束—收益—风险框架回答“为什么选它、什么时候换它”即可。
